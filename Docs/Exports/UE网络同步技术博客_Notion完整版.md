## 第一章：网络基础

整理日期：2026-09-27。返回总目录。

本章要解决的是：一条消息怎样从程序发到另一个程序，途中为什么会等待、丢失、重复，以及应用应如何处理。TCP/UDP 详细掌握；HTTP、HTTPS、DNS 理解常见机制与边界；网络层和链路层先掌握路径，不展开路由算法推导。

建议阅读顺序：先看 1.1 建立分层概念，再重点读 1.3 TCP、1.4 UDP，随后补 1.2 应用层；1.5～1.7 用来把协议和实际游戏程序联系起来。预测、插值、帧同步与状态同步的完整设计留到第二章，UE 专有实现留到第三章。

### 1.1 分层与几个必须分清的指标

**1.1.1 OSI 七层与 TCP/IP 四层**

分层的作用是分清职责，不是要求所有软件必须照着层数拆成相同数量的类。

| OSI 概念层 | TCP/IP 常用分层 | 回答的问题 | 例子 |
| --- | --- | --- | --- |
| 应用、表示、会话 | 应用层 | 消息是什么意思，怎样编码与管理应用会话？ | HTTP、DNS、游戏消息、序列化；TLS 提供安全保护 |
| 传输 | 传输层 | 数据怎样交给两端的应用，是否要可靠和有序？ | TCP、UDP |
| 网络 | 网络层 | 目标在哪，经过哪些网络转发？ | IPv4、IPv6、路由、ICMP |
| 数据链路、物理 | 网络接口层 | 如何把数据交给当前链路的下一跳？ | 以太网、Wi-Fi、MAC、物理信号 |

发送时逐层添加需要的控制信息，接收时逐层解析。可以粗略理解为“业务消息 → TCP 段或 UDP 数据报 → IP 包 → 当前链路的帧”。

> **Q：模型层数、端口和 Socket 容易混在哪里？**
>
> - TCP/IP 也有五层教学划分，通常只是把网络接口层再拆开，不是两套互相冲突的网络。
> - TLS、QUIC 和实际协议栈的职责不总能机械塞进单一 OSI 方格；分层主要用于解释接口与责任。
> - IP 地址用于网络寻址；端口用于传输层分用。TCP 连接通常用源 IP、源端口、目的 IP、目的端口标识；跨不同传输协议讨论时再加协议类型，成为五元组。
> - 同一服务器端口可以服务很多 TCP 连接，因为对端的 IP/端口等不同。监听 Socket 和每条已建立连接不是同一个对象。
> - Socket 是操作系统提供的通信接口，不是与 TCP、UDP 并列的网络协议。Linux socket 手册

**1.1.2 延迟、RTT、抖动、丢包、吞吐和包率**

| 指标 | 含义 | 游戏中主要影响 |
| --- | --- | --- |
| 单程延迟 | 消息从一端到另一端的时间 | 输入何时到达服务器 |
| RTT | 一次往返所需时间 | 确认、重传和预测历史窗口 |
| 抖动 | 延迟或到达间隔的变化 | 插值缓冲是否耗尽、表现是否忽快忽慢 |
| 丢包率 | 在明确统计口径和时间窗内，预期数据未收到的比例 | 重传、状态缺口与恢复成本 |
| 带宽 / 吞吐 | 可承载能力 / 实际完成的传输速率 | 单位时间能同步多少内容 |
| 包率 | 每秒的数据包数量 | 包头、系统调用和收发处理开销 |

宽带下载很快，不代表操作延迟低。等待可能来自无线竞争、路由传播、发送队列、服务器排队、逻辑 Tick，以及客户端为了平滑显示而增加的缓冲。

> **Q：为什么下载快，也不能说明联机体验好？**
>
> - RTT 除以二只能估计单程延迟，上下行可能不对称。精确单程测量还需要处理两端时钟偏差。
> - RTT 可以包含对端处理或延迟确认时间，比较数据前先定义计时起止点。
> - 应用没收到消息，不一定是物理链路丢包，也可能是本机缓冲溢出、过滤、过期丢弃或解析失败。
> - Mbps 是兆比特每秒，MB/s 是兆字节每秒，换算要除以 8；应用有效负载还要扣除协议与重传开销。
> - 渲染 FPS、服务器 Tick、Actor 更新频率上限、实际包率是四件事。设置 100 Hz，不代表每秒真的发出 100 个更新包。
> - 平均值会隐藏停顿，除了均值，还应看 P95/P99、峰值和采样条件。不能把某个 CPU 作用域耗时当成整帧耗时。

### 1.2 应用层：HTTP、HTTPS、DNS 与连接入口

**1.2.1 HTTP 在解决什么问题**

HTTP 规定请求方法、资源标识、请求/响应字段、状态码等语义。请求通常包含方法、目标和字段，也可以有内容；响应包含状态、字段和可选内容。

HTTP 不是“TCP 的另一种叫法”。HTTP/1.1 和常见 HTTP/2 使用 TCP；HTTP/3 使用 QUIC，而 QUIC 建立在 UDP 上。TLS 是否使用、是否新建连接、如何复用连接，需要结合协议版本和运行环境判断。

**1.2.2 GET 和 POST 的区别**

重点是**请求语义**，不是简单背“一个放 URL，一个放 body”。

| 维度 | GET | POST |
| --- | --- | --- |
| 主要语义 | 获取目标资源的表示 | 让目标资源按自身规则处理提交的内容 |
| 安全性语义 | 属于安全方法：不请求改变服务器业务状态 | 不属于安全方法，可以请求状态变更 |
| 幂等性语义 | 幂等 | 不默认保证幂等 |
| 缓存 | 常见，可按缓存规则保存响应 | 在满足规范条件时也可缓存，但实际支持较少 |
| 常见用法 | 查询公告、读取配置 | 提交订单、创建房间的后台请求等 |

这里“安全”不是指加密，“幂等”也不是指响应字节完全相同：幂等是相同操作执行一次与多次，对目标业务状态的预期效果一致。重复 DELETE 可能第一次返回成功、第二次返回不存在，仍可符合幂等语义。

> **Q：GET/POST 的常见简化说法哪里不准确？**
>
> - GET 的请求内容没有通用定义的语义；不能写成“协议语法绝对禁止 body”，但也不应依赖它被服务器、代理和缓存一致处理。常规查询使用查询参数。
> - POST 也可以包含 URL 查询参数，并非参数只能放 body。
> - HTTP 没有规定所有 GET 的 URL 都只能是某个固定长度；浏览器、代理和服务器有各自限制。POST 内容也不是无限长。
> - POST 不比 GET 天然保密。没有 TLS 时，两者都可能被窃听；使用 HTTPS 时，路径、查询串和内容都在加密保护内，但 URL 仍可能进入浏览器历史、应用日志等。
> - “GET 只发一个 TCP 包，POST 一定发两个”是错误说法。分段取决于消息大小和网络栈；`Expect: 100-continue` 是可选机制，不是 POST 固定流程。
> - POST 可以通过业务请求 ID、唯一约束和事务设计成可安全重试的接口，但这是业务实现，不是方法名自动提供的能力。
> - 对“发奖请求超时”不能直接判定没发奖：可能服务器已成功处理，只是响应丢失。重试必须能识别是否为同一笔操作。

依据与细读：RFC 9110 §9：方法语义。

**1.2.3 状态码、缓存与幂等**

常见状态码先掌握这些：200 成功；201 创建；204 成功但无响应内容；301/308 永久重定向；302/307 临时重定向；304 条件请求命中可复用缓存；400 请求有问题；401 缺少或不满足认证凭据；403 拒绝访问；404 不存在；409 状态冲突；429 限流；500 服务内部错误；502 网关收到无效上游响应；503 暂时无法服务；504 等待上游超时。

> **Q：状态码与缓存还需要分清哪些边界？**
>
> - 307/308 要求重定向时保留方法；301/302 的历史客户端行为可能把 POST 改成 GET，不能仅凭“永久/临时”来选。
> - 304 不是发送一份新资源正文，而是让客户端复用已有表示并更新相应元数据。
> - 401 和 403 不等于简单的“没登录/登录了”二分；按认证挑战和访问策略理解。
>
> 缓存分成“仍新鲜，直接使用”和“先问服务器还能不能用”两条常见路径：
>
> - 新鲜度通常由 `Cache-Control: max-age` 等控制；命中时可能不发请求。
> - 需要重新验证时可发送 `If-None-Match` 对应 ETag，或 `If-Modified-Since` 对应 Last-Modified；内容未变可返回 304。
> - `no-cache` 不是禁止保存，而是复用前需要验证；`no-store` 才是要求不存储。
> - ETag 与 Last-Modified 都有时，条件请求的处理有优先规则，不是随便选一个；秒级修改时间也未必能表达短时间内的所有变化。
> - POST 响应可缓存不等于缓存可以替服务器执行下一笔 POST。其缓存需满足规范的显式条件，不能用“上次成功了”替代新事务处理。

参考：RFC 9110 §13：条件请求、RFC 9111：缓存。

**1.2.4 HTTP 无状态，为什么还能保持登录**

无状态指请求语义不要求协议自动保留上一条请求的业务上下文，不是“服务器不能存数据”，也不是“每条请求必须重新建 TCP”。

- Cookie 是浏览器按域、路径、过期和安全属性等规则保存并随请求携带的数据。
- 常见服务端 Session 保存登录上下文；Cookie 中只放一个随机 Session ID，让服务端找到对应记录。
- 也可以用签名令牌等方案表达身份与声明；签名只能防篡改，不意味着内容已加密，也不自动解决撤销。
- 禁用 Cookie 不代表不能登录。可以按应用协议传递令牌，例如 Authorization 字段；浏览器应用还需要考虑保存方式与攻击面。不建议把长期凭据放在 URL。

> **Q：Cookie、Session 和本地存储有哪些不同？**
>
> - HttpOnly 限制 JavaScript 直接读取 Cookie；Secure 限制其通过安全通道发送；SameSite 限制某些跨站携带情形。它们解决的问题不同。
> - localStorage 不会像 Cookie 一样自动随 HTTP 请求发送，可被同源脚本访问，因此要防 XSS；“存在 localStorage 就安全”不成立。
> - Cookie 自动携带凭据带来 CSRF 风险；XSS 则可能在用户会话中执行恶意脚本。两者不是同一种问题。
> - 浏览器 Cookie、Web 登录 Session、TCP 连接和 UE Online Session 是不同层的概念。UE 的房间 Session 不是浏览器会话 Cookie。

参考：MDN：HTTP Cookies、MDN：Web Storage。

**1.2.5 HTTP 长连接、WebSocket 与 RPC**

HTTP/1.1 默认支持持久连接，同一 TCP 可以承载多次请求/响应；“长连接”不等于有永久在线保证。空闲超时、代理策略和故障都可能断开连接。

WebSocket 建立后提供双向消息通信，适合持续推送。经典 HTTP/1.1 建立方式通过 Upgrade 握手；后续有自己的帧格式，不是每条消息都重新发送一份 HTTP 请求。其他 HTTP 版本有相应建立机制，不应把 Upgrade 固定成所有版本的唯一流程。

RPC 是“请求远端执行某项操作”的调用抽象；HTTP 是协议，两者不是只能二选一。RPC 可基于 HTTP、TCP 或其他传输实现。UE 的 Gameplay RPC 还有自身的 Actor、连接与可靠性规则，不能套用一般后台 RPC 的所有行为。

> **Q：长连接、多路复用和心跳是什么关系？**
>
> - HTTP/2 多路复用减少了 HTTP/1.1 连接内的请求排队限制，但 TCP 丢失字节仍会阻塞该连接向上连续交付，影响其上的多个流。
> - HTTP/3 使用 QUIC 的独立流，降低跨流的传输层队头阻塞；同一可靠流缺少必要数据仍要等待，连接拥塞仍会影响整体，不是“永不阻塞”。
> - WebSocket over TCP 仍受 TCP 有序交付影响。双向实时推送不意味着丢包后无需等待。
> - HTTP Keep-Alive 是连接复用；TCP Keepalive 是传输层探测；应用心跳用于判断应用级活性，三者不能混用。

参考：RFC 9112 §9：HTTP/1.1 连接管理、RFC 9113：HTTP/2、RFC 9114：HTTP/3、RFC 6455：WebSocket。

**1.2.6 HTTPS 与 TLS：不仅是把正文加密**

HTTP 明文传输不能自行提供链路保密、对端身份认证和抗篡改。HTTPS 通过 TLS 保护 HTTP 通信；SSL 是历史名称，现代说明应以 TLS 为主。

以常见 TLS 1.3 证书认证、临时密钥交换的完整握手为例：

1. 客户端发送 ClientHello，携带支持的版本、算法、密钥交换参数等。
2. 服务器选择参数并发送 ServerHello，双方根据协商结果派生握手密钥。
3. 服务器发送受保护的握手信息，包括证书、证明持有私钥的签名及 Finished。
4. 客户端验证身份与握手完整性，再发送自己的 Finished，之后使用派生的应用流量密钥保护业务数据。

这是机制概括，不是所有恢复会话、客户端证书或 HelloRetryRequest 分支的完整时序。TLS 1.3 完整握手通常按 1-RTT 描述，不包含之前的 DNS 和 TCP 建连耗时。

> **Q：证书验证、密钥协商和 0-RTT 有哪些限制？**
>
> - 不要把 TLS 1.3 写成“客户端生成 AES 密钥，用服务器证书公钥加密发过去”。常见流程是临时 (EC)DHE 协商并派生密钥；证书私钥签名负责身份认证，恢复会话还可能使用 PSK。
> - 客户端需要验证信任链、签名、有效期、访问主机名与证书身份匹配、证书用途等；撤销等检查取决于实现与策略。仅仅“证书能解开”不是完整校验。
> - 可信根通常来自本地信任库，不是服务器发一个自称可信的根就可以被信任。
> - 不跳过证书验证，是抵抗中间人冒充的关键。若攻击者控制终端、植入可信根或偷取密钥，仍可能突破相应安全边界。
> - TLS 1.3 的 0-RTT 是特定恢复场景的提前数据，并不意味着首次连接零等待；提前数据有重放风险，不适合未经保护的发奖、购买等操作。
> - 对称加密负责高效保护数据；AEAD 同时提供机密性与完整性。加密流量仍可能暴露长度、时序与端点等元信息。
> - HTTPS 保护传输，不保证服务端逻辑正确，也不能阻止玩家在自己的游戏进程里修改明文或构造合法格式的作弊输入。

参考：RFC 8446 §2：TLS 1.3 握手、§8：0-RTT 与重放。

**1.2.7 DNS：域名怎样变成可连接的地址**

应用需要地址时，通常先经过本地解析机制与缓存，再向递归解析器查询。解析器缓存未命中时，可依次向根、顶级域和权威服务器获得委派与答案，最后缓存结果返回。根服务器通常给下一步该问谁，不是替每个域名直接保存最终 IP。

常见记录：A 对应 IPv4；AAAA 对应 IPv6；CNAME 表示别名；NS 指示权威服务器。TTL 指导缓存时长，改记录不会让所有旧缓存瞬间失效。

> **Q：DNS 解析与传输方式有哪些容易混淆的地方？**
>
> - 客户端向递归解析器提出递归请求，不代表解析器每一步也递归替换；它常通过迭代查询沿委派链寻找答案。
> - DNS 既支持 UDP，也支持 TCP。传统 UDP 小包上限与 EDNS 扩展要区分；截断可触发 TCP 重试，也可直接使用 TCP，不是“只有超过 512 字节才准用 TCP”。
> - DoT 和 DoH 分别通过 TLS、HTTPS 保护相应查询链路；DNSSEC 用于验证 DNS 数据真实性，和链路加密不是同一件事。
> - 一个域名可能对应多个地址；返回 IP 不等于该 IP 上的目标端口可达，后面仍有路由、防火墙、监听和 TLS 校验。

参考：RFC 1034：DNS 概念、RFC 7766：DNS over TCP。

**1.2.8 输入网址到页面显示，怎样串起来**

以一次需要新建连接的普通 HTTPS 请求为例：解析 URL → 查缓存并取得地址 → 选择路径建立 TCP → TLS 验证和协商 → 发送 HTTP 请求 → 网关/应用处理并响应 → 浏览器解析 HTML、获取资源并布局绘制。

> **Q：每次打开页面都必须经历所有步骤吗？**
>
> - 命中缓存、复用既有连接、预连接等会省掉部分步骤；HTTP/3 不走 TCP 三次握手。
> - 页面不是等所有资源都下载完才统一开始绘制；脚本、样式和资源依赖会影响后续解析与渲染。
> - 一页可能访问多个域名和连接；“页面显示后立刻四次挥手”不是固定步骤，连接可以继续复用。

**1.2.9 Nginx：知道放在哪里即可**

它可作为反向代理，将客户端请求转给后端服务，也可承担负载均衡、静态资源、缓存和 TLS 终止等职责。正向代理代表客户端访问外部，反向代理代表后端服务接收客户端请求。

HTTP 反向代理不等于能直接代理任意 UDP 游戏连接。Nginx 另有 stream 等模块处理 TCP/UDP，部署时还需要考虑协议、会话路由、超时与真实地址传递，不能只加一条 HTTP 配置就宣称完成游戏服务器部署。Nginx stream proxy 官方说明

### 1.3 TCP：本章重点

**1.3.1 TCP 究竟提供什么**

TCP 提供面向连接、全双工、可靠有序的**字节流**。双方建立连接状态后，可以同时发送与接收；应用不需要自己重排 TCP 已交付的字节，但仍需要定义自己的消息边界与业务确认。

“可靠”不代表网络永远不坏，也不保证操作在指定时间内完成。连接可能超时或被复位；即使对端 TCP 确认了字节，也不能推导出对端应用已经发奖、写盘或处理成功。

> **Q：TCP 可靠，能否证明业务已经成功？**
>
> - `send()` 成功通常说明数据被本机网络栈接受，不说明已经到达远端，更不说明远端业务完成。
> - 同一个 TCP 字节流的顺序保证，不能扩展成多个连接之间的全局顺序。
> - 网络可重复传输某些段，但正常 TCP 接收会去重后向应用交付字节；应用超时后主动再次发送同一条请求，仍可能形成两条合法业务消息。
> - TCP 校验和用于发现传输错误，不是密码学身份认证；TCP 本身不会把数据加密。

参考：Microsoft send 语义、RFC 9293：TCP 规范。

**1.3.2 TCP 头部：优先理解字段用途**

| 字段 | 大小或形式 | 为什么需要 |
| --- | --- | --- |
| 源端口、目的端口 | 各 16 位 | 分用到对应通信端点 |
| Sequence Number | 32 位 | 标识当前发送方向的字节位置 |
| Acknowledgment Number | 32 位 | 表达接收方下一步期待的连续字节序号 |
| Data Offset | 4 位，以 4 字节为单位 | 找到 TCP 内容从哪里开始 |
| 控制标志 | SYN、ACK、FIN、RST、PSH、URG 等 | 建连、确认、关闭及其他控制 |
| Window | 16 位字段，可配合窗口扩大选项 | 告知接收空间，不是固定发送速度 |
| Checksum | 16 位 | 检测传输中的差错 |
| Urgent Pointer | 16 位 | 配合 URG 表达紧急指针；普通游戏消息无需依赖它 |
| Options 与填充 | 可变长 | MSS、窗口扩大、SACK、时间戳等扩展 |

基本头部至少 20 字节；Data Offset 对应的常规最大头长为 60 字节。MSS 是 TCP 数据部分的最大段大小，不含 TCP/IP 头，不要与链路 MTU 混同。

> **Q：序号、控制标志和头部图有哪些细节？**
>
> - SYN 用于建立并同步序号；FIN 表示发送方向结束；RST 用于中止或拒绝等情况，不能把它等同于正常挥手。
> - ACK 标志表示确认号字段有意义，不是说这条报文一定没有数据。数据报文经常同时携带 ACK。
> - PSH 不是应用消息结束标记，不能拿它解决粘包；一次 `send()` 也不保证对应一个 PSH 段。
> - 序号按字节计数。若发送从 1001 开始的 100 字节，全部连续收到后可确认 1101。
> - SYN、FIN 各占一个序号位置；纯 ACK 不占。TCP 的两个方向分别维护自己的序号，不共用一个序列。
> - 一些历史教学图使用“保留 6 位 + 六个标志”的布局。RFC 9293 图已包含 CWR/ECE；当前 IANA 还列有 AE 扩展。基础学习掌握六个常见标志即可，但不能把旧图当成所有当前扩展位的完整定义。

参考：RFC 9293 §3.1：头部、IANA：TCP Header Flags、RFC 7323：窗口扩大与时间戳。

**1.3.3 三次握手：消息、序号与状态变化**

以常规客户端主动连接、服务器监听为例，双方初始序号分别为 x、y：

| 步骤 | 报文 | 主动连接方状态 | 监听方状态 |
| --- | --- | --- | --- |
| 初始 | 尚未请求连接 | CLOSED | LISTEN |
| 1 | 客户端发 SYN，Seq=x | 进入 SYN_SENT | 收到合法 SYN 后进入 SYN_RCVD，并准备回复 |
| 2 | 服务器发 SYN+ACK，Seq=y，Ack=x+1 | 收到合法响应后进入 ESTABLISHED，并发送确认 | 等待自己的 SYN 被确认 |
| 3 | 客户端发 ACK，Seq=x+1，Ack=y+1 | 已建立 | 收到合法确认后进入 ESTABLISHED |

状态变化取决于各端实际发送/接收事件，并不是两端在同一时刻一起切成 ESTABLISHED。图中的标准关闭状态名称是 `CLOSED`，不是 `CLOSE`。

**图 1｜TCP 建连与关闭的两条时间线**

```text
建连：客户端                                  服务器
      SYN(x)              ───────────────→  SYN_RCVD
      SYN+ACK(y, x+1)     ←───────────────  等待确认
      ACK(y+1)            ───────────────→  ESTABLISHED
      ESTABLISHED                            双方确认本次序号

关闭：主动关闭方                              被动关闭方
      FIN                 ───────────────→  CLOSE_WAIT（等本地应用关闭）
      FIN_WAIT_2          ←───────────────  ACK
      TIME_WAIT           ←───────────────  FIN
      ACK                 ───────────────→  LAST_ACK → CLOSED
      等待 2MSL，随后 CLOSED
```

两条时间线表达的是状态依赖；实际抓包中的 ACK 可以与数据或 FIN 合并，丢包也会导致重传。TIME_WAIT 位于发出最后 ACK 的一方，不固定等于“客户端”。

> **Q：为什么不能只做两次？**
>
> TCP 不只是让服务器“听到有人要连”，还要建立双方对**本次连接、双向初始序号**的共同认识。
>
> 服务器的 SYN+ACK 一边确认 x，一边提出自己的 y。没有第三次确认，服务器无法据此知道对方确实接受了当前这次握手的 y。如果一个旧 SYN 延迟到达，服务器只凭自己回复一次就宣布建连，也容易把历史请求当成有效新连接。
>
> 第三次确认让服务器等待对当前响应的有效反馈。说“确认双方收发正常”可以建立直觉，但不应省略序号和旧连接干扰这两层原因；它也不是防所有伪造攻击的完整安全方案。

> **Q：为什么通常不是四次？**
>
> 双方需要各发送一个 SYN，并各确认对方 SYN。服务器把“对客户端 SYN 的 ACK”和“自己的 SYN”合并成第二个报文，因此常规流程三次完成。不是因为协议规定所有握手只能出现三份实际网络报文；丢包重传与同时打开都可能改变抓包结果。

> **Q：三次分别丢了会怎样？**
>
> | 丢失位置 | 常规处理思路 |
> | --- | --- |
> | 第一次 SYN | 客户端没有得到响应，按重传策略重发 SYN，达到限制则连接失败 |
> | 第二次 SYN+ACK | 服务器仍等确认，客户端也未完成握手；重传 SYN 或 SYN+ACK 可推动恢复 |
> | 第三次纯 ACK | 服务器仍在 SYN_RCVD，通常重发 SYN+ACK；客户端收到后再次确认 |
>
> 第三次**纯 ACK 没有独立的 ACK 超时重传计时器**。后续携带有效 ACK 的数据也可能让服务器完成握手。如果第三次报文本身携带数据，则其中的数据受可靠传输规则管理，不能与纯 ACK 混说。

> **Q：握手可以带数据吗？**
>
> 第三次可以带数据。基础 TCP 也允许 SYN 携带数据，但常规语义要等握手完成后才交给应用；TCP Fast Open 的重要变化是允许满足条件时更早交付 SYN 数据，因此还要考虑重复执行的风险。不要简单背“前两次绝对不能带数据”。

> **Q：SYN 队列与 accept？**
>
> 连接握手状态和应用的 `accept()` 调用是两层事情。普通实现中，内核先维护建连与已完成连接队列，应用再取走完成的连接；不是每次都要应用主动发出 SYN+ACK。
>
> 大量只发 SYN 而不完成握手的流量可能消耗资源。SYN cookies、队列限制和限流等是防护手段，但不等于完成认证或抵抗所有 DDoS。

参考：RFC 793 §3.3～3.4：序号与握手原理、RFC 1122 §4.2.3.6：Keepalive 章节中的纯 ACK 说明、RFC 7413 §2：TFO 与 SYN 数据、RFC 4987：SYN Flood。旧 RFC 用于理解背景，现行 TCP 主规范以 RFC 9293 为准。

**1.3.4 四次挥手：先记“两个方向分别关闭”**

假设 A 主动结束发送，B 暂时还有数据要发送。FIN 只表示“我以后不再沿这个方向发新数据”，不要求对方同时关闭自己的发送方向。

| 步骤 | 发生的事 | A | B |
| --- | --- | --- | --- |
| 初始 | 双向可传数据 | ESTABLISHED | ESTABLISHED |
| 1 | A 发 FIN | FIN_WAIT_1 | 收到 FIN 后确认，进入 CLOSE_WAIT |
| 2 | B 的 ACK 到达 A，确认 A 的 FIN | FIN_WAIT_2 | CLOSE_WAIT；本地应用仍可能发送剩余数据 |
| 3 | B 的应用决定关闭，本端发 FIN | 收到后回复 ACK，进入 TIME_WAIT | LAST_ACK |
| 4 | 最后 ACK 到达 B | TIME_WAIT，等待期结束后 CLOSED | CLOSED |

这是普通顺序关闭的简化表，省略了数据与控制报文交错。B 如果当时也准备关闭，可以把对 A 的 ACK 与自己的 FIN 合并，因此抓包可能只有三次；重传又可能让数量更多。所谓四次挥手是在讲两个方向的关闭与确认，不是固定包数配额。

**1.3.5 CLOSE_WAIT、LAST_ACK、FIN_WAIT 到底在等谁**

| 状态 | 已经发生什么 | 现在主要等什么 |
| --- | --- | --- |
| FIN_WAIT_1 | 本端已经发 FIN | 本端 FIN 的确认，以及可能先到的对端 FIN |
| FIN_WAIT_2 | 本端 FIN 已被确认 | 对端也发送 FIN |
| CLOSE_WAIT | 收到对端 FIN，已知道对端结束发送 | 本地应用结束自己的发送并关闭 |
| LAST_ACK | 被动关闭一方随后也发了 FIN | 对端对这个 FIN 的确认 |
| CLOSING | 自己的 FIN 尚未确认，先收到了对端 FIN | 自己 FIN 的确认，常见于同时关闭 |
| TIME_WAIT | 关闭流程最后阶段的确认已发送 | 尾部重传与旧报文隔离所需的等待期 |

> **Q：如何从关闭状态判断该检查哪一端？**
>
> - **什么时候进入 CLOSE_WAIT？**常见于 ESTABLISHED 收到对端有效 FIN 后。此时对方不会再发新数据，但本地应用可能仍需处理已缓存内容或发送回复。
> - 大量长期 CLOSE_WAIT，应优先检查本地应用有没有漏掉关闭、被某个任务卡住、引用未释放或错误路径没有收尾；不是先把锅归给网络延迟。
> - 单个 CLOSE_WAIT 不一定是故障，短暂半关闭可以是正常协议过程。
> - FIN_WAIT_2 等对方 FIN，不是等最后一个 ACK。如果长期积累，应检查对端是否正常完成关闭，以及本机的超时与资源回收策略。
> - 同时关闭时双方都可能经过 CLOSING 并进入 TIME_WAIT；“只有客户端会 TIME_WAIT”是错误结论。
> - RST 可以中止连接，不走完整正常关闭路径；不能为减少 TIME_WAIT 就随意用复位代替优雅关闭，尚未处理的数据可能丢失。

参考：RFC 9293 §3.3.2：TCP 状态、§3.6：关闭连接。

**1.3.6 TIME_WAIT 为什么要等 2MSL**

MSL 是报文最大生存时间的设计参数，2MSL 表示其两倍，不是“两次 wait”、也不是“两倍 RTT”。

这个等待有两个目的：

1. **给关闭尾部的恢复留机会。**若最后 ACK 丢失，对方还在 LAST_ACK，会重发 FIN；本端保留 TIME_WAIT 状态，能再次确认，不至于立刻忘记这条连接。
2. **隔离旧连接的迟到报文。**避免同一组地址和端口很快被新连接复用后，旧数据仍在网络中徘徊，增加新旧连接混淆风险。

为什么是两倍而不是一倍：关闭相关的尾部报文与响应可能各经历一段最长生存时间，协议为这种往返残留留出窗口。实际收到重传 FIN 时还会重新确认并重启等待。它是协议保守规则，不是根据当前测速得到的 RTT 临时乘二。

> **Q：TIME_WAIT 多是否一定有问题，怎样区分 CLOSE_WAIT？**
>
> - 常见顺序关闭中，主动关闭并发送最后 ACK 的一端进入 TIME_WAIT；服务器也可以主动关闭，双方同时关闭也可能都进入。
> - 不能把 2MSL 写成所有操作系统统一的“60 秒”“120 秒”或“4 分钟”；实现与策略不同，排查时看目标系统。
> - TIME_WAIT 多首先可能反映短连接创建/关闭很多，不直接等同内存泄漏。应结合数量、端口耗尽、连接错误和业务流量判断。
> - 优先检查能否合理复用连接、减少无意义短连接；贸然关闭保护或复用旧四元组，可能引入迟到报文干扰等问题。
> - CLOSE_WAIT 的主要责任是本地应用收尾；TIME_WAIT 是内核正常协议等待。两者处理方向完全不同。

参考：RFC 793：序号与旧报文隔离、RFC 9293 §3.10.7：TIME-WAIT 收包处理。

**1.3.7 TCP 为什么可靠：把机制连起来**

不能只回答“因为有重传”。可靠字节流由多个机制配合：字节序号标记位置，确认告诉发送端哪些连续数据已收到，校验发现错误，发送端保留未确认数据，丢失时重传，接收端重排与去重，窗口控制在途数量。

例如连续字节 1001～1100 已到，1101～1200 丢失，1201～1300 先到：累计确认仍期待 1101。接收端可先缓存后面的字节，但不能把它们当成连续字节流越过缺口交给普通 TCP 应用。

> **Q：累计 ACK、乱序和应用交付之间是什么关系？**
>
> - 累计 ACK=n 表达 n 以前的连续序号空间已确认，下一期待位置为 n，不是“只确认编号 n 这个包”。
> - 接收端可以先收到并缓存后续数据，“队头阻塞”指不能按字节流语义向应用跳过缺口交付，不是后续包一定没到网卡。
> - 新累计 ACK 可以覆盖较早确认，所以不是每丢一个 ACK 就必须重传一份数据。
> - 序号是有限宽度，会回绕。协议判断要结合有效窗口，不能把裸整数大小比较当作永远正确的新旧判断。
> - 接收方缓存、发送方保留的未确认数据、双方对确认的理解都必须一致，单独增加一个序号字段并没有实现完整可靠协议。

**1.3.8 超时重传、快速重传与 SACK**

**超时重传**：在预计时间内没有得到足够确认，发送端触发重传。RTO 依据平滑 RTT、波动与时钟精度估算，不能固定写成一个 RTT。基础形式为 `SRTT + max(G, 4 × RTTVAR)`；标准还有初值、上下限和退避要求，操作系统实现细节可能不同。

超时后会增加等待间隔，避免网络越拥塞就重传得越猛烈。重传过的数据如果无法判断 ACK 对应哪次发送，不能直接拿来当精确 RTT 样本，这是 Karn 算法要处理的歧义。

**快速重传**：经典 TCP 可以根据连续重复 ACK 提前推断中间缺段，不必等整个 RTO。常见规则是三个重复 ACK；但乱序也能产生重复 ACK，所以它是推断，不是绝对证明。现代实现还可能结合其他丢包检测方法。

**SACK**：接收端补充说明已收到哪些不连续字节区间，帮助发送端更准确选择需要重传的内容。它需要能力协商，不能理解成另一套完全替代累计 ACK 的确认方式。

> **Q：快速重传和 SACK 是否足以解决所有丢失？**
>
> - 只有很少数据、尾部丢失时，未必能等到足够重复 ACK，仍需超时等机制。
> - SACK 描述的是已经收到的区间，不是简单列表“这些包肯定丢了”。
> - SACK 与“选择重传 ARQ”有关联，但前者是 TCP 的具体扩展机制，不等于任何 UDP 协议都必须照搬。
> - 按 RFC 2018，只有 SACK 确认的数据仍应保留必要的重传能力，不能当作累计确认后立刻彻底删除；接收端可能放弃已缓存但不连续的数据。
> - 可靠重传始终受连接状态和超时上限约束，不是无限等待直到宇宙尽头。

参考：RFC 6298：RTO 与 Karn 规则、RFC 5681 §3.2：经典快速重传、RFC 2018：SACK。

**1.3.9 滑动窗口、流量控制与拥塞控制**

停等发送一次只让少量数据在路上，链路可能大部分时间都在等 ACK。滑动窗口允许多份未确认数据同时在途，收到确认后窗口前移，继续发送。

| 机制 | 保护谁 | 关键信息 |
| --- | --- | --- |
| 流量控制 | 接收方，防止来不及处理的数据撑满缓冲 | 接收窗口 rwnd |
| 拥塞控制 | 网络路径，避免过量发送造成拥塞恶化 | 拥塞窗口 cwnd、ACK、丢失、ECN 等反馈 |

在通常的解释模型中，在途未确认量受 `min(rwnd, cwnd)` 限制；还能新发多少还要减去已有在途量，并考虑其他协议条件。窗口是量，不直接等于每秒速度。

> **Q：窗口为零是否断线，窗口大小是否等于速度？**
>
> - 接收窗口为零，意味着对方暂时没空间，不等于断线。零窗口探测可发现窗口重新打开，避免窗口更新消息丢失后双方一直停住。
> - 零窗口探测、TCP Keepalive、应用心跳和数据重传不是同一个计时器或同一个目的。
> - 同样窗口下，RTT 越大，理想吞吐越受限制。带宽时延积可帮助理解需要多少在途数据才能填满链路，但真实吞吐还受丢包、应用供给等影响。
> - rwnd 较大并不意味着 cwnd 也大；对方机器空闲，不代表中间网络不拥堵。

参考：RFC 1122 §4.2.2.17：零窗口探测、RFC 5681 §2：窗口术语。

**1.3.10 慢启动、拥塞避免与快速恢复**

理解经典 Reno 系列的直觉即可，不能说所有现代系统逐字执行同一算法：

- 慢启动：从较小窗口探测路径，随着 ACK 增长；理想条件下每 RTT 近似成倍增长，不是“增长速度很慢”。
- 拥塞避免：达到一定条件后更谨慎增加在途量，经典模型近似线性增长。
- 快速重传 / 恢复：根据确认反馈推断缺口，补发并调整窗口；不同算法对多处丢失的恢复不同。
- 超时：通常意味着更严重或更不明确的传输问题，需要更保守地缩减发送、退避重传。

> **Q：拥塞控制能否只按丢包次数机械处理？**
>
> 丢包可能来自拥塞，也可能来自无线差错；协议仍要根据反馈控制流量。不要因“游戏用 UDP”就跳过拥塞控制，更不能网络越差越无限加倍发包。

参考：RFC 5681：经典拥塞控制、RFC 6582：NewReno 恢复。

**1.3.11 延迟确认与 Nagle：为什么小请求会额外等一会**

延迟确认让接收端短暂等待，以合并 ACK 或让 ACK 搭上反向数据，减少包数。Nagle 则在已有未确认数据时，限制继续发许多小段，等待确认或积累出足够数据。

假设应用把一条逻辑请求分两次写入：第一小段已经发送，第二小段被 Nagle 暂缓；接收端又在等后续数据以合并确认，便可能出现额外等待。确认计时器最终会推动它继续，不应描述成永久死锁。

> **Q：禁用 Nagle 能解决所有 TCP 延迟吗？**
>
> - Nagle 不是“不足 MSS 就永远不能发”；没有未确认数据时也可能立即发小段。
> - Delayed ACK 不是所有系统固定等待 200 ms。具体时限、确认频率和自适应策略要看实现；不要把抓到的一次延迟背成协议常量。
> - `TCP_NODELAY` 用于禁用 Nagle，不是关闭拥塞控制，也不能消除 TCP 丢包后的有序交付等待。
> - 延迟敏感的小消息可评估禁用 Nagle；代价可能是包率上升。也可先优化应用写入方式，将一条已完整准备好的消息一次提交，而非逐字段写出。

参考：RFC 1122 §4.2.3.4：Nagle、RFC 5681 §4.2：确认策略。

**1.3.12 粘包、拆包：TCP 没把消息弄坏，是应用没定义边界**

应用连续发送三条消息，接收端可能一次读到半条、一条半或几条。TCP 保证字节顺序，不保留 `send()` 调用的边界；一次 `recv()` 也不对应一次发送。

常见分帧方式是固定长度、分隔符、长度字段加内容。游戏消息常用“固定长度的头 + 头里声明的内容长度”。

```text
收到字节 -> 加入有总量上限的接收缓冲
循环：
    不足固定头长：等待更多字节
    按约定字节序读取版本、类型、内容长度
    版本/类型非法，或长度超过消息上限：拒绝并结束连接/请求
    不足完整消息：等待更多字节
    取出一条完整消息 -> 校验内容 -> 派发处理
    继续解析缓冲中剩余字节
```

> **Q：加一个长度字段就完成了安全的消息分帧吗？**
>
> - 不能信任对端声明的长度直接分配内存；要限制单条长度、连接缓冲总量和未完成消息等待时间。
> - 检查“头长 + 内容长”时也要防整数溢出。
> - 分隔符方案需要转义或禁止内容出现分隔符；固定长度则可能浪费空间。
> - 只加 `TCP_NODELAY` 不能解决消息边界问题，粘包不是 Nagle 独有的错误。
> - Socket 写入也可能只接受部分数据，发送端要记录偏移并继续处理，而不是只写一个 `send()` 就假定完整消息交付。

### 1.4 UDP 与选择性可靠传输

**1.4.1 UDP 提供什么，不提供什么**

UDP 提供数据报语义：应用发送的一个数据报具有自己的边界。基本头部为 8 字节，由源端口、目的端口、长度和校验和组成。它不内建 TCP 式连接握手，也不自动保证送达、顺序、去重或拥塞控制。

“UDP 不保证可靠”描述的是协议本身，不能推出“基于 UDP 的应用一定不可靠”。UE 的玩法网络、QUIC 等都在其上组织额外机制，只是目标和保证范围不同。

> **Q：UDP 无连接，为什么代码还可以调用 connect？**
>
> UDP Socket 的 connect 可在本地设置默认对端，并影响发送接口、接收过滤和错误处理；它不自动产生 TCP 三次握手。应用仍可另外设计认证、心跳与逻辑会话。

> **Q：UDP 是不是没有校验？**
>
> 有校验和。IPv4 UDP 允许按规则禁用校验和；IPv6 默认要求使用，只有受严格约束的特定场景存在例外。校验和只检测差错，不提供身份认证、可靠交付或反作弊。

> **Q：UDP 没有粘包，就不会收到半条消息吗？**
>
> 它保留数据报边界，但接收缓冲太小可能导致截断或错误；一个业务消息如果由应用拆成多个数据报，仍需自己重组。IP 分片丢失也会使原数据报无法完整重组。不要将“数据报边界”与“任意大的业务消息完整交付”混为一谈。

参考：RFC 768：UDP、RFC 8085 §3.4：校验和、Linux recv 手册。

**1.4.2 游戏为什么常考虑 UDP，而不是“UDP 一定快”**

假设旧位置 A 丢了，新位置 B 已到。对某些独立编码的位置快照而言，B 更有价值，不必等 A 重传后才表现 B。UDP 让应用有机会按业务选择交付策略，而不是所有数据都服从同一条可靠有序字节流。

但登录、下载或低频服务请求也可能很适合 TCP/HTTPS。应先问“这条消息是否过时、是否可覆盖、是否需要严格顺序”，再选传输方式，而不是给整个游戏只允许一种协议。

| 消息要求 | 可考虑的语义 | 仍需处理的事 |
| --- | --- | --- |
| 最新位置覆盖旧位置 | 不可靠、带序号，过时数据丢弃 | 插值/有界外推、状态不连续、基线依赖 |
| 相互独立但不能丢的通知 | 可靠无序 | 消息去重、超时、连接失效 |
| 必须依次执行的流程 | 可靠有序 | 本通道队头阻塞、排队上限 |
| 短暂非关键表现 | 不可靠无序或带时效 | 丢失不影响权威结果 |
| 购买、发奖等业务事务 | 可靠传输加业务请求标识 | 重连重试后的重复提交、持久化与事务 |

> **Q：血量、死亡和开门都可以丢了等下一包吗？**
>
> 不能只按变量名字决定可靠性。如果状态会周期性完整重发、可从后续状态恢复，某个旧更新可以丢；若只发一次“死亡事件”就不再保存结果，丢失便无法恢复。应明确持久状态的恢复保证、更新机制和瞬时表现的区别。UE 属性复制的机制放在第三章，不直接等同于“裸 UDP 发一次”。

**1.4.3 在 UDP 上补可靠性，需要哪些状态**

RUDP 不是一个统一标准协议。一个教学上的可靠消息层通常需要：会话标识、包序号、确认信息、逻辑消息标识、重传队列、接收窗口、流量限制以及失效清理。

发送端流程：生成消息 → 分配消息 ID → 装入带包序号的数据报 → 记录待确认关系 → 收到 ACK 后更新状态 → 超时只重传仍需要交付的消息 → 超过时长/队列预算则失败或恢复连接。

接收端流程：检查长度、版本与会话 → 校验认证信息 → 判断新旧与重复 → 更新确认窗口 → 重组必要分片 → 按通道语义交付消息。

一种简化 ACK 位图约定：Ack=100，位 0 表示 99 是否收到，位 1 表示 98，依次覆盖一段历史。双方必须约定同一含义；TCP 的累计字节 ACK 与这种包位图不是一回事。

> **Q：PacketSeq 和 MessageId 为什么不一定是同一个编号？**
>
> 一个包可装多条消息，一条消息也可能分片或换一个新包重传。包确认用于管理传输，消息 ID 用于业务消息去重；只按包去重，可能把重装在新包里的旧消息再次执行。

> **Q：只保存最大的序号，遇到更小的就丢，可以吗？**
>
> 对“只关心最新值”的状态流可以这样设计；对仍有价值的可靠消息会错杀合法乱序数据。应使用有界接收窗口与已收位图。有限位宽序号还要按模空间处理回绕，并限制有效窗口，不能永远用普通大于号比较。

> **Q：传输层去重以后，为什么发奖还要请求 ID？**
>
> 玩家断线后可能在新连接里重发同一笔业务；新的包和消息编号可以完全不同。业务仍要按玩家身份与请求 ID 识别同一事务，并定义记录保留和并发处理规则。

**1.4.4 ARQ、FEC 和冗余发送各解决什么**

| 方法 | 核心思路 | 主要代价与限制 |
| --- | --- | --- |
| 停等 ARQ | 发出一份，确认后再继续 | 简单，长 RTT 下难以充分利用链路 |
| 滑动窗口 / 选择重传 | 允许多份在途，只补仍缺失的必要内容 | 要维护窗口、确认、排序和队列 |
| FEC | 预先发送校验冗余，丢失在能力范围内时恢复 | 额外带宽与计算，可能等待足够分组 |
| 重复附带少量历史输入 | 后续包再次带上近期重要输入 | 实现较直接，但增加流量；连续丢包仍可能全丢 |

等长块 A、B、C 加一个异或块 P=A XOR B XOR C，在这一组里丢任意一个块时可由另外三个恢复。丢两个独立未知数据块就不能只靠这一份异或校验恢复；更强编码的恢复能力取决于具体码与冗余量。

> **Q：FEC 是零等待，而且语音必须用 FEC 吗？**
>
> 都不能这样概括。FEC 可能避免等待一次重传往返，但需要凑够恢复所需数据；语音可以结合 FEC、丢包隐藏和播放缓冲，具体策略取决于编解码器和延迟预算。PLC 也不保证任何丢包都听不出来。

> **Q：每包发三次，丢包率 10% 就能降到 0.1% 吗？**
>
> 只有把三次丢失视为独立事件时，才有 0.1³ 的估算。实际丢包可能成串发生，拥塞时重复发送还可能使情况更差。需要实测相关性并约束额外流量。

参考：RFC 6363：FEC 框架、RFC 8085：UDP 可靠性与拥塞控制边界。这些是机制背景，不表示本项目实现了自研 RUDP 或 FEC。

**1.4.5 QUIC：了解它解决了哪些 TCP 使用痛点**

QUIC 建立在 UDP 上，提供安全连接、可靠流、多路复用与拥塞控制等。独立流的交付减少了一条流丢数据对其他流的直接阻塞；Connection ID 和路径验证等机制支持特定条件下的连接迁移。

> **Q：QUIC 既然走 UDP，就能把它当游戏的不可靠快照通道吗？**
>
> QUIC 的可靠流仍要求本流有序交付。需要过期即弃的消息，可以考虑相应 DATAGRAM 扩展或其他实时通道，并评估实现支持。它不是“UDP 上的东西都一样”，也不是 UE 原有 Gameplay 网络的一键替换件。

参考：RFC 9000：QUIC、RFC 9221：不可靠数据报扩展。

### 1.5 网络层与网络接口层：知道包怎样找到下一跳

**1.5.1 IP、路由和 ICMP**

IP 提供跨网络寻址和尽力交付。主机根据路由表选择下一跳，路由器继续转发；目标不在本地子网时，常交给默认网关。端口不属于 IP 寻址本身，而由 TCP/UDP 等上层使用。

IPv4 地址为 32 位，IPv6 为 128 位。TTL / Hop Limit 等限制报文在路由环中的传播。ICMP 用于错误报告和诊断，不是 TCP/UDP 的可靠消息通道。

> **Q：ping 通了，游戏一定能连接吗？**
>
> 不能。ICMP 可达不代表目标 UDP/TCP 端口开放，也不代表程序在监听、协议版本相同或认证成功。反过来，ICMP 被禁也不一定意味着游戏端口不可达。

参考：RFC 791：IPv4、RFC 8200：IPv6。

**1.5.2 MAC、ARP 与本地链路**

链路层负责当前链路的传输。以太网中，IPv4 主机可通过 ARP 查询同一链路上某个下一跳 IP 对应的 MAC；IPv6 使用邻居发现相关机制。跨网段时常解析的是网关 MAC，不是最终远端服务器 MAC。

> **Q：为什么有 IP 还需要 MAC？**
>
> IP 用于跨网络寻址，MAC 用于当前链路的帧交付，职责不同。普通路由转发时每一跳重新组织链路帧；不要把目标 MAC 理解成一路保持不变的公网目的身份。

参考：RFC 826：ARP、RFC 4861：IPv6 邻居发现。

**1.5.3 MTU、MSS 与分片**

MTU 限制链路承载的网络层报文大小；PMTU 是整条路径上的约束。MSS 限制 TCP 每段的数据大小，数值还要考虑 IP/TCP 头和可用路径。

例如常见 1500 字节 MTU，在没有 IP/TCP 选项等额外因素时，IPv4 TCP 可对应 1460 字节数据，IPv4 UDP 可对应 1472 字节内容。这只是条件化计算，不是任何网络下都安全的固定发包上限。

> **Q：为什么大 UDP 包更值得警惕？**
>
> 超过路径能力可能分片或直接失败。依赖 IP 分片时，缺少任一必要片段就不能重组原数据报，丢失放大、重组资源和中间设备兼容都会成为问题。IPv6 路由器不替源端分片，应结合路径发现和源端策略处理。
>
> 因此不把“1400 字节一定安全”当通用定理。隧道、VPN、IPv6 头及其他封装会改变预算；应用层拆分也要限制总大小、分片数量和等待时间。

参考：RFC 8085 §3.2：UDP 消息大小、RFC 8200 §4.5：IPv6 分片。

**1.5.4 NAT、端口映射、打洞与中继**

NAT 将内部地址/端口映射为外部端点。客户端主动发起到公网服务器的通信，往往能建立相应映射；让另一名公网玩家主动连到家中 Listen 主机，则可能需要端口映射、穿透或中继。

STUN 可帮助发现公网映射；ICE 组织候选地址与连通性检查；TURN 提供中继能力。不存在对所有 NAT 都保证成功的简单打洞公式。

> **Q：局域网搜到房间，为什么公网就可能搜不到？**
>
> 局域网发现、可路由地址、NAT/防火墙和应用会话是不同问题。局域网广播不会自然跨越公网；即使知道公网 IP，也要有可达端口和正确的连接入口。本项目当前 LAN Session 测试不能证明已经解决公网穿透。

参考：RFC 8489：STUN、RFC 8445：ICE、RFC 8656：TURN。

### 1.6 Socket、I/O 与连接生命周期

**1.6.1 一条典型 TCP 服务端调用路径**

服务端：`socket → bind → listen → accept → recv/send → shutdown/close`。客户端：`socket → connect → send/recv → shutdown/close`。实际异步框架会包装这些过程。

> **Q：listen 的 Socket 能直接代表每个玩家吗？**
>
> 监听 Socket 用于接收新连接，accept 返回的是某条已建立连接的 Socket。一个监听端口对应多条连接；关闭一条连接不应该不加区分地关闭整个监听服务。

> **Q：recv 返回 0、返回暂不可读和返回错误，有什么区别？**
>
> 在请求读取非零长度的普通 TCP 场景中，缓冲中的数据读完后返回 0，通常表示对端有序关闭发送方向；非阻塞的 EAGAIN/EWOULDBLOCK 表示暂时无数据，不是断线。错误要看具体错误码。UDP 可以收到合法的零长度数据报，不能直接套用 TCP 的 EOF 判断。

> **Q：shutdown 与 close 是同一个动作吗？**
>
> shutdown 可关闭某个通信方向；close/关闭句柄用于释放应用持有的描述符等资源，实际连接生命周期还与引用、系统语义和关闭方式有关。半关闭时本端可以结束发送但继续接收，不能把它当成两端同时立即断开。

参考：Linux socket、recv、shutdown。

**1.6.2 阻塞、非阻塞、就绪与完成通知**

- 阻塞调用可能停住当前线程，直到数据、错误或其他条件出现；不能把长期阻塞的收包放进游戏主线程。
- 非阻塞调用立即返回当前结果，没有数据时交给事件机制或后续调度，不要用忙循环空转占满 CPU。
- select/poll/epoll 等就绪机制告诉程序“可以尝试 I/O”；IOCP 等完成机制围绕异步操作的完成结果组织处理。

> **Q：用了 epoll，就不需要循环读剩余数据了吗？**
>
> 仍需要处理部分读取。尤其边沿触发通常要配合非阻塞，读取到暂不可读再等下一次事件；只读一点就返回可能留下数据却等不到预期的新边沿。也不能简化为“epoll 的所有处理都是 O(1)”。

> **Q：网络线程解析完，就可以直接改 UE Actor 吗？**
>
> 应按引擎的数据所有权和线程规则处理。常见自定义方案由网络线程收包、校验和生成消息，再交给游戏线程修改玩法对象；还要防止排队期间对象已销毁或世界已切换。换线程不自动让任意 UObject 操作安全。

参考：Linux epoll 手册、Microsoft IOCP。

**1.6.3 心跳、超时与重连**

连接故障不能只靠“是否还持有一个 Socket 指针”判断。静默断网可能既没有 FIN，也没有立即到来的错误，需要结合收发失败、协议探测与超时。

通用业务恢复链可以是：检测异常 → 暂停会重复提交的关键操作 → 有限重试 → 重新验证身份 → 服务器决定接回旧角色还是创建新角色 → 下发当前状态 → 清理旧回调与旧请求。

> **Q：超时就是确定对方已经死亡吗？**
>
> 超时是基于预算的判断，可能由拥塞、后台挂起或对端卡顿引起，不是全知结论。阈值越短，发现故障越快，也越容易误判；应定义可恢复状态和最大重试次数。

> **Q：重连一定要指数退避吗？**
>
> 大规模服务常用退避并加入随机扰动，减少大量客户端同时重试；具体间隔要匹配服务与体验预算。本项目使用配置化有限重试，不因此声称已经具备大规模重连风暴治理或身份续接。

> **Q：Wi-Fi 切到移动网络一定断线吗？**
>
> 传统基于固定地址/端口的连接常需要恢复，但 QUIC 等具备路径迁移机制时可能保留逻辑连接。应按协议与实现判断，不能把“IP 变化必然断线”当所有协议共同规则。

### 1.7 通用网络优化与安全边界

**1.7.1 先减少不必要的数据，再考虑压缩**

优先问四件事：谁需要知道、多久需要知道、没变要不要处理、数据过时后还有没有价值。它们分别引向相关性、更新频率、稳定状态处理和队列淘汰。

接着才是编码优化：按所需精度量化数值、用 ID 代替重复字符串、只编码相对已知基线的变化，以及为合适负载评估通用压缩。传输消息与游戏状态的优先级策略还要留到第二、第三章结合具体机制讨论。

> **Q：16 位整数存厘米位置，是不是任何地图都够？**
>
> 还要看范围。无符号 16 位以厘米计只能覆盖 655.35 米的一维跨度，有符号范围不同；大型地图需要分区、相对原点或其他编码。8 位表示完整 360° 方向，步长约 1.40625°，也要看玩法精度是否能接受。

> **Q：增量压缩就是与上一个发出的包相减吗？**
>
> 不一定。接收端必须拥有所引用的基线；上一个发出不等于对端已收到。协议要管理基线标识、确认与恢复，不然更省字节却无法解码。

> **Q：LZ4、Zstd 能保证省一半带宽吗？**
>
> 不能。压缩率取决于真实数据；小包、已经量化或高熵内容可能收益很小，甚至变大，还要支付压缩/解压 CPU、临时内存和延迟。不预设固定百分比。

**1.7.2 小包合并、缓冲与背压**

合并多个已经准备好的小消息可以减少包头和处理次数，但为了合并而等太久会增加延迟，大包丢失也可能同时影响更多内容。

一个简化算例：只计算无选项 IPv4 的 20 字节头与 UDP 的 8 字节头，10 份各 50 字节内容分别发送是 780 字节，合并为一次是 528 字节，减少约 32.3%。它没有计入链路、安全、业务分帧和重传开销，不是项目实测收益。

> **Q：网络发不出去，先全部放队列不就行了？**
>
> 无上限队列会把丢包问题变成内存增长和持续变大的排队延迟。要限制总量、消息寿命与优先级：旧位置可被新位置覆盖；可靠业务要明确拒绝、超时或重试策略，不能默默丢弃仍承诺可靠的事务。

> **Q：丢包越多就增加 FEC、复制次数和缓冲，是不是总有效？**
>
> 若原因是拥塞，追加流量可能继续恶化。需要区分原因，限制总发送预算，必要时减少低优先级内容。缓冲主要用延迟换抗抖动，也有上限，不能让操作越来越落后。

**1.7.3 序列化与安全不要混成一件事**

JSON 适合可读配置和接口；Protobuf、FlatBuffers 或自定义二进制各有编码、访问方式和兼容取舍。不能说“游戏统一首选某种序列化”，也不能直接把带填充的 C++ 结构体内存当跨平台协议。

消息入口至少检查长度、类型、版本、枚举范围、数组规模、会话与权限，限制资源消耗。加密与认证保护传输边界，服务器业务规则保护结果，两者不能互相替代。

> **Q：普通 hash、HMAC、数字签名是一回事吗？**
>
> 不是。普通 hash 没有密钥，攻击者修改内容后也能重新算；HMAC 是共享密钥的消息认证码，不是公钥数字签名。非对称签名使用私钥签名、公钥验证；AEAD 可组合提供加密与认证。不要写成“HMAC 数字签名，作用只是防哈希碰撞”。RFC 2104：HMAC

> **Q：有序号就能防任何重放和作弊吗？**
>
> 序号需绑定经过认证的会话，并配合接收窗口等规则，否则攻击者可伪造新编号。即使传输安全，玩家仍控制客户端输入与内存环境；服务器还需检查玩法权限、状态、距离、速率和事务重复执行。

### 1.8 本章收束与后续章节

到这里应能沿一条消息说清：应用规定语义和边界 → 传输层提供选定的交付保证 → IP 与链路把包送向目标 → 程序按线程和生命周期安全处理 → 超时与重试不破坏业务正确性。

几个不能互相替代的结论：

- 传输 ACK 不等于业务成功；连接重建不等于玩家状态恢复。
- 有序交付不等于低延迟；没有可靠交付不等于可以无限发包。
- 数据报边界不等于完整业务消息；MTU 不等于可随意使用的业务内容长度。
- 设置频率不等于实际包率；少发字节不等于 CPU、帧率和视觉效果同比改善。
- 加密不等于反作弊；协议无状态不等于应用不保存状态。

下一章讨论帧同步与状态同步：同样的网络条件下，输入、状态、时间轴与纠错该怎样组织。之后在UE 网络机制中对应到实际的连接、通道、复制属性和角色移动。

## 第二章：帧同步与状态同步

返回总目录 · 上一章：网络基础

网络把消息送到另一台机器，同步模型决定这些消息怎样变成一个共同的游戏世界。传输可靠，不代表各端状态自然一致；画面流畅，也不代表客户端拥有裁决权。

本章先沿着输入驱动的帧同步讨论确定性、等待和回滚，再沿着权威状态更新讨论预测、插值和回溯。以下是通用架构原理；本项目未实现确定性输入回滚、通用世界回滚或服务器历史命中判定。角色移动预测与校正后的重演由第三章所述 CMC 提供，不能与上述能力混为一谈。

### 2.1 从通用传输优化进入同步模型

TCP/UDP、可靠通道、ARQ/FEC、分包与 MTU 已在第一章说明。这里只保留一条连接两章的原则：先确定业务需要哪种时间语义，再选择消息的可靠性与过期策略。

同样是“第 100 帧的数据”，含义可能完全不同：帧同步的输入会影响后续每一步计算，不能未经协议约定直接丢掉；独立的状态快照可能被更新快照覆盖；增量快照则还要检查解码基线。可靠性策略由这些依赖关系决定。

| 需要分清的维度 | 回答的问题 | 常见选择 |
| --- | --- | --- |
| 同步内容 | 各端靠什么保持一致？ | 输入指令、完整或增量状态、二者组合 |
| 权威归属 | 分歧出现后谁有最终裁决权？ | 专用服务器、房主、约定的分布式裁决 |
| 推进方式 | 数据未到时怎样继续？ | 等待、预留输入延迟、预测并纠错 |
| 网络拓扑 | 消息怎样到达其他参与者？ | 客户端—服务器、点对点、转发中继 |

“帧同步必然点对点”“状态同步禁止客户端计算”都把这些维度绑得过紧。帧同步可以有权威服务器，状态同步客户端也可以运行预测逻辑。

本章用“状态同步”泛指通过状态更新校准客户端的方案。不同资料的术语范围并不完全一致：Gaffer 将纯快照插值与双方都运行模拟的 State Synchronization 分开讨论，阅读时应先看实际数据流。Gaffer：State Synchronization

### 2.2 帧同步：共享输入，重复计算相同的状态

**2.2.1 从一帧输入到共同状态**

帧同步的基本关系是：

```text
S[n + 1] = F(S[n], I[n], 固定步长, 同一版本的规则与配置)
```

`S[n]` 是执行第 n 帧前的逻辑状态，`I[n]` 是这一帧约定采用的输入集合。参与模拟的各端必须使用相同初始状态、相同输入顺序和确定的状态转移规则，才能得到一致结果。

以有定帧服务器的架构为例，一轮流程可以是：

1. 客户端采集操作，附上玩家标识、输入序号和目标逻辑帧。
2. 服务器检查身份、输入范围及可接受的帧窗口，按规则归入对应帧。
3. 服务器确定第 n 帧输入集合及同帧操作顺序，发送给参与者。
4. 客户端根据帧号入队，去重并检查连续性；到达顺序不直接决定执行顺序。
5. 参与者执行第 n 帧，产生 `S[n + 1]`，必要时生成状态摘要用于排查分歧。

这种方案通常让带宽更接近“玩家输入量”，而不是“全部单位状态量”；单位越多、输入越紧凑，收益越明显。但初始化、重连快照、输入冗余和观战仍会消耗带宽。

服务器既可以只定帧转发，也可以执行相同模拟并做权威校验，或者另设校验进程。是否运行完整逻辑是架构选择，不是帧同步的定义。Gaffer：Deterministic Lockstep

**2.2.2 确定性是完整的工程约束**

固定步长只是起点。两个客户端都以 30 Hz 执行逻辑，如果实体遍历顺序、随机调用次数或碰撞求解结果不同，仍可能从一次小偏差逐渐分叉。

| 影响来源 | 需要建立的约束 |
| --- | --- |
| 时间 | 冷却、计时器和逻辑移动使用逻辑帧或固定步长；墙钟只负责调度与观测 |
| 数值运算 | 明确精度、舍入、溢出和数学函数行为，并验证目标平台与构建配置 |
| 随机数 | 固定算法及版本、初始状态、调用次序；按系统分流时明确每个随机流的状态 |
| 容器与实体 | 影响结果的遍历使用稳定顺序，避免指针地址或未约定的哈希遍历决定胜负 |
| 并行与物理 | 固定任务合并顺序、碰撞排序和求解规则，排除线程调度带来的结果变化 |
| 内容版本 | 使用一致的逻辑代码、规则参数、地图与资源数据 |

定点数是常见选择，但不是唯一选择，也不会自动保证确定性：乘除中间值、溢出和查表规则仍需定义。浮点数在受控平台、编译选项和运算路径下可以做到确定；随意跨平台运行同一份浮点代码则不能据此保证一致。

同样，随机数不必使用 LCG。关键是可复现的算法与状态管理；“相同 seed”不能修复不同的调用顺序，表现层随机数也不应随意消耗战斗逻辑的随机流。Gaffer：Floating Point Determinism

排查不同步时，应在同一已确认逻辑帧比较规范化的状态摘要，再缩小到实体和字段。不能直接对含有地址、填充字节的内存块求哈希，也不能拿两端不同进度的状态比较。

**2.2.3 严格锁步、输入延迟与预测回滚**

| 推进策略 | 输入尚未到齐时 | 代价与收益 |
| --- | --- | --- |
| 严格锁步 | 停在该逻辑帧，等待必需输入 | 不产生输入预测误差，但慢链路会造成等待 |
| 延迟输入 | 把采样输入安排到稍后的逻辑帧，预留传输时间 | 用额外操作延迟换取较少停顿；超出预算仍需处理缺输入 |
| 预测回滚 | 暂用预测输入推进，真值不同再重演 | 降低等待感，增加保存状态、重演与表现纠错成本 |

这些并非完全互斥。例如回滚方案也可以保留少量输入延迟，以减少预测错误及回滚深度。不能把所有现代帧同步统称为“无等待、零延迟的乐观锁步”。

严格锁步要求各端执行同一逻辑帧时采用相同输入，不要求所有机器在同一个墙钟瞬间执行。渲染帧、逻辑帧和网络发送批次也不必一一对应。

尤其要区分“玩家确认没有操作”与“输入还没收到”。若协议允许截止时间后补默认输入，必须由一致的裁决规则确定这帧究竟采用什么，并规定迟到输入如何处理；不能由各端自行把缺包永久当作 Empty，否则会把丢包变成不同的游戏事实。

**2.2.4 输入缓冲与追帧**

输入帧缓冲让客户端稍晚消费完整输入，吸收一部分到达间隔波动。缓冲越深通常越少断粮，也越容易增加操作等待；自适应调整还应考虑时钟漂移，避免目标深度来回跳变。

收到一批迟到输入后，逻辑可能已经落后。追帧的目标是更快执行**尚未模拟的连续逻辑帧**，而不是把帧号直接改到最新值。

- 少量落后：每次渲染前多执行有限个逻辑步，逐步缩短差距。
- 大量落后：暂时减少中间渲染与非必要表现，把预算留给模拟。
- 缺少必需输入：按锁步等待、既定缺输入规则或预测机制处理；追帧本身不能补出真值。
- 持续算不动：限制单次追赶预算，避免模拟挤占全部 CPU 后越追越落后；必要时重同步或退出。

“跳过渲染”不等于“跳过逻辑”。例如第 101 帧触发碰撞、第 102 帧结算死亡，直接跳到 103 帧就会漏掉状态转移。只有加载一份合法的后续快照，才是另一种明确的恢复路径。

**2.2.5 预测回滚：修正已经模拟过的历史**

预测回滚需要区分已确认输入和暂定输入，并保存可恢复的模拟状态。一个简化例子是：

```text
已知：第 100 帧前的完整状态 S[100]
暂缺：对手第 100 帧输入，先预测为继续前进
本地：已按预测执行 100、101、102 帧
收到：对手第 100 帧真实输入是防御
恢复：加载 S[100]，用修正输入重演 100 → 101 → 102
显示：采用重演结果，处理预测期间产生的视觉差异
```

预测策略可以从“沿用最近输入”开始，但要配合最大预测窗口。网络迟迟不给真值时，不能无限向前猜；超过可保存、可重演的窗口后应等待或重同步。

回滚还会重新执行触发事件的代码，因此音效、粒子、伤害数字需要稳定事件标识以及去重、撤销或延后确认策略。发奖、写数据库等不可逆副作用不应随着每次本地重演重复执行。

这解释了回滚的成本：每个逻辑步不仅要算得出，还要能保存、恢复，并在不重复渲染的情况下快速重演。它隐藏的是网络等待，不会消除网络传播、设备输入和画面刷新延迟。GGPO 官方：工作原理

**2.2.6 快照、断线重连与回放**

假设一局 20 分钟、30 个逻辑帧/秒，共有 36,000 帧。重连时从头回放全部输入可能很慢，可以用“最近可信快照 + 后续已确认输入”缩短恢复距离。

这里的快照要足以继续模拟，不能只有渲染需要的位置与血量。设计时至少核查：

- 快照对应的逻辑帧，以及保存的是该帧执行前还是执行后的状态。
- 实体标识、生命周期、技能阶段、冷却、计时器和待执行逻辑事件。
- 会影响后续结果的物理与碰撞状态，而不只是可见变换。
- 每个伪随机流的**当前内部状态**，不能只存开局 seed。
- 逻辑、配置、地图和快照格式版本，以及必要的完整性校验。
- 与该快照严格衔接的输入日志范围、排序规则及断线期间玩家的处理规则。

恢复时先验证版本与快照，再连续重演缺失区间，最后接上实时输入。快照传输期间服务器仍在前进，因此必须保存衔接区间，不能留下“下载时漏掉的几帧”。

回放沿用相同原则：记录初始条件、版本和输入，定期快照可支持跳转。游戏逻辑更新后，旧输入未必能重现旧结果；需要保留兼容执行环境、迁移支持，或明确回放有效版本范围。

**2.2.7 权威与作弊边界**

如果客户端必须拥有所有参与模拟的隐藏信息，战争迷雾只在画面上遮挡便无法阻止内存读取。加密保护传输链路，也不能让已经交给玩家机器的数据重新变成秘密。

但“改本地攻击力”并不自动修改其他端或权威服务器的结果；规范的固定帧推进也不应因为客户端墙钟加速就允许更多有效输入。风险取决于谁提交结果、谁验证输入、谁裁决分歧。

可采取的工程措施包括权威重演、输入频率与帧窗口检查、隐藏信息隔离以及回放审计。各客户端互报摘要适合发现分歧，不能单独证明某端诚实；行为异常也只是需要进一步验证的证据。

### 2.3 状态同步：用权威结果校准各端

**2.3.1 服务器权威与客户端职责**

典型的服务端权威流程是：客户端提交操作意图，服务器检查资格并推进模拟，再向相关客户端发送状态或事件。服务器决定是否拾取成功、实际伤害和胜负；客户端负责输入响应以及可见表现。

“服务器拥有最终裁决权”并不要求客户端等回复才移动。客户端可以预测自己的移动、插值远端对象，甚至运行局部物理；这些结果仍需接受权威状态校准。

自身对象与远端对象的数据来源常常不同，但不是必然要复制两份完整玩法代码。可以复用运动规则，再为本地预测、远端表现建立不同驱动路径。“1P/3P 对象伪造”也不是状态同步协议的必备术语。

服务器权威能拒绝伪造结算，不会自动消除透视、自动瞄准、非法请求或服务器校验漏洞。背包和资产同样不能仅因“属于某个玩家”就默认交给不可信客户端裁决。

**2.3.2 本地预测与服务器校正**

客户端预测让自身输入先得到反馈，服务器校正则解决“反馈可能不对”的问题。比较时必须对齐输入序号或模拟时间，不能把服务器过去的位置直接拿来否定客户端现在的位置。

```text
客户端已发送并预测：输入 21、22、23
服务器返回：权威状态 S，最后处理的输入序号 = 21
客户端处理：丢弃已确认的 21，保留 22、23
重新计算：从 S 出发，按顺序重放 22、23
得到结果：以最新权威依据重建的本地预测状态
```

服务器回执应明确哪些输入已经处理，丢包、重复输入和时间步长也须有协议约定。客户端随后可在表现层平滑小误差；碰撞等逻辑状态要先回到有效状态，不能只把所有物理值做 Lerp 就当作修复。

预测不必覆盖全部业务。开枪动画可以先播，扣除他人生命值、死亡结算和发奖则应按权威确认规则处理。预测范围越广，需要保存和重演的依赖通常越多。Gambetta：Client-Side Prediction and Server Reconciliation

**2.3.3 远端实体插值与航位推测**

远端玩家的后续输入尚不可知，客户端常保存带服务器时间的状态样本，选择一个稍早的呈现时刻：

```text
t_render = 估计的当前服务器时间 - 呈现延迟 D
找到 t0 ≤ t_render ≤ t1 的两个有效样本
α = (t_render - t0) / (t1 - t0)
位置 = (1 - α) × p0 + α × p1
```

这里的 D 要覆盖所需的样本滞后与缓冲余量，不能机械地等同于一个发送周期。也可以围绕“最新样本时间减缓冲量”设计播放时钟，但要把网络年龄与额外缓冲分清。

两份样本必须包围呈现时刻；“永远拿最近两份”并不正确。抖动、连续丢包或实体刚进入同步范围时，可能根本没有足够样本，需要短暂保持、有限外推或重新调整播放进度。

航位推测是在没有后续样本时，用已有位置、速度等估计未来，例如 `p(t + Δt) ≈ p(t) + vΔt`。它是外推，不能称作两个已知端点之间的插值；遇到急转、碰撞和瞬移容易失准，应限制外推时长并处理重新收敛。

旋转通常采用四元数插值；传送等不连续变化则应重置相关插值历史，避免画面穿越本来没有经过的区域。Gaffer：Snapshot Interpolation、Gambetta：Entity Interpolation

**2.3.4 服务器回溯与延迟补偿**

玩家看到的是经过传输与插值处理的远端目标。射击指令到达服务器时，目标可能已经移动；若只查询接收时刻的位置，瞄准画面中的目标也可能判空。

一种处理方式是保存有限长度的碰撞历史，根据经校验的射击时间与客户端呈现延迟估计当时所见的时间点，在历史碰撞体上查询命中，再把结果应用到当前权威状态。

```text
t_seen ≈ t_receive - 估计的上行传播时间 - 受约束的客户端呈现延迟
```

这只是说明时间组成的近似式，不是可直接信任的协议。实际实现需做客户端与服务器时钟映射、检查输入序号和时间戳，并限制允许回溯的区间；`RTT / 2` 只是对称链路假设，客户端自报时间也不是可信事实。

最大窗口是玩法与公平性的选择，例如可以讨论 200 ms 的设计预算，但它不是行业固定值。过旧、过新或历史缺失的请求应有明确拒绝或降级规则，不能无限回溯。

回溯不一定真的把实时世界搬回过去，也可以对历史数据构造临时查询场景。它通常是在过去做一次命中查询，随后继续当前世界；要明确哪些目标、姿态、移动掩体参与历史记录。

代价是被击中者可能已在自己画面里进入掩体。延迟补偿是在不同玩家的时间视角之间取舍，不能保证消除所有争议。Gambetta：Lag Compensation、Valve：Latency Compensating Methods

**2.3.5 同步范围、频率与带宽预算**

先修正一个容易算错的例子。假设 1000 个玩家，每个对象一次状态 100 B，20 次/秒，每人都接收另外 999 人的数据，不考虑压缩及协议开销：

```text
单客户端下行：999 × 100 B × 20/s = 1,998,000 B/s ≈ 2 MB/s
全服合计出口：1000 × 999 × 100 B × 20/s ≈ 2 GB/s ≈ 16 Gbit/s
```

这里采用十进制单位；约 2 GB/s 是发往全部客户端的合计有效载荷，不是每名玩家的流量。全量互发随人数接近平方增长，应该先减少同步关系，而不只是继续压缩字段。

AOI（兴趣区域）决定某连接需要哪些信息。距离、队伍、所属关系、声音、任务和跨区域交互都可能构成兴趣；它不等于摄像机当前可见范围。背后的攻击者也许需要同步，藏在墙后的敌人也不应因进入网格就必然暴露全部数据。

空间网格、四叉树或八叉树可用于查找候选对象，之后仍需应用业务相关性和隐私规则。对象进入范围时要有可解码的初始状态，离开时要处理移除或失效；边界滞回可以减少来回进出造成的抖动。

在相关对象内部，再按交互重要程度、误差增长和长时间未更新程度分配预算。近处高速对象往往更需要更新，但“低优先级”不能意味着永远饿死。逻辑 Tick、输入发送频率和快照发送频率是不同参数，20/30/60 Hz 都只是可能的配置。Gaffer：State Synchronization 的优先级累积

**2.3.6 增量快照与重连**

增量快照应标明基线 ID，并相对接收方已确认持有的有效基线编码。不能只说“相对上一个发送包做差”：上一个包可能已经丢失，接收方根本无法重建。

缺少基线时，可以使用双方仍保留的其他基线，或发送完整恢复状态。量化、字段省略、更新频率和休眠也要保证重要的最终变化能被接收方确认，尤其不能让“停止移动”的最后一包丢失后对象永远外推。

重连时通常可以从当前权威基线恢复相关对象，而无需重演断线期间的全部世界模拟。但仍需恢复实体生命周期、所有权、必要的业务状态与待确认请求，重新建立插值历史，并决定哪些本地预测输入仍然有效。

“当前状态”也无法自动替代所有事件。例如血量减少只能说明结果，若要准确显示伤害来源和暴击，还需同步所需事件信息；断线期间不能遗漏的奖励记录则应由持久业务状态恢复。Valve：Source Multiplayer Networking

### 2.4 两种模型的取舍与组合

**图 2｜两类同步方案各自把什么送到远端**

```text
帧同步：本地输入 + 远端输入 → 同一逻辑帧 → 各端按确定性规则推进
                           └─ 迟到输入可能触发等待、追帧或回滚重演

状态同步：本地输入 → 服务器权威计算 → 按连接发送相关状态
               └→ 本地可预测自身动作          └→ 客户端校正自身、插值显示他人
```

这里的“帧”是约定的逻辑模拟步，不等于渲染帧；“状态更新”也不表示客户端只能等待结果、完全不能预测。

| 比较维度 | 输入驱动的帧同步 | 权威状态更新 |
| --- | --- | --- |
| 一致性来源 | 相同条件与输入产生相同结果 | 以权威状态纠正各端偏差 |
| 自身响应 | 取决于输入延迟、等待及是否预测 | 可通过本地预测立即反馈，再校正 |
| 确定性要求 | 共享模拟范围内要求严格 | 不要求所有客户端长期逐位一致；预测路径仍需尽量一致 |
| 抖动处理 | 输入缓冲、受限预测及追赶 | 状态缓冲、插值及有限外推 |
| 主要带宽因素 | 输入量、冗余、快照和重同步 | 相关对象数、字段大小、变化率和发送频率 |
| 计算成本 | 参与端运行共享模拟，回滚要留重演预算 | 服务器承担权威计算，客户端成本取决于预测范围 |
| 信息保护 | 全量共享模拟常面临隐藏信息泄露 | 可按连接过滤，但过滤策略仍需正确 |
| 回放与重连 | 版本化快照与输入日志 | 状态记录、必要事件，也可利用服务端输入重演 |

RTS 的大量单位与较紧凑指令、格斗的精确时序、FPS 的自身响应与命中裁决，会推动不同取舍，但游戏类型不能直接替代技术论证。应结合单位规模、交互方式、跨平台范围、延迟容忍度和开发成本选择。

混合架构可以让一个确定性战斗子系统共享输入，其他实体使用权威状态更新。前提是清楚规定状态所有者、跨系统消息对应的逻辑时刻，以及回滚时哪些依赖也必须恢复。

“服务器发一个技能事件，客户端播放相同特效”本身不构成帧同步；它可能只是事件驱动表现。用了随机种子、固定 Tick 或技能时间轴，也不足以证明各端在运行一个共享的确定性模拟。

### 2.5 补充问题

> **Q：预测、回滚和服务器回溯有什么区别？**
>
> 预测是在真值到达前先算；回滚是恢复旧状态并重新模拟已经执行过的区间；服务器回溯通常是读取历史状态完成一次查询。预测可配合回滚，回溯命中查询却不必重演整段世界历史。

> **Q：追帧与回滚都会连续执行多个逻辑帧，为什么还要区分？**
>
> 追帧补算此前没执行的帧；回滚重算已经执行但依据有误的帧。二者可以复用快速模拟能力，但输入管理、快照和副作用处理不同。

> **Q：帧同步能否丢掉一个旧输入，等下一帧覆盖？**
>
> 通常不能。那次输入可能已经决定碰撞、随机调用和技能触发。只有协议明确规定了输入保持、替代及迟到处理规则，才能一致地推进；位置快照的覆盖语义不能直接套给逻辑输入。

> **Q：状态同步是否完全不需要确定性？**
>
> 它不依赖所有端无限期产生逐位相同的完整世界，但预测重演仍依赖足够一致的规则。客户端运动、服务器运动或量化方式长期不匹配，会造成持续纠正，表现为拉扯和抖动。

> **Q：怎样验证这些设计没有只在局域网里成立？**
>
> 分别注入延迟、抖动、乱序、重复和连续丢包，记录输入等待、缓冲欠载、回滚深度、重演耗时、校正幅度、基线丢失和恢复时间。确定性还需跨目标平台、构建配置运行同一输入日志并比较同帧摘要；这些是验证方法，不是本项目已经取得的测试结果。

## 第三章：UE 中的网络同步——从 UDP 数据包到权威游戏状态

返回目录 · 上一章：同步模型 · 下一章：项目网络设计

UE 的联网能力横跨传输、对象复制和玩法框架。理解它时，需要分别回答三个问题：数据怎样送到另一台机器，哪些对象和状态应当发送，以及谁有权决定游戏结果。

本章以本项目使用的 **UE 5.5、IpNetDriver 和传统 Actor 复制路径**为依据。机制说明来自本地 UE 5.5 源码核对，Epic 文档用于补充概念；项目选择和实验数据留在第四、第五章。

### 3.1 先确定当前讨论的是哪一条网络路径

**3.1.1 本工程的版本与复制系统**

项目的 `multiplayer.uproject` 标记引擎版本为 5.5，`DefaultEngine.ini` 使用 `OnlineSubsystemNull`。它负责局域网会话发现等服务；游戏对象的复制仍由 NetDriver 体系处理。会话加入成功也不等于游戏连接、地图加载和所有 Actor 初始化已经完成。

当前项目配置没有替换 GameNetDriver。引擎 `BaseEngine.ini` 的默认定义将它映射到 `/Script/OnlineSubsystemUtils.IpNetDriver`。`UIpNetDriver::CreateSocketForProtocol` 创建数据报 Socket，因此这里讨论的常规游戏传输走 UDP。

UE 5.5 中存在 Iris 代码，不代表本项目已经启用 Iris。该版本 `IrisConfig.cpp` 中 `net.Iris.UseIrisReplication` 的初始值为 0；引擎还会综合驱动能力、GameInstance 请求和命令行决定实际复制系统。`bCanUseIris=true` 只是具备使用资格。

从当前 `Source`、`Config` 和项目描述文件中没有发现显式启用 Iris、替换复制系统或配置 Replication Graph 的设置。因此本章以传统路径解释现有工程；某次运行若额外传入覆盖参数，应以该次运行的驱动和日志为准。

源码入口：IpNetDriver.cpp：CreateSocketForProtocol（引擎源码定位：`Engine/Plugins/Online/OnlineSubsystemUtils/Source/OnlineSubsystemUtils/Private/IpNetDriver.cpp:771`）、IrisConfig.cpp（引擎源码定位：`Engine/Source/Runtime/Experimental/Iris/Core/Private/Iris/IrisConfig.cpp:12`）、UnrealEngine.cpp：WillNetDriverUseIris（引擎源码定位：`Engine/Source/Runtime/Engine/Private/UnrealEngine.cpp:14183`）。

**需注意的细节**

> **Q：用了 OnlineSubsystemNull，就意味着 UE 自己没有可靠传输吗？**
>
> 两者职责不同。OnlineSubsystem 提供会话等服务，游戏连接上的确认、可靠消息和属性补发由 UE 网络与复制层处理。不能从会话后端的名称推断传输保证。

**3.1.2 反射系统：引擎怎样认识 C++ 的类、字段和函数**

网络复制需要知道“这个字段是什么类型，怎样序列化”“收到函数标识后调用哪个入口”。UE 的反射系统为这些操作提供类型描述和调用入口，而不是运行时重新打开头文件分析 C++。

构建时，UBT 组织构建任务并调用 UHT；UHT 解析带有 UE 标记的声明，生成与 UObject 系统有关的代码，再由 C++ 编译器编译手写代码与生成代码。运行时使用的是已经构建好的类型信息。宏本身不是一个能独立完成反射的魔法开关。Epic：Unreal Header Tool（5.5）

```text
UCLASS / USTRUCT / UPROPERTY / UFUNCTION 等声明
    → UHT 解析并生成 .generated.h、.gen.cpp 等代码
    → C++ 编译与链接
    → 类型注册与运行时描述
    → 编辑器、蓝图、序列化、GC 和网络系统按各自规则使用
```

`.generated.h` 配合 `GENERATED_BODY()` 接入生成的声明与样板代码，应按 UE 约定放在该头文件的最后一个 include；`.gen.cpp` 包含类型构造、字段/函数描述和注册等实现。生成文件属于构建产物，不应手工修改来补功能。

| 运行时描述 | 主要表达什么 | 与网络的联系 |
| --- | --- | --- |
| `UClass` | UObject 类、继承关系、函数和默认对象等信息 | 找到实例所属类型及可用的复制/调用描述 |
| `UStruct` / `UScriptStruct` | 结构化字段布局；后者描述反射结构体 | 遍历并序列化结构中的字段，不是网络原子事务的保证 |
| `FProperty` | 字段类型、标志以及定位实例内数据所需的信息 | 为字段比较和序列化提供依据；特定类型可走定制路径 |
| `UFunction` | 函数标志、参数布局和调用入口 | 识别网络方向与可靠性，读写 RPC 参数并分发调用 |

UE 5.5 普通反射字段的实现以 `FProperty` 体系为主，不能照搬旧资料把所有字段描述都当成 `UProperty` 对象。类型描述和具体实例的值也要分开：类描述可以共享，每扇门的开关状态仍保存在自己的实例里。

生成的原生函数桥接入口负责把反射调用参数转交给 C++ 实现。`ProcessEvent` 是反射函数分发的重要入口；对于 Actor 的 RPC，还要结合函数标志、调用空间和 NetDriver 决定本地执行或远程发送。它并不是每次都发网络包，普通 C++ 函数的直接调用也不必全部经过它。

反射是这些能力的共同基础，不代表所有能力同时开启：

- 编辑器与蓝图按暴露标志提供属性编辑和函数调用。
- 序列化系统结合属性标志、Archive 和自定义实现决定保存什么，反射不等于自动永久存档。
- GC 可以沿可识别的 UObject 引用关系追踪对象；弱引用不因此成为强引用，普通 C++ 资源也不会因为所属类有反射就自动被 GC 管理。
- 网络系统在类型描述之上额外应用复制登记、方向、相关性、条件和连接预算；反射不会自动把全部字段发给所有人。

概念入口：Epic：Reflection System（5.5）。本地源码可对照 FProperty（引擎源码定位：`Engine/Source/Runtime/CoreUObject/Public/UObject/UnrealType.h:188`）、ProcessEvent（引擎源码定位：`Engine/Source/Runtime/CoreUObject/Private/UObject/ScriptCore.cpp:1997`） 与 Actor RPC 调用空间（引擎源码定位：`Engine/Source/Runtime/Engine/Private/Actor.cpp:4963`）。网络层如何使用这些描述，见本章 3.4 的属性路径和 3.6 的 RPC 路径。

> **Q：`StaticClass()`、`GetClass()` 和 CDO 是同一个东西吗？**
>
> `AMyActor::StaticClass()` 返回这个指定类型的 `UClass*`，不创建一个场景 Actor。`Object->GetClass()` 返回实例的实际运行时类型，可能是派生蓝图类。CDO 是每个类的默认对象，用于默认值与初始化等用途；它不是当前玩家或场景中的 GameState，也不应存一局比赛的可变状态。因此 `GameStateClass = AmultiplayerCoopGameState::StaticClass()` 是选择由框架创建哪一种 GameState，不是在这一行创建实例。

> **Q：加 `UPROPERTY()` 就能让对象不被回收、在蓝图可见并自动复制吗？**
>
> 不能把三个承诺合成一个。字段首先进入反射描述；可达对象上的受跟踪强 UObject 引用可以参与 GC 引用链，蓝图可见性取决于对应标志，联网还需要复制声明与登记以及对象复制条件。`UPROPERTY()` 标注的弱引用仍是弱引用；所属对象本身不可达，也不能指望一个普通成员独自把它永久保活。

> **Q：`UFUNCTION()`、蓝图事件、Delegate 和 RPC 是否都会跨网络？**
>
> 不会。普通反射函数和本地委托不因此成为 RPC；`BlueprintCallable` 只是允许蓝图调用，`BlueprintImplementableEvent` 只是提供蓝图实现入口。网络方向需要相应 RPC 声明与合法调用环境。本项目 `OnGameWon.Broadcast()` 是本机通知，另一端的通知来自那一端收到复制状态后再广播。

> **Q：RPC 可以直接调用 `_Implementation()` 吗？**
>
> 那是本地 C++ 实现入口，直接调用会绕过正常 RPC 包装与远程路由，不能用它向服务器发请求。业务调用 RPC 声明的函数名，由引擎选路；也不能把 `_Implementation` 名称或 C++ 的 private/protected 当作对远端输入的安全校验。

> **Q：反射会不会让所有代码都变慢？**
>
> 生成代码和类型描述有体积与初始化成本，动态查找、分发、序列化也可能有运行成本，但普通 C++ 直接调用不会仅因类支持反射就自动变成动态查找。热点应缓存查找结果、减少无意义序列化并按采样判断，不用“有宏所以慢”代替定位。

### 3.2 UDP 之上：连接、通道、Bunch 和 Packet

**图 3｜UE 常规游戏连接的传输层次**

```text
Server RPC / 复制属性 / 角色移动消息
            ↓  序列化与 ActorChannel / Bunch
    UNetConnection：包序号、确认、发送预算
            ↓  IpNetDriver → UDP 数据报
    对端：按连接与通道拆包、处理可靠序号
            ↓  Server RPC 执行 / 属性更新与 OnRep

可靠 Bunch 丢失：通道内保留并重发，后续可靠内容等待缺口补齐。
普通复制状态丢失：依据复制历史考虑重发变化，或发送更新后的当前状态。
```

下图中的两条恢复路径解决不同语义：必须按通道顺序执行的调用，与最终应收敛到权威值的属性，不能因为都走 UDP 就描述成同一种“可靠 UDP”。

裸 UDP 不负责可靠交付，但 UE 不会把一组游戏变量直接扔进 Socket 就结束。传统路径在 UDP 上维护连接状态、包序号、接收历史、通道、对象标识和复制记录。

| 层次 | 主要职责 | 不应混淆的概念 |
| --- | --- | --- |
| `UNetDriver` / `UIpNetDriver` | 管理连接，驱动收发和复制调度，适配底层 Socket | 一个 Actor 不对应一个 Socket |
| `UNetConnection` | 管理对端连接、Packet 收发、确认历史和发送预算 | 网络包确认不是业务完成确认 |
| `UActorChannel` | 为某个连接承载 Actor 及其复制子对象的数据 | 同一 Actor 面向不同连接有不同复制上下文 |
| `FOutBunch` / `FInBunch` | 表示通道上的序列化数据单元，包含属性或 RPC 等内容 | 一个 RPC 不必独占一个 UDP 包 |
| Packet | 聚合待发数据并携带网络控制信息，交给驱动发送 | Packet 与 Bunch 不是一一对应 |

可以沿着下面的路径阅读源码：

```text
属性变化 / RPC 调用
  → ActorChannel 与对象复制器序列化
  → FOutBunch（必要时拆成 Partial Bunch）
  → NetConnection 聚合并发送 Packet
  → IpNetDriver / IpConnection → UDP Socket
  → 对端解析 Packet、分发 Bunch → 更新对象或执行 RPC
```

一个 Packet 可以装入多个 Bunch；较大的 Bunch 也可能拆分后跨越多个 Packet。合并与拆分服务于包大小和发送效率，因此应用层不能把“一次函数调用”“一个 Bunch”和“一个网络包”等同起来。

`FNetPacketNotify` 根据包序号与接收历史生成交付通知，`UNetConnection::ReceivedPacket` 将其分发到 `ReceivedAck` 或 `ReceivedNak`。这里的 NAK 是引擎判断某个包未成功交付的通知，不必对应一个独立发送的“NAK 数据包”。

可靠 Bunch 则具有通道序号。发送端保留未确认记录；`UChannel::ReceivedNak` 会重发丢失包中尚未确认的可靠 Bunch。接收端遇到可靠序号缺口时缓存后续 Bunch，等缺口补齐后继续处理，重复内容也会被序号检查过滤。

这形成了**通道内可靠消息的顺序约束**。不同 Actor 通道没有由此获得统一总顺序；非可靠内容也不能套用相同的等待和重发承诺。通道之间仍共享连接带宽、包预算和部分对象依赖，不能反过来认为它们完全互不影响。

发送窗口与缓冲是有限资源。连接有未确认包序号范围和发送预算，通道有可靠消息队列；持续产生可靠数据可能挤压其他更新，队列溢出甚至导致连接关闭。它们不能直接套用 TCP 的 `rwnd/cwnd` 公式，也不是无限重试的消息数据库。

源码入口：NetConnection.cpp：ReceivedPacket（引擎源码定位：`Engine/Source/Runtime/Engine/Private/NetConnection.cpp:2945`）、DataChannel.cpp：ReceivedNak（引擎源码定位：`Engine/Source/Runtime/Engine/Private/DataChannel.cpp:1633`）。`ReceivedRawBunch`、`SendBunch` 和 `PrepBunch` 可继续追踪排序、拆包及可靠缓冲管理。

**需注意的细节**

> **Q：既然 UE 会重发可靠消息，是否等同于把整个游戏变成 TCP 字节流？**
>
> UE 仍按消息类别、连接和通道处理数据；部分旧消息允许丢弃，属性有独立的状态补发逻辑。可靠交付还受连接存活、缓冲和对象生命周期约束，不提供断线后自动续接所有历史调用的能力。

### 3.3 Authority、所有权和本地控制是三件事

对于服务器生成并复制的玩法 Actor，服务器持有权威实例。拥有该角色的远端客户端通常持有 `AutonomousProxy`，其他客户端持有 `SimulatedProxy`。角色名称描述网络职责，不表示每台机器上存在不同的 C++ 类。

`HasAuthority()` 判断当前 Actor 的本地网络角色；`IsLocallyControlled()` 判断 Pawn 是否在本机受控；`Owner` 及 owning connection 决定 RPC 路由和部分复制条件。客户端拥有一个 Pawn，并不因此获得修改服务器血量、库存或胜负的权力。

Listen Server 主机的本地 Pawn 可以同时具有 Authority 和本地控制。服务器上的远端 Pawn 具有 Authority，却不属于主机的本地输入；远端客户端自己的 Pawn 则本地受控但没有服务器权威。这也是输入、规则和表现不能仅靠一个布尔判断统一处理的原因。

Actor 的 owning connection 通常沿 Owner 链追溯到 PlayerController。组件使用其所属 Actor 的网络归属。场景中的公共门、平台或机关通常不归任意一个客户端所有，不能因为玩家正看着它，就直接把它当成合法的 Server RPC 入口。

参考：Actor Owner and Owning Connection、Actor Role and Remote Role。

**需注意的细节**

> **Q：`HasAuthority()` 能否直接当成“这台机器是服务器”的通用判断？**
>
> 它描述 Actor 的角色。客户端自行创建且没有参与服务器复制的本地 Actor 也可能具有 Authority。判断 World 的网络模式用 `GetNetMode()`；判断玩法写权限则结合对象来源和服务器规则。

### 3.4 属性复制：让接收方收敛到当前状态

传统属性复制的方向是服务器到客户端。Actor 需要参与复制，属性需要通过 `Replicated` / `ReplicatedUsing` 声明，并在 `GetLifetimeReplicatedProps` 中登记；组件和子对象还要满足各自的注册与复制要求。仅仅添加一个 `UPROPERTY` 不会自动联网。

服务器将符合条件的 Actor 交给 `UActorChannel::ReplicateActor`，再由 `FObjectReplicator`、`FRepLayout` 等处理字段布局、变化比较和序列化。传统轮询路径需要比较当前状态与跟踪状态；Push Model 可以改变脏状态通知方式，但必须按它的规则正确标脏。

复制结果按连接维护。两个客户端可能有不同相关性、复制条件、已确认历史和可用带宽，因此“服务器已经发送过这个 Actor”不能推出“所有客户端已经收到同一份更新”。部分变化检测可以共享计算，但连接自己的发送与确认进度仍需分别处理。

常规属性更新不必使用可靠 Bunch。属性层维护发送历史，丢包通知会让相关变化重新进入发送考虑；后续可以发送更新后的当前值。`FObjectReplicator::ReceivedNak` 中的历史重发标记，与上一节可靠 Bunch 的重发是两条不同路径。

例如服务器在两次有效复制之间把计数从 `0 → 1 → 2`，客户端可能直接看到 `0 → 2`。只要连接、相关性、复制条件和对象生命周期允许继续同步，它应当得到后续权威状态；引擎不承诺每个短暂中间值都产生一次客户端通知。

因此，门是否打开、当前目标进度、玩家是否存活，适合建模成状态；必须逐条保存的交易、对话记录或操作流水，应有记录标识和历史管理。不能靠反复翻转一个复制布尔值来表达必须观察到的所有事件。

`ReplicatedUsing` 把接收端状态变化连接到 `OnRep`。在 C++ 中，服务器普通赋值不会自动触发本机的接收端 RepNotify；Listen Server 的本地表现通常也需要在权威写入后调用共享应用函数。

```cpp
// 仅示意两条入口汇合；字段声明、复制登记和 Actor 初始化略。
void AExampleActor::SetStateOnServer(const FExampleState& NewState)
{
    if (!HasAuthority()) return;
    State = NewState;
    ApplyStateLocally();        // 服务器侧通知；内部区分规则与本地表现
}

void AExampleActor::OnRep_State()
{
    ApplyStateLocally();        // 客户端收到状态后复用同一套应用逻辑
}
```

共享应用函数应可重复执行，用当前值设置显示和碰撞等表现。创建 UI 还要检查本地玩家，不能让 Dedicated Server 或服务器上的每个远端 Controller 都创建界面。蓝图 RepNotify 的 Set 节点可能有不同的本地通知行为，不应机械套用 C++ 赋值结论。

多个独立属性的 `OnRep` 没有可依赖的固定调用顺序。紧密关联的小字段可放入同一个状态结构，在一个回调中读取，必要时附带版本号；这有助于统一应用时机，但不会把跨 Actor 更新变成分布式事务。

**需注意的细节**

> **Q：在客户端修改一个复制属性，会不会立刻被服务器值覆盖？**
>
> 客户端修改不会自动上传，但纠正也不一定发生在下一帧。服务器若没有新的可发送变化，客户端错误值可能暂时保留。共享状态应通过服务器规则入口修改，不能把复制机制当成本地任意写入后的自动撤销器。

### 3.5 复制调度：相关性、频率、优先级与休眠

`UNetDriver::ServerReplicateActors` 不会每帧向每个连接无条件发送整个世界。它先建立候选列表，再结合连接视点、关卡加载和相关性决定候选 Actor，按优先级处理，最后在预算允许时复制变化。

| 机制 | 回答的问题 | 常见误解 |
| --- | --- | --- |
| Relevancy | 这个连接现在需要此 Actor 吗？ | 把相关性简单等同于距离 |
| `NetUpdateFrequency` | Actor 多久获得一次更新考虑机会？ | 配置 30 就保证每秒收到 30 包 |
| `NetPriority` / `GetNetPriority` | 预算竞争时谁应更早更新？ | 提高优先级会创造额外带宽 |
| Dormancy | 长期不变的 Actor 能否暂时跳过变化检查？ | 休眠后修改字段仍会自动及时同步 |

相关性还可能涉及所有者、`bAlwaysRelevant`、`bOnlyRelevantToOwner` 和自定义规则。提高频率不能让不相关的 Actor 自动出现；`ForceNetUpdate()` 是推动下一轮更新考虑，也不会绕过所有连接预算、相关性和对象可用条件。

休眠适合长期稳定、偶尔改变的对象。Dormant Actor 可以继续存在于客户端，其复制通道却可能已经关闭。它与 Actor 因失去相关性而从客户端移除，不是同一种生命周期事件。

修改休眠对象前应先按场景调用 `FlushNetDormancy()` 或唤醒 Actor；组件和复制子对象也依赖所属 Actor 的休眠状态。修改之后才处理唤醒可能错过用于比较的基线，不能把休眠理解成“变化自动唤醒”。

源码入口：NetDriver.cpp：ServerReplicateActors（引擎源码定位：`Engine/Source/Runtime/Engine/Private/NetDriver.cpp:5911`）。补充：Detailed Actor Replication Flow、Actor Network Dormancy。

**需注意的细节**

> **Q：属性没有变化，就完全没有复制开销吗？**
>
> 通常可避免发送该字段的数据，但候选筛选、相关性判断、变化比较和连接维护仍可能占 CPU。频率、休眠、复制条件和对象组织分别作用于不同成本，优化前应先确定瓶颈。

### 3.6 RPC：带方向和归属约束的远程调用

**3.6.1 调用方向、所有权与顺序**

RPC 把一次调用的函数标识和参数序列化给远端。它不是本地函数跨机器同步返回结果；需要响应时，应设计后续 RPC、复制状态或带请求标识的结果。

下面只列常见的合法远程路径。完整行为还取决于调用端、Actor 复制状态和 owning connection，方向说明符并不保证每次调用都真正跨网络。

| RPC | 常见调用位置 | 目标与前提 |
| --- | --- | --- |
| `Server` | 所属客户端的 Pawn、Controller 或其复制组件 | 发往服务器；远程调用者需具有正确 owning connection |
| `Client` | 服务器上的 Actor | 发往该 Actor 的 owning client |
| `NetMulticast` | 服务器上的复制 Actor | 在服务器和符合发送条件的相关客户端执行 |

客户端在自己不拥有的公共机关上调用 Server RPC，通常不能按预期到达服务器；客户端调用 NetMulticast 也不会获得向其他客户端广播的能力。客户端自行 `SetOwner` 不会改变服务器认可的归属。

常见交互链是“本地输入 → 自己拥有的 Controller/Pawn → Server RPC → 服务器查询目标并判定 → 修改权威状态”。请求携带目标与意图，服务器核对调用者、距离、目标有效性、当前阶段、资源、频率及重复请求，而不是直接接受客户端提交的最终结果。

`Reliable` 是消息传输选项，不是权限验证。业务拒绝通常在服务器实现中清楚处理；使用 `WithValidation` 时，校验失败会导致调用客户端断开，不能把所有正常的“现在不能开门”都当作协议违规。

在同一连接、同一 Actor 通道的通常发送路径上，可靠 RPC 保持相对执行顺序；共享该通道的复制子对象也使用通道内序列。不同 Actor 之间没有全局调用顺序，可靠与非可靠 RPC 混用也不能依赖整体顺序。

例如先在钥匙 Actor 调用“隐藏”，再在门 Actor 调用“打开”，不能据发送端代码顺序要求所有客户端先隐藏再开门。如果这两个动作有共同约束，应由权威状态、版本和依赖就绪条件组织表现，而不是跨 Actor 串接隐含时序。

同样，先给属性赋值再调用 RPC，不代表接收方执行 RPC 时一定已应用该属性。RPC 所需的瞬时参数应明确传入；持续状态由复制属性表达。把某个包内常见排序当成跨帧、跨 Actor 的因果保证，会留下丢包后才暴露的问题。

“可靠传输中的重复 Bunch 被过滤”也不等于“一个业务请求永远只执行一次”。用户连续点击、应用超时重试和重连后重发，可能产生多个不同调用；需要一次性效果时，服务器应检查状态转移或维护请求标识。

非可靠 RPC 适合允许遗漏的瞬时表现或可由后续新数据覆盖的采样。重要的低频意图可以用可靠 RPC，但持续状态仍应保存在可复制对象中，方便后来加入或重新相关的客户端重建当前世界。

补充：Remote Procedure Calls、Replicated Object Execution Order。

**需注意的细节**

> **Q：给所有 RPC 都加 `Reliable`，是否最安全？**
>
> 高频旧消息会占用可靠缓冲并形成等待，影响后续更新，严重时触发连接错误。可靠级别应由消息是否允许遗漏、是否会过期和是否能由状态恢复决定；它不能替代限流、校验和业务幂等。

**3.6.2 属性复制与 RPC：状态和调用不是互斥选择**

属性复制主要回答“现在是什么状态”，RPC 主要回答“请求执行或通知一次什么操作”。二者是 Actor 网络通信的两类核心机制，不是两种完全独立的传输协议；普通属性更新和 RPC 都可以进入前述连接、通道与包路径。

| 比较维度 | 属性复制 | RPC |
| --- | --- | --- |
| 内容 | 当前状态，以及为恢复该状态所需的信息 | 一次函数调用的标识与参数 |
| 通常方向 | 服务器向符合条件的客户端发布 | 按 Server、Client、NetMulticast 等方向与归属规则路由 |
| 发起方式 | 状态进入复制流程，由调度和变化检测等决定发送 | 业务显式调用；实际发送仍受合法性、调度和预算约束 |
| 可靠性含义 | 满足持续同步条件时收敛到权威状态，不保证观察所有中间值 | Reliable 有受限的重发与通道内顺序；Unreliable 允许遗漏 |
| 晚加入/重新相关 | 对象仍存在且符合复制条件时，可建立当前状态 | 不自动重放此前已执行的历史调用 |
| 接收后逻辑 | 更新字段，必要时执行 RepNotify | 反序列化参数并执行对应函数 |
| 主要成本 | 候选与变化检查、每连接记录、字段序列化和带宽 | 调用次数、参数序列化、发送量及可靠队列压力 |
| 安全要求 | 控制服务器写入口与数据可见范围 | 除路由检查外，验证请求内容、状态和频率 |

如果门状态依次经历 `关 → 开 → 关`，客户端可能只看到最后的“关”；这是状态协议允许的合并，不能用它精确计数“开门事件发生了几次”。反过来，只广播一次“开门”RPC 而不保存状态，晚加入者也无法靠历史调用知道门目前是否开着。

两者常组成同一个闭环：**请求用 RPC，服务器判定并保存结果，持续结果用属性复制，允许丢失的瞬时表现按需用非可靠 RPC。** 有的动作根本不需要客户端请求，例如本项目服务器碰撞触发的宝物归位，不能为了套这个流程额外增加 RPC。

> **Q：属性复制一定比 RPC 省带宽吗？**
>
> 不一定。相同状态的重复 RPC 往往可以被状态模型替代，但属性也有比较、基线和序列化成本。要比较相同业务保证下的调用量、字段大小、连接数量与 CPU，而不能仅数接口名称。Fast Array、Push Model 等优化同样要针对具体成本。

> **Q：RepNotify 能当作“每次赋值的远程回调”吗？**
>
> 不能。赋值次数、实际发送次数和接收通知次数不是一一对应；通知条件还受配置影响。需要可靠记录每次发生的业务事件时，应设计带序号的记录及保留/确认策略，而不是快速翻转同一个布尔值。

**3.6.3 按业务语义选择：请求、状态与瞬时表现**

| 场景 | 优先表达方式 | 不能漏掉的条件 |
| --- | --- | --- |
| 血量、弹药、目标进度、门是否开启 | 服务器状态 + 属性复制，按需 RepNotify | 不依赖收到所有中间值；晚加入可读取当前值 |
| 玩家请求使用机关、换弹或重开 | 所属 Pawn/Controller 的 Server RPC | 服务器核对身份、目标、资格和重复请求；低频重要意图可用 Reliable |
| 一次允许遗漏的枪口火光、碰撞音效 | 按需 Unreliable RPC，或由已有状态变化派生 | 只是表现，不在其是否送达上决定真实伤害 |
| 服务器只通知某玩家一次拒绝原因 | 拥有该连接的对象上的 Client RPC | 选择所需可靠级别；若信息需长久保留，另存可恢复状态 |
| 灼烧持续特效、持续施法或长时间机关过渡 | 阶段/开始时间等可恢复状态，再由本地表现 | 不把持续状态误当作一声播放指令；处理晚到、结束与重入 |
| 奖励领取、交易等不能重复的结果 | 权威业务记录 + 请求标识/去重 + 确认 | Reliable RPC 不是数据库事务，也不是跨重连的恰好一次执行 |

上表包含通用案例，不表示本 Co-op 已实现射击、灼烧或交易。也不是“所有粒子都发 RPC”：能从已复制状态恢复的本地表现，通常没有必要再同步同一事实。

本项目已有两个具体对照：

- `GameState.ObjectiveState` 使用 `ReplicatedUsing`，客户端接收后通知本地监听者显示进度和胜利；不是靠胜利 Multicast 保存结果。
- `PlayerController::ServerRequestRestartCurrentRound` 使用低频 Reliable Server RPC。服务器转交 GameMode 检查当前胜利、请求者和重复重开标记；可靠传输本身不批准重开。

源码：CoopGameState（仓库路径：`Source/multiplayer/Core/multiplayerCoopGameState.h`）、CoopPlayerController（仓库路径：`Source/multiplayer/Player/multiplayerCoopPlayerController.cpp`）、GameMode（仓库路径：`Source/multiplayer/Core/multiplayerGameMode.cpp`）。

> **Q：为什么交互请求不直接写在公共门的 Server RPC 上？**
>
> 公共门通常不属于这个客户端，没有对应的合法 owning connection。先通过自己的 Controller/Pawn 发出请求，服务器再查询并验证目标；临时在客户端 SetOwner 不是授权方法。本项目自动归位由服务器 Overlap 驱动，也不需要套上主动交互请求。

**3.6.4 可靠性与安全性必须分开评价**

可靠性关注消息遗漏、顺序与恢复；安全性关注不可信一端能否伪造结果、越权读取或耗尽资源。**“属性复制天然安全、RPC 天然不安全”不成立。** 服务器向下复制能建立清楚的结果写方向，但如果服务器先相信了错误请求，再把结果复制出去，错误仍然存在。

可以把安全边界分为四层：

1. **路由与身份。** 引擎根据连接归属筛选客户端 Server RPC；业务还需要依据服务器所知的请求者，而不是信任参数里的“我是某玩家”。拥有 Actor 只代表可从这个入口提交请求，不代表请求内容可信。
2. **规则校验。** 服务器检查对象有效性、距离/视线、资源、冷却、阶段及数值范围。传入对象引用、时间戳和最终伤害都不能直接当事实；按玩法选择相应检查，本项目并没有完整实现所有这些通用防护。
3. **信息与资源。** 不向无权知晓的连接发送隐藏信息；控制请求频率、参数和队列规模。`private`、`BlueprintReadOnly` 都不是网络加密，已经送到玩家机器的数据也不能靠不显示来保密。
4. **结果与恢复。** 重复点击、超时重试和重连重发可能是不同调用。用状态转换或请求标识防止重复结算；重要持久结果仍需业务存储和审计。

`COND_OwnerOnly` 等复制条件可帮助限制字段的接收对象，但不能代替账号鉴权，也不能收回接收方此前已获得的数据。RPC 则增加了显式的远程输入入口，所以尤其要检查其业务参数与调用频率；这不意味着必须禁止 RPC。

本项目已经把共享目标限制为服务器写入，并给重开请求增加服务器状态检查与重复保护。这是局部信任边界，不应写成“完成反作弊系统”；公网身份认证、全面限流与恶意流量防护仍是另外的工程任务。

> **Q：`Reliable` 能保证请求合法、被接受，而且只执行一次吗？**
>
> 都不能由这个标志单独保证。它提供连接存活等前提下的传输保证，不判定操作资格，也不跨业务重试和断线保存事务。网络收到与业务批准是两种结果；需要时必须明确返回批准或拒绝信息。

> **Q：客户端能修改自己的复制属性，那服务器权威还有意义吗？**
>
> 有意义。玩家可以篡改自己的内存和画面，目标是让这种修改不能成为其他玩家接受的权威事实。服务器不自动接收该本地赋值；但若后续 RPC 又把客户端自报数值当真，就主动破坏了这条边界。隐藏信息保护和权威结果保护也不是同一件事。

> **Q：Listen Server 的 Authority 能防主机作弊吗？**
>
> 不能。主机拥有权威进程，能修改该进程中的规则和状态。Dedicated Server 由可信运营环境管理时可以改变这项信任前提，但仍要验证所有客户端请求；单靠一个 HasAuthority 判断不会让不可信的主机变可信。

参考：Epic：RPC 的方向与可靠性（5.5）、属性复制与条件（5.5）。接收顺序与底层确认路径沿用本章 3.2～3.6.1 的源码依据，不从可靠性直接推导安全性。

### 3.7 CharacterMovement：预测、校正与重放如何衔接

角色移动不能等每次往返结束才响应输入。`ACharacter` 与 `UCharacterMovementComponent` 为此提供了一套专用机制：所属客户端先预测，服务器重演并校验，出现偏差时纠正，其他客户端则接收移动状态并平滑显示。

本项目的正式 `multiplayerCharacter` 继承 `ACharacter`，把增强输入转成 `AddMovementInput` 等调用，构造函数配置标准 CharacterMovement 参数。正式角色未替换 CMC，也没有另一套手写角色位置 RPC；测试角色使用仅增加观测记录的 CMC 派生类。以下预测与重放流程属于引擎能力。

| 阶段 | 所在实例 | 发生的工作 |
| --- | --- | --- |
| 本地预测 | Owning Client / AutonomousProxy | 即时模拟移动，并保存 `FSavedMove_Character` |
| 提交移动 | Owning Client → Server | 合并可合并的移动，发送必要的时间、输入和结果信息 |
| 权威校验 | Server / Authority | 从服务器自身状态模拟，验证时间和移动误差 |
| 确认或纠正 | Server → Owning Client | 确认已处理移动，或返回权威位置等纠正信息 |
| 重放 | Owning Client | 从纠正状态重新模拟尚未确认的 SavedMoves |
| 远端表现 | 其他客户端 / SimulatedProxy | 应用复制移动并进行网络平滑 |

`ReplicateMoveToServer` 负责将本地移动与保存记录、发送过程衔接。`SavedMoves` 不只是历史日志：收到服务器确认后可以移除对应记录；收到纠正后，它为尚未被服务器确认的本地操作提供重放依据。

UE 5.5 的 packed movement 路径使用 `ServerMovePacked` 和 `ClientMoveResponsePacked`，它们在 `Character.h` 中声明为 **Unreliable RPC**。移动层通过时间戳、保存记录、可选旧 Move 及后续确认/校正处理遗漏，不依赖把每个移动采样都塞进可靠 RPC 队列。

`ServerMove_HandleMoveData` 可以处理旧 Move、待合并 Move 和新 Move，`ServerMove_PerformMovement` 在服务器执行对应模拟。客户端报告的位置用于误差检查，不是服务器不加判断地接受的最终位置。

需要纠正时，客户端先接受服务器提供的基准，再由 `ClientUpdatePositionAfterServerUpdate` 重放未确认记录。预测使操作及时，纠正使状态回到权威轨道，重放则保留纠正点之后仍有效的本地输入。

远端角色的网络平滑负责减轻低频更新带来的视觉跳跃；`SmoothClientPosition` 与本地玩家的预测重放不是同一件事。平滑画面不等于把服务器碰撞和判定也改成纯视觉插值，更不能保证严重丢包时永远没有跳变。

开发自定义冲刺、攀爬或其他移动能力时，影响模拟的额外状态也要纳入保存、序列化和重放规则。直接在客户端反复设置位置，很容易与服务器纠正相互争夺；原有预测并不会自动理解所有新增玩法变量。

源码入口：CharacterMovementComponent.cpp：ReplicateMoveToServer（引擎源码定位：`Engine/Source/Runtime/Engine/Private/Components/CharacterMovementComponent.cpp:8666`）、ClientUpdatePositionAfterServerUpdate（引擎源码定位：`Engine/Source/Runtime/Engine/Private/Components/CharacterMovementComponent.cpp:8365`）、Character.h：移动 RPC（引擎源码定位：`Engine/Source/Runtime/Engine/Classes/GameFramework/Character.h:279`）。补充：Networked Movement in the Character Movement Component。

**需注意的细节**

> **Q：项目里有预测和回放，能否称为已经实现全局回滚或帧同步？**
>
> 这里是 CMC 针对所属角色移动的纠正与 SavedMoves 重放，不是将整个玩法世界回退到历史帧。本项目也没有实现独立的确定性帧同步内核或通用世界回滚系统。

### 3.8 框架对象：把规则、共享状态和本地生命周期分开

UE 的玩法框架已经给出一组网络职责边界。选择存储位置时，先确定状态由谁写、谁需要看、是否跨地图保留，再决定使用哪个类。

| 对象 | 网络中的常见分布 | 适合承担的职责 |
| --- | --- | --- |
| `GameMode` | 服务器 World 存在，客户端没有对应权威规则实例 | 准入、出生、回合和胜负规则 |
| `GameState` | 服务器维护，复制给客户端 | 比赛阶段、共享目标和公共进度 |
| `PlayerController` | 服务器有各玩家实例；客户端通常只有自己的 | 玩家输入、所属连接 RPC 入口、本地 UI 桥接 |
| `PlayerState` | 服务器维护，通常复制到各客户端 | 名称、积分等需要共享的玩家状态 |
| `GameInstance` | 每个游戏实例各自存在，本身不复制 | 会话接口、旅行流程、本地跨地图状态 |
| `Pawn / Character` | 服务器权威实例和满足复制条件的客户端代理 | 当前可控制的身体与移动状态 |

客户端不能通过读取 GameMode 获得共享进度；把进度放进 GameInstance 也不会让其他机器自动得到相同数据。反过来，把所有玩家公共信息放进 PlayerController，会遇到其他客户端没有该 Controller 的分布边界。

PlayerState 与 Pawn 的生命周期有区别，适合把部分玩家身份和统计从“当前身体”中分离；但断线恢复、跨服务器续玩和永久存档仍需要显式设计，不会因使用 PlayerState 自动完成。

参考：Gameplay Framework。本项目中这些职责怎样连接，见第四章。

**需注意的细节**

> **Q：GameInstance 跨地图存在，是否等于跨机器共享且永久保存？**
>
> 它只属于当前游戏实例的本地生命周期；不同进程或 PIE 实例各有自己的对象。跨地图保留、网络复制和持久化存档是三种不同保证。

### 3.9 Listen Server 与 Dedicated Server：部署改变了什么

两种模式都可以采用服务器权威、属性复制和 RPC。Dedicated Server 并不会把状态同步自动变成帧同步，Listen Server 也不是允许每个客户端随意决定结果的对等模型。

| 维度 | Listen Server | Dedicated Server |
| --- | --- | --- |
| 本地玩家 | 主机同时参与游戏 | 服务器没有本地玩家 |
| 资源 | 权威模拟与本地画面、音频等共享机器资源 | 可集中资源处理模拟和网络 |
| 时延与信任 | 主机玩家在权威机器本地执行，存在体验和信任差异 | 玩家都通过远程连接参与，但 RTT 仍可不同 |
| 生命周期 | 主机退出通常使当前服务器消失 | 可独立于玩家上线、下线运行 |
| 部署 | 适合玩家临时建房；公网仍有连通性问题 | 需要服务端构建、部署、监控和容量管理 |

Dedicated Server 没有本地玩家，不应依赖本地视口、UI 或某个主机 Controller 才能推进服务器规则。Listen Server 则更容易暴露另一类问题：只在客户端 OnRep 内更新表现，会漏掉主机本地路径。

独立服务器可减少主机玩家优势，并将权威执行环境交给运营方管理；这不等于所有玩家延迟相同，也不意味着自动具备反作弊、跨区调度、自动扩容或故障恢复。

当前工程使用 Listen 建房流程，已有源码中没有独立 Server Target；这里也没有 Dedicated Server 部署与运行验证记录。因此本章讨论的是迁移边界，不把它写成项目已完成的能力。OnlineSubsystemNull 的局域网发现同样不能替代公网账号、匹配或中继服务。

参考：Networking Overview：Network Modes 与 Server Types。

**需注意的细节**

> **Q：主机退出后，其他客户端能否自动选出一个新主机继续运行？**
>
> 这需要主机迁移、状态恢复和重新连接等额外机制。Listen Server 与 Session 接口本身不为当前项目提供这样的保证；连接回仍存活的原服务器也不是主机迁移。

### 3.10 帧同步、Replication Graph 与 Iris 的后续边界

在 UE 中实现帧同步，关键是建立独立、可重复的逻辑模拟：固定逻辑步长、明确输入帧和缺失输入策略、受控随机数、稳定的实体遍历与事件顺序，以及必要的校验、快照和恢复机制。状态同步与帧同步的通用取舍见第二章。

仅固定 Tick 间隔、打开物理子步或让双方使用同一个随机种子，不能消除全部浮点、物理接触、异步调度和执行顺序差异。普通 Actor Tick 与默认物理世界不会自动变成跨机器确定性内核。

可行的架构通常把确定性逻辑状态与 UE 表现对象分离：逻辑层处理按帧确认的输入，Actor 层消费模拟结果做渲染、音效和界面。传输层还要定义输入缺失时等待、预测还是回滚；混合同步模式则需要清楚划分权威归属和数据边界。

Replication Graph 主要面向大量 Actor 和连接时的候选收集与相关性组织，通过节点复用和空间/业务分组降低调度成本。它不会自动改变玩法权威规则，也不替代属性定义和 RPC 设计。Epic：Replication Graph

Iris 是另一套复制系统演进方案，涉及不同的状态描述、过滤和优先级路径。引入时需要核对项目版本、功能兼容性和子对象等用法，不能把传统 `UActorChannel` 的全部实现细节原样套过去。Epic：Iris Replication System（UE 5.5）

本工程没有自建帧同步内核、配置 Replication Graph 或显式启用 Iris；也没有接入 GAS。它们可以作为后续研究方向，但不参与解释现有项目的网络成果。

**需注意的细节**

> **Q：规模增大后，是否应该直接换一套复制系统？**
>
> 先区分是候选筛选 CPU、序列化成本、带宽、可靠队列，还是玩法依赖关系出了问题。复制系统升级解决的是特定成本与能力边界，不会自动修正客户端越权、事件丢失或跨 Actor 的错误时序假设。

下一章把这些机制落到本工程的角色、机关、目标快照和会话数据流；测试证据与问题复盘放在第五章。

## 第四章：项目中的网络同步方案、取舍与边界

整理日期：2026-09-27。返回总目录。前置：UE 网络机制；后续：问题与优化复盘。

本章回答“当前项目怎样工作，为什么这样选择”。排查过程和完整数据分别放在第五章与实验附录（见文末附录；仓库路径：`Docs/Reports/2026-09-27/Appendix.md`），不把通用网络知识当成本项目已经实现的功能。

### 4.1 先明确项目规模和目标

项目是 UE 5.5 双人局域网 Co-op 原型，使用 OnlineSubsystemNull 与 Listen Server。目标是让双方完成宝物触碰归位、压力板与合作门、移动平台、共享进度、胜利、当前关卡重开与退出，并处理短暂断线后的有限重连。

当前建房让主机所在 World 原地开始监听，发布的是当前地图；不会自动选择合作地图。客户端解析会话连接地址后进入主机所在地图。胜利后的重开则重载当前关卡，这与“创建房间后自动选图”不是一回事。

设计原则是：有影响的结果由服务器决定，客户端展示这些结果；稳定机关不为每一帧的网格位置付出持续复制成本；角色移动使用引擎现有能力，不另造一套预测系统。

> **Q：这里有没有专用服务器、GAS 或自研预测回滚？**
>
> 当前没有专用服务器部署，也没有将 GAS 作为这一版网络方案。角色使用 CharacterMovement 内建的预测与纠错，不等于项目自行实现了预测回滚。平台仍使用普通 Actor 位移复制，不能把角色的能力一起算到平台上。

### 4.2 规则、状态、连接和表现分别放在哪里

| 模块 | 当前职责 | 不负责什么 |
| --- | --- | --- |
| GameMode | 目标登记、胜利复核、人数规则与合法重开请求 | 不在客户端保存一套独立胜负结果 |
| CoopGameState | 保存并复制目标数量、进度与胜利状态 | 不代替客户端 UI，也不管理 Session |
| GameInstance | Session 创建/搜索/加入/退出、连接失败、有限重连、配置读取 | 不通过属性复制同步自己的成员给所有玩家 |
| PlayerController | 所属玩家的请求入口、本地界面和连接进入确认 | 不把每个玩家的界面广播到所有客户端 |
| 各机关 Actor | 服务器判断本机关规则，发布所需状态 | 不把全部机关逻辑塞进 GameMode |
| PlayerOccupancyComponent | 不同角色计数、多碰撞体处理、销毁清理 | 不直接决定合作门最终规则 |
| TransporterComponent | 服务器沿固定轨道推进平台 | 不做通用碰撞避障或客户端预测 |
| VictoryPresenter / Widget | 订阅并补读当前胜利状态，显示本地界面 | 不决定是否胜利，不复制 Widget |

关键结果的主线为：宝物服务器重叠检查 → 插槽完成一次性登记 → GameMode 更新进度并复核规则 → GameState 发布共享结果 → 客户端据此更新本地状态与界面。

**图 4｜项目中的请求、裁决与表现。**下方文字版随正文导入；单独图片文件：`figures/04-ue-authority-flow.png`。

```text
远端玩家输入 ─→ 自身 CMC 预测 ─→ ServerMove ─→ 服务器 CMC 校验/校正

服务器碰撞检测 ─→ 宝物/插槽、压力板/门规则 ─→ GameMode 复核胜利

```

远端玩家拥有输入入口，机关结果由服务器判断；平台使用变换复制，角色预测由 CMC 提供。这些箭头表示权力与数据流，不表示跨不同 Actor 的数据在同一网络帧原子到达。

但门的开关保存在门上，平台的位置由平台复制。并非所有网络数据都绕 GameState 一圈。

### 4.3 按对象行为选择同步方式

| 对象 | 当前服务器行为 | 网络发布内容 | 选择理由与代价 |
| --- | --- | --- | --- |
| Character | 处理移动与权威校验 | CMC 的移动协议与复制结果 | 复用引擎预测、纠错和移动基座能力；需遵守其移动路径 |
| 宝物与插槽 | 真实 Overlap 检查、归位、一次性进度登记 | 宝物安装等状态、相关附着/位置；共享进度另由 GameState 发布 | 当前是自动归位玩法，不需要每次交互自己设计一套客户端请求协议 |
| 压力板 | 统计不同玩家并判断目标条件 | 激活状态，初始复制的运行速度 | 不持续发压下网格的位置；远端按收到状态播放过渡 |
| 合作门 | 合并板状态与不同玩家集合 | 开关状态，初始复制的运行速度 | 同一规则输入触发重算，状态没变不重复发布 |
| 移动平台 | 根据激活来源启停、沿轨道移动 | Actor Movement Replication | 会影响角色站立，直接发布服务器变换；不是只给客户端一个开关让它自行算碰撞轨迹 |
| 目标和胜利 | GameMode 校验，GameState 保存结果 | 同一个目标状态结构 | 避免 UI 各自猜测进度；不要求收到每个中间变化 |

**4.3.1 门和压力板：同步结果，不同步每帧动画**

两者关闭 Actor Movement Replication，常规更新频率上限为 5 Hz，并在稳定时休眠。客户端根据开关状态和运行速度，更新本地网格过渡；服务器本地也走共用表现路径，照顾 Listen 主机。

服务器状态变更前刷新休眠，然后赋值、更新本地表现并请求网络更新。相同状态不反复广播，也不靠高频 Multicast 持续推送门位置。

> **Q：这是不是客户端预测？**
>
> 不是。这里是收到服务器结果后做本地过渡，不是在服务器确认前预测玩家行为，也没有保存输入并重演。减少同步字段与预测是不同技术。

> **Q：门开关只发一个状态，有没有代价？**
>
> 有。当前没有同步共同的服务器过渡起始时间，各端收到状态的时刻不同，过渡进度可能暂时不同；门碰撞又跟随本地网格，因此弱网中通行表现有待专门验收。若确实影响玩法，可以补阶段、起始时间和起始进度，或者让碰撞切换采用更明确的权威规则，而非直接扩大为全套预测回滚。

参考实现：PressurePlate（仓库路径：`Source/multiplayer/Mechanisms/multiplayerPressurePlate.cpp`）、CoopGate（仓库路径：`Source/multiplayer/Mechanisms/multiplayerCoopGate.cpp`）。

**4.3.2 平台：连续运动不能照抄静止机关方案**

平台设置 `bReplicates` 与 `ReplicateMovement`，频率上限为 30 Hz；服务器的 Transporter 计算固定世界轨道，到位后停止运动 Tick，客户端接收变换。当前补齐了三个配合环节：Transporter 在 `TG_PrePhysics` 更新，以配合 CMC 的基座依赖；服务器按实际位移维护根组件速度，客户端通过 `PostNetReceiveVelocity` 接收速度；开始、反向和停止时请求网络更新。

角色起跳不只依赖平台位置，还要继承基座速度。项目现在选择保留空中水平惯性，`BrakingDecelerationFalling` 从 1500 改为 0；这也改变普通跳跃松开方向键后的手感，是明确的运动规则取舍，不是带宽优化，也不是自研预测算法。

这里的目标是**自由跳跃**：离地时继承平台当时的速度并解除基座，之后由惯性、重力、空中输入与碰撞决定运动；平台后来停止或反向，不应仅因原基座关系直接改变空中角色的运动。保留惯性不等于保留基座。曾试验的 `AirBase` 会在平台上方继续随基座运动，虽然仍可接受空中输入，却不符合本项目的独立运动规则，已撤回正式角色接入。

没有选“只复制终点和开关，让两端独立跑平台”，是因为平台还参与角色承载。仅靠本地时间推进的两份轨迹，在延迟和停启时序不同的情况下，会增加角色与基座不一致的问题。当前先保持简单的服务器位置真相，再通过载人测试检查实际结果。

> **Q：普通 Actor 复制已经保证平台和角色完全平滑了吗？**
>
> 没有。早期动态实验在三档网络各运行一次，双方都观察到站立、行走、换向、起跳落回通过；其中 Harsh 为 13 次校正、最大可比较误差约 72.12 cm。后续另一轮同 Move 定位记录到 10 次、84.23 cm，两者属于不同运行，不能当作前后收益。这些 NullRHI 结果证明指定动作能完成，不证明画面完全平滑；最新对照和未解决边界见第五章阶段七。

> **Q：平台会自动避免穿墙或挤压吗？**
>
> 不会。当前保留无碰撞 Scene 根与承载网格，固定轨道移动显式不 Sweep。轨道避障依靠关卡布局；如果玩法要求遇障停下或挤压规则，就必须补碰撞策略和网络验收，不能只修改一条注释。

参考实现：MovingPlatform（仓库路径：`Source/multiplayer/Mechanisms/multiplayerMovingPlatform.cpp`）、TransporterComponent（仓库路径：`Source/multiplayer/Mechanisms/multiplayerTransporterComponent.cpp`）。

**4.3.3 宝物、胜利与重复触发**

当前地图的宝物预绑定目标插槽。角色进入范围后，由服务器检查宝物与插槽状态，自动吸附到插槽并登记进度。插槽先确认安装成功、设置已激活并关闭触发，再调用外部登记，减少重复进入导致重复结算的机会。

胜利不是客户端看见进度满了就自己宣布。WinArea 汇合人数与目标条件，GameMode 再检查人数、目标完成和已有胜利状态，随后提交 GameState。

> **Q：这是两条线程同时修改导致的并发问题吗？**
>
> 当前核心问题是游戏线程中的多人请求、多个重叠回调与同步重入，不需要为这些单线程路径额外加互斥锁。状态检查和“先确认处理标记、再调用外部监听者”的顺序更关键。

> **Q：是不是所有对象状态在同一网络帧里原子到达？**
>
> 不是。把相关目标字段组织在一个结构中便于本地按当前结果解释，但宝物、插槽、门和 GameState 是不同对象，不能假设它们同帧到达。UI 读取可恢复的当前结果，不等待某次历史表现事件。

> **Q：源码中保留的 CarryComponent 是否代表当前玩法有背包携带？**
>
> 不代表。它服务于保留的备用路径，当前关卡与这次 Flow 验证的是预绑定插槽的触碰归位。不将未完整验证的备用交互写成主体玩法成果。

### 4.4 会话与短线重连：把成功分成不同阶段

创建、搜索和加入使用明确操作状态限制重入；DestroySession 的后续动作区分重新建房和主动退出。回调句柄按流程解除，避免将“接口已经返回”当成“异步流程已经成功”。

加入链路为：选中当前搜索结果 → JoinSession 完成 → 解析连接地址 → ClientTravel → 本地控制器进入 PlayingState。最后一步是项目结束 Joining/重连等待的确认点，但它不保证所有复制 Actor 和 GameState 都已经可用，因此 UI 还需要自己的绑定与补读。

短线重连保存最近一次有效地址，按 JSON 间隔有限尝试，默认 1、2、4 秒。主动退出取消重试；服务器仍存活时，新连接获取现有共享目标。失败信息当前主要记录在日志中，没有增加完整重连提示 UI。

> **Q：重连成功恢复了哪些东西？**
>
> 恢复的是到原服务器的连接，以及服务器仍保存的共享进度和机关状态；不是旧 Pawn 身份、个人位置、背包或私人存档的恢复，也没有主机迁移。主机退出导致世界消失，缓存地址不能把它恢复出来。

> **Q：为什么错误处理需要区分一条连接与整个房间？**
>
> 一个客户端超时并不意味着 Listen 主机停止服务。服务器端对该类远端断开保留自己的 Session，由引擎清理对应连接；客户端丢失主机连接才决定重连或本地清理。还要按 World、GameInstance、NetDriver 过滤全局错误事件，避免处理其他实例的失败。

> **Q：同一关卡重开为什么还需要网络处理？**
>
> 旧 World 与新 World 是不同生命周期。项目需保证重开 URL 保留 listen，目标重新初始化，远端进入替换后的世界。恢复“旧世界仍存在”的加载失败分支也不等于覆盖任意崩溃、损坏资源和引擎中止。

参考实现：GameInstance（仓库路径：`Source/multiplayer/Network/multiplayerGameInstance.cpp`）、PlayerController（仓库路径：`Source/multiplayer/Player/multiplayerCoopPlayerController.cpp`）、GameMode（仓库路径：`Source/multiplayer/Core/multiplayerGameMode.cpp`）。

### 4.5 已做的优化，分别省了什么

| 措施 | 主要减少什么 | 是否已有量化 |
| --- | --- | --- |
| 机关只复制关键状态，客户端播放过渡 | 不必要的连续变换同步 | 有实现；没有单独隔离这一项的前后收益 |
| 稳定门/板网络休眠，变化前刷新休眠 | 稳定对象的复制检查 | 有静止压力板规模对照 |
| 平台 30 Hz 上限 | 持续变化对象的发送压力 | 有 100/30 Hz 合成参数对照；不是旧版本整体升级 |
| 相同状态不重复提交与广播 | 重复通知和更新调度 | 有实现；没有逐项量化 CPU 收益 |
| 到位停 Tick、客户端关闭不必要触发计算 | 无效本地计算与重叠处理 | 有实现；不能借用复制实验百分比替它计算收益 |
| GameState / UI 事件驱动并补读状态 | 不必要轮询及初始化漏状态 | 正确性设计；不夸大成独立性能实验 |

**4.5.1 静止压力板的结果**

构建 A、同机双进程、NullRHI，新增 0/50/200/500 个始终相关的压力板，两组频率上限同为 30 Hz，只改唤醒/休眠。每组 3 轮、约 30 秒采样。

500 档服务器复制作用域均值的三轮中位数从 1.210 ms 降到 0.133 ms，减少约 1.077 ms（89.0%）；每帧每连接复制调用均值的三轮中位数从约 216 降至 11。发送量仍接近背景，没有证明静止机关带宽显著下降。

**4.5.2 移动平台的结果**

同一构建新增 1/5/20 个持续运动平台，比较更新频率上限 100/30 Hz。20 档引擎发送量中位数由 12,269.3 降至 7,830.6 B/s，减少约 36.2%；复制 CPU 的三轮范围有重叠，不声称显著改善。

> **Q：为什么这些结果不能直接写成游戏性能提升？**
>
> CPU 测的是 ServerReplicateActors 作用域，不是整条 GT 或总帧时；B/s 包含背景和测试通信，是引擎发送计数，不是网卡抓包。100/30 Hz 是配置上限，本轮实际运行约 45 FPS；原生产平台已是 30 Hz。正式压力板本来为 5 Hz，实验统一设为 30 Hz 来隔离休眠变量。合成负载、参数对照和历史版本收益必须分开。

### 4.6 当前能证明的边界，和仍不知道的上限

| 维度 | 已有证据 | 不能据此推出 |
| --- | --- | --- |
| 人数 | 一名 Listen 主机玩家 + 一名远端玩家的回归 | 8 人乃至百人同时游玩已经验收 |
| 机关规模 | 500 个静止板、20 个持续平台的单变量压力档 | 完整交互关卡或更多连接下仍满足预算 |

玩法配置允许把房间人数设到 2～8，但配置范围不是经过压测的容量。500 与 20 是本次取样档位，不是测得的容量上限。旧 Ride 的平台最大横向偏移统计排除了首秒，不能将日志中的 0.0 cm 当成上平台全程零误差；新的 RideMotion 每阶段约四秒，不删除阶段开头的校正峰值，两套指标不能混用。

因此目前应表述为：**双人核心流程有自动回归，复制成本有可复核的单变量基线，但真实部署容量与有画面的弱网体验尚未完整建立。**

### 4.7 如果扩展为大型在线游戏：保留、补充和替换

以下是扩大规模时的设计讨论，不是当前项目必须补齐的清单。截至 2026-09-28，先保留现有双人玩法、网络成本对照和真实故障复盘，暂停自由跳跃的后续优化，不继续扩展 GAS 或专用服务器。复习时应能说明已完成的代码、数据适用范围和已知限制，不把设想当成果。

“大型”需要先具体化：同场人数、每人相关对象数、移动/战斗频率、服务器预算、出口带宽和目标网络条件。对象数量增加与连接数量增加会带来不同压力，不能只把同机合成机关翻倍。

**4.7.1 可以保留的原则**

服务器决定结果；状态与表现分离；所属玩家提交请求，服务器重新检查；稳定对象不做无意义更新；生命周期结束时清理订阅；测试同时观察服务器和客户端。这些原则不因规模扩大而过时。

**4.7.2 需要补充或替换的系统**

| 当前选择 | 规模扩大后的变化 | 先拿什么证据决定 |
| --- | --- | --- |
| LAN OnlineSubsystemNull | 按目标平台接入身份、房间目录、匹配和连接服务；公网可达方案独立设计 | 真实双机/公网加入、鉴权失败、版本不兼容与房间生命周期 |
| 玩家设备承载 Listen Server | 若要求公平、持续运行和集中运维，转向 Dedicated Server；局域网好友合作也可以继续 Listen | 无本地玩家运行、服务器构建与部署、峰值 Tick/内存/出口预算 |
| 默认复制调度 | 先做明确的相关性与频率预算；必要时评估 Replication Graph 或目标版本的 Iris | 按连接的相关对象、收集/比较/序列化耗时、内存与尾延迟 |
| 缓存地址的新 Pawn 重连 | 增加可信玩家身份、会话续接、旧实体接管策略、快照/持久化和请求去重 | 断线时重复请求、服务重启、恢复期限和数据一致性 |
| 简单开关过渡和普通平台位置复制 | 视体验需求补服务器时间/阶段、适当表现插值与移动基座处理 | 纠错次数/幅度、通行一致性、不同延迟下的视频与日志 |
| 低频简单 RPC | 明确权限、速率限制、请求大小、重复执行和审计；战斗按需求加入预测与命中回溯 | 非法请求不能改结果，高频请求不能拖垮服务器 |
| 单个小目标结构与局部事件 | 大型可变集合按数据特点评估增量集合复制、分页和订阅范围 | 每类属性占用与实际改动比例，而非只看总字节 |
| 同机 30 秒对照和少量回归 | 双机/多连接压测、长时间运行、异常中断、版本一致性与持续回归 | 明确的延迟/丢包/抖动、采样区间、P95/P99、资源曲线 |

> **Q：是不是直接打开 Replication Graph 或 Iris 就能变大型？**
>
> 不是。它们针对复制组织与调度等问题，不能替代玩法预算、后台服务和正确性。应先知道瓶颈是对象筛选、属性比较、序列化、带宽还是服务器模拟，再做兼容性验证。尤其本项目使用 UE 5.5，应按该版本功能状态评估；不把两个方案当作必须叠加的开关清单。

> **Q：哪些地方应该替换，而不是继续给现有代码打补丁？**
>
> 真正跨公网的身份/会话发现应替换当前 LAN 假设；需要账号级断线续玩时，应把“缓存地址重试”升级为身份与状态恢复协议；需要独立运维的权威进程时，应补 Dedicated 构建和部署。反过来，简单门状态和一次性插槽规则未必需要重写，应在新预算与场景下继续验证。

> **Q：当前最值得先补什么？**
>
> 优先补有画面双端验收、真实双机 LAN、胜利前后不同事件顺序和同一最终构建的重复性能对照。随后根据实际问题选择平台时间对齐、连接可观测性或更大规模相关性调度。没有证据前，不为堆功能而重写传输层、引入 GAS 或给普通机关增加通用回滚。

## 第五章：从玩法正确性到网络成本——一次有证据边界的复盘

返回总目录 · 上一章：项目网络方案

这次整理的主线是：规则先能正确变化，再确认远端确实看到变化；连接断了、世界重建后仍能继续；最后才讨论为了同步这些结果付出了多少成本。

下面按问题依赖组织阶段，不声称它们就是实际修改日期的先后顺序。历史静态审计发现的风险、已有防护、本轮真实故障和性能对照会分别标明；没有记录的猜测与试错过程不补写。

前六个阶段的运行环境是 UE 5.5.4、OnlineSubsystemNull、Windows Development 打包程序，同机两个独立进程运行 Listen Server 与客户端，使用 NullRHI。新增的阶段七动态载人实验使用后续编辑器构建的 `-game -NullRHI`，环境单独记录。两者能检查规则、复制与计数，不能代替有画面的游玩验收。

完整实验条件见实验报告（仓库路径：`Docs/Reports/2026-09-27/NetworkExperimentReport.md`），逐轮结果、原始日志索引与构建指纹统一放在数据附录（见文末附录；仓库路径：`Docs/Reports/2026-09-27/Appendix.md`）。本章不重新运行实验，也不将不同构建的数据拼成一次优化。

### 阶段一：先把“什么变化会影响规则”说完整

网络会把服务器结果送出去，但不会替服务器补齐遗漏的规则依赖。压力板就是一个具体例子。

**板还亮着，门的条件却已经变了**

历史审计发现：A 同时覆盖两块板，两块板都激活，但不同玩家只有一个；B 再进入其中一块，激活布尔值仍是真，不同玩家数却变成两个。如果门只订阅板的开关变化，就可能漏掉这次开门条件变化；B 离开时也可能漏关门。

根因不是复制延迟，而是事件没有覆盖完整依赖。当前实现把开关变化与占用变化分开，压力板先更新自身状态，再通知占用变化；门重新合并各板上的角色，并用集合按角色身份去重。同一个人踩两块板不算两个人。

本轮 Flow 针对这个顺序检查 `PlateDistinctPlayers`、`GateRules`，再由客户端检查 `GateOpen`、`GateClosed` 和门网格终点。三档网络均通过。源码入口是 PressurePlate::HandleOccupancyChanged（仓库路径：`Source/multiplayer/Mechanisms/multiplayerPressurePlate.cpp`） 与 CoopGate::EvaluateGateState（仓库路径：`Source/multiplayer/Mechanisms/multiplayerCoopGate.cpp`）。

> **Q：为什么不直接每帧重新统计，省去这些事件？**
>
> 条件只随占用、目标或机关状态改变，完整订阅这些变化即可。事件驱动的关键不是少发事件，而是不漏掉影响结果的输入；相同开关可以不重复通知，但人数变化不能一起丢掉。

**同一帧的重复进入，也要只登记一次**

宝物路径还有另一种风险：两名角色在同一服务器 Tick 内依次触碰同一物体，或者调用外部逻辑时同步重入。这里不是两个 CPU 线程同时写数据，而是业务入口可能被重复调用。

当前地图的宝物预绑定目标插槽。服务器收到真实 Overlap 后检查是否已安装；插槽确认归位成功后，先设置已激活状态、关闭触发碰撞，再向 GameMode 登记进度。已经完成的宝物或插槽拒绝再次提交。它不是“玩家拿到手里再搬到插槽”的演示流程。

Flow 的 `OverlapKeys` 在同一 Tick 依次放置两名角色，经过碰撞入口完成 4 个预绑定宝物归位，并检查每个插槽只增加一次进度。没有直接调用进度登记函数冒充完整拾取。代码见 CoopKey（仓库路径：`Source/multiplayer/Mechanisms/multiplayerCoopKey.cpp`） 与 KeySocket::CommitServerActivation（仓库路径：`Source/multiplayer/Mechanisms/multiplayerKeySocket.cpp`）。

**对象消失也是一种规则变化**

只在 BeginOverlap 加一、EndOverlap 减一并不完整：同一角色可能有多个碰撞体，Pawn 也可能在区域内直接销毁。弱引用失效本身不会告诉门“现在少了一个人”。

PlayerOccupancy（仓库路径：`Source/multiplayer/Mechanisms/multiplayerPlayerOccupancyComponent.cpp`） 按角色记录重叠次数，对外只按角色数计人；首次记录绑定 `OnDestroyed`，销毁时移除整条记录并发布人数变化。Flow 真正销毁仍压板的远端 Pawn，`DestroyedPawnCleanup` 检查只剩主机且门关闭，三档均通过。

这一阶段建立的是服务器规则的完整性。占用重绑定恢复已有重叠虽有实现，却没有本轮独立断言；多轮反复进出也还值得补。接下来的问题是：服务器判对了，客户端真的收到并正确消费了吗？

### 阶段二：把“服务器通过”升级为“双端通过”

服务器到达平台终点，不证明远端角色站稳了；服务器胜利，不证明客户端界面出现了。测试必须验证结果的消费者，而不只验证结果的生产者。

当前流程由两个独立进程走实际建房、搜索和加入入口。每轮带唯一 Token，日志还要匹配模式、角色、必要 ASSERT 及双端 DONE；缺失或超时不能因为某条旧日志写了 PASS 就算成功。

| 检查对象 | 不够充分的判断 | 当前增加的检查 |
| --- | --- | --- |
| 宝物 | 直接调用登记函数后进度正确 | 从真实 Overlap 进入，检查安装和一次计数 |
| 门 | 主机 `bGateOpen` 正确 | 客户端收到开关，并到达对应网格终点 |
| 平台 | 主机位移超过阈值 | 客户端解析平台、确认真实 CMC 基座，再检查载人位移 |
| 胜利 | 服务器 `bGameWon` 为真 | 远端收到胜利，真实 Widget 已加入 Viewport |
| 压测负载 | 主机生成了配置数量 | 客户端确认对象类型、数量、唯一引用及平台已移动 |

载人测试本身也暴露过配置错误：合成平台默认由外部压力板激活，但测试没有绑定板，因此它不移动。正确处理是在完成生成前明确选用“自身占用激活”，而不是修改正式平台规则让测试变绿。

另一个边界是对象到达时序。服务器生成平台后，客户端不一定立刻拥有可用引用。测试先等待客户端解析平台、确认站立基座，再进入运动检查，不能用任意延迟猜测已准备好。

这些变化见 CoopNetTestScenarios（仓库路径：`Source/multiplayer/Testing/CoopNetTestScenarios.cpp`） 与 CoopNetTestDriver（仓库路径：`Source/multiplayer/Testing/CoopNetTestDriver.cpp`）。它们属于验证工具的修正，不应全部记作玩法代码故障。

> **Q：自动断言越多，就越接近完整游玩吗？**
>
> 只有断言回答了目标问题才有价值。Widget 加入 Viewport 不等于像素显示正确，更不等于按钮实际被点过；服务器摆放角色触发 Overlap，也不覆盖玩家按键和全部关卡摆放。

双端验证把一般玩法连接起来后，完整流程继续走到了“胜利后重开”。这里出现的不是测试配置问题，而是一个真实的网络生命周期故障。

### 阶段三：同一张地图重开，为什么监听服务器消失了

首次完整打包 Flow 已通过宝物、门、载人和胜利检查，到了重开，客户端却无法回到主机。原始失败记录保留在 `package-flow-normal`，没有被后来的通过结果覆盖。

根因是两份状态没有一起延续：建房用 `World::Listen` 让当前 World 原地监听，但没有同步更新引擎保存的 `FWorldContext.LastURL`；`RestartGame` 的 `?Restart` 又会重新读取 LastURL。地图仍是原地图，`listen` 选项却丢了，新 World 退回单机。

修复只发生在合法的 Listen Server 重开前：向当前 WorldContext 的 LastURL 保留 `listen`，再重载当前地图。没有增加自动选图，也没有靠增加客户端重试次数掩盖主机已经不监听的事实。

具体入口见 GameMode::RequestRestartCurrentRound（仓库路径：`Source/multiplayer/Core/multiplayerGameMode.cpp`），原地监听见 GameInstance::EnsureCurrentWorldIsListening（仓库路径：`Source/multiplayer/Network/multiplayerGameInstance.cpp`）。

**原理补充：地图名相同，不代表运行对象相同**

重开会替换 World，并带来 GameMode、GameState 和连接状态的重新建立。Session 保存房间信息，NetDriver 承担网络连接，URL 保存加载选项，它们不是同一个对象，也不会自动拥有完全相同的生命周期。

因此只检查“再次加载了同一地图”不够，还要看新世界是否仍监听、目标是否归零、客户端是否真正进入新世界。

最终三档 Flow 的 `Restart` 与 `ClientRestart` 都通过，覆盖上述新世界与重新入场条件。首次重开失败的恢复分支也通过了开发故障注入检查，但这不证明所有损坏地图或引擎中止比赛都能原地恢复。

> **Q：为什么不直接重新调用一次建房来解决？**
>
> 当前需求是保留这局房间并重载当前关卡。先定位丢失的是加载选项，修复这个边界即可；重新创建 Session 会额外改变房间生命周期，不能拿它代替对原因的解释。

重开能恢复连接之后，仍有一个更隐蔽的问题：连接成功是否意味着房间也还正常？下一阶段的真实断包测试说明，两者不能画等号。

### 阶段四：重连成功了，但 Session 可能已经被删掉

初版断包测试观察到客户端用缓存地址重新连接成功，报告通过。进一步核对主机超时日志和错误处理链发现，服务器自己的 Session 已被清理。监听 World 仍能接受连接，因而“直连成功”遮住了“房间记录消失”。

根因是失败影响范围判断过宽：引擎也会向服务器报告单个远端客户端的 `ConnectionTimeout`；旧逻辑把它当成整个主机联网失败，执行全局会话清理。

修复后，服务器收到远端连接丢失或超时，只记录日志并保留房间，由引擎处理对应连接与 Pawn。客户端是否重连则按客户端自己的状态处理。代码位于 GameInstance::HandleNetworkFailure（仓库路径：`Source/multiplayer/Network/multiplayerGameInstance.cpp`）。

同时，验收条件增加 `HostSessionRetained`：检查 Session 仍存在、仍是主机、广告开关仍开启，且房间 Token 属于本轮。连接恢复与会话保留分开检查，不再用一个成功条件代替另一个。

最终 Reconnect 的三个网络档位均通过这些断言。主机在测试中施加 12 秒的 100% 入站与出站丢包，并把连接超时缩短到 5 秒；等待引擎真实报告断线，再恢复传输。它不同于直接调用一个失败回调来模拟断线。

恢复的是保留主机世界中的共享进度。客户端建立新连接和新 Pawn，不是恢复旧角色身份、位置或私人存档，也不包含主机迁移。

> **Q：房间记录和广告配置仍在，能说玩家一定重新搜索得到吗？**
>
> 还不能。本轮新增断言没有再完整运行一遍断线后的搜索菜单。下一步应由真实客户端重新搜索并加入，最好在两台机器上验证，同时保留双方日志。

这一阶段最重要的修正不只是一个条件分支，而是补全了“成功”的定义。规则、消费端和恢复流程有了明确检查，才能继续衡量复制成本；否则更低的发送量可能只是房间或连接坏了。

### 阶段五：状态不变，为什么静止机关还消耗复制 CPU

现在可以把正确性与压力负载分开测试。静止实验只增加压力板：0、50、200、500 个，新增平台固定为 0；两组更新频率上限同为 30 Hz，只改变保持唤醒或网络休眠。

每组至少预热 5 秒、采样约 30 秒、独立运行 3 轮。客户端确认实际负载后才开始采样，合成对象强制网络相关、关闭交互碰撞，背景地图不变。这是复制压力对照，不是正式关卡支持多少机关的容量证明。

下面每个数字都是三轮统计值的中位数，CPU 只取 `Exclusive/GameThread/ServerReplicateActors` 作用域。

| 新增压力板 | 唤醒复制均值 ms | 休眠复制均值 ms | 每帧每连接复制调用：唤醒 → 休眠 |

**原理补充：不发数据，不等于不做检查**

属性没有变化时，保持唤醒的对象仍可能进入复制相关检查。网络休眠让稳定对象避开这类反复处理；对象状态要改变时，再按需要刷新。它与关闭 Actor Tick 是两层机制，关 Tick 不会自动停止复制检查。

门与压力板在修改复制属性前先 `FlushNetDormancy`，再提交状态、更新本机表现并请求 `ForceNetUpdate`。这样不只减少静止检查，也为后续状态变化保留正确入口；ForceNetUpdate 不是保证远端立刻收到的同步屏障。

结果没有显示静止机关带宽显著降低：发送计数仍约 1.8～2.0 KB/s，500 档休眠组还略高。状态不变时本来就很少发送属性，因此这里应讲复制 CPU，而不是套用同一个百分比去讲带宽、整条 GT 或 FPS。

> **Q：0 个新增机关时，休眠标签组为什么反而更慢？**
>
> 两组此时没有新增负载差异，六轮复制均值仍在 0.0805～0.1231 ms 波动，体现测量噪声和顺序漂移。小差异不能直接算优化；500 档差距远大于本轮背景波动，但仍不是跨硬件统计结论。

正式压力板原本为 5 Hz，实验两组都设为 30 Hz 以隔离休眠变量，所以这不是一次“历史正式版本前后提升 89%”。本轮静止系列 24/24 通过；远端门切换与激活压力板晚加入也有回归，更多激活—复位循环仍待补。

静止对象的主要收益落在检查 CPU；下一步自然转向另一个模型：位置不断变化的平台，成本是否主要体现在发送量？

### 阶段六：降低平台频率上限，代价是否只是少发字节

运动实验固定新增压力板为 0，分别加入 1、5、20 个持续往返平台，只比较更新频率上限 100 Hz 与 30 Hz。每组同样三轮，预热至少 5 秒、采样约 30 秒，共 18 轮。

**图表 6｜运动平台数量与发送量。**下表给出图像中的引擎发送计数；单独图片文件：`figures/02-moving-platform-bytes.png`。100/30 Hz 是设置上限，B/s 包含背景流量。

| 新增平台 | 100 Hz 上限：引擎发送 B/s | 30 Hz 上限：引擎发送 B/s | 发送计数减少 |
| ---: | ---: | ---: | ---: |
| 1 | 2436.7 | 2186.4 | 10.3% |

20 档三轮发送量范围为 12158.0～12295.6 B/s 和 7821.3～7858.9 B/s，支持降低频率上限减少了本场景的发送计数。复制 CPU 均值范围却有重叠，本轮不声称得到显著 CPU 收益。

B/s 来自 `OutTotalBytes` 增量除以实际采样秒数，包含背景与测试通信及配置的包头开销，不是平台独占字节、成功送达量或网卡抓包。进程实际约 45 FPS，100/30 Hz 只是上限设置，不能写成实际每秒发送 100/30 次。

生产平台在本轮前已经使用 30 Hz。100 Hz 是人为构造的压力基线，这次验证频率选择的成本，不是把正式旧版本从 100 Hz 改到 30 Hz 的历史优化。

**省下发送量之后，还必须检查乘客**

此前构建 B 的三档 Flow 与三档 Ride 共 6 次站立载人检查均通过，每次记录 46/46 个有效基座样本。最大横向相对偏移在进入 Ride 阶段 1 秒后才开始统计，该统计段记录为 0.0 cm（日志精度），不包含上平台阶段和 Ride 首秒。

实际通过门槛并非必须零误差：有效基座占比至少 70%、统计段最大横向偏移小于 100 cm、角色 X 位移超过 250 cm，同时等待平台进入终点 3 cm 容差且 Ride 超过 5 秒。这是一组逻辑检查，不是画面质量标准。

当前平台由服务器运动，使用普通 Actor Movement Replication；没有自行实现平台预测、回滚或自定义平滑。角色沿用 CharacterMovement 的既有机制，不能把角色机制写成平台也具备同一套预测能力。

> **Q：既然载人通过，还需要保留哪些怀疑？**
>
> 此前这组检查中玩家是在平台上站立。走动、起跳、换向、上平台首段及弱网下肉眼可见的抖动都未被这组指标完整覆盖；没有对应证据前，不应继续盲目降低频率，更不能宣称任意运动下零误差。下面的动态载人实验正是为补其中一部分缺口，不是把旧断言重新命名为全面通过。

还有一个有意保留的能力边界：平台是固定轨道机关，Scene 根无碰撞，承载网格是子组件。当前显式不 Sweep，由关卡保证轨道不穿墙，没有实现遇障停止、绕行或挤压。载人通过不能替它证明自动避障；取舍见 Transporter（仓库路径：`Source/multiplayer/Mechanisms/multiplayerTransporterComponent.cpp`）。

至此得到两类局部成本证据，但“降低发送成本”与“乘客动作正常”仍是不同问题。接下来不继续压低频率，而是让角色真正走动、起跳，检查网络数据与运动规则能否配合。

### 阶段七：平台能载人，不代表角色跳起后还能落回

**先把动作纳入测量，而不是只检查平台终点**

新增 `RideMotion` 场景依次运行站立、横向行走、平台换向、起跳落回。客户端逐帧提交真实移动输入，继续经过 CMC 的预测与服务器验证；服务器和客户端分别观察升空、落地和基座，不由服务器在动作阶段传送角色。

每段双端各采样约四秒，采样放在 `TG_PostPhysics`，等待平台和角色完成本帧运动。不删除开头峰值；指标在采样截止时冻结，最终“仍站在平台”与换向位置则在阶段完成检查时读取，不声称所有断言严格对应同一帧。

测试使用带校正记录的专用 CMC 派生角色，读取关卡实际蓝图角色的行走速度、跳跃速度、空中控制、摩擦和制动参数，并同步给测试双方。它不是完整蓝图角色、摄像机和动画的验收，但也不能靠给测试 Pawn 单独设置更有利参数来掩盖实际玩法配置。

**第一层原因：平台比角色更新得晚**

Transporter 沿用普通组件的 `TG_DuringPhysics`，而 CMC 在 `TG_PrePhysics` 更新。角色识别出运动基座，不代表较晚 TickGroup 的组件会被基座依赖自动提前。

处理是将平台移动放入 `TG_PrePhysics`，配合 CMC 的基座更新依赖。没有每帧再附着一次角色，也没有写第二套代码额外搬动角色。这个顺序问题可由引擎源码确认，但单独贡献多少抖动改善，本轮没有拆成独立实验量化。

**第二层原因：位置在动，基座速度却是零**

`SetActorLocation` 不会替该移动方式维护完整的根组件速度。站着跟随主要依靠基座变换，起跳离开却还需要读取基座速度；只验证前一种行为会漏掉后者。

服务器改为用实际位移除以帧时间更新根组件 `ComponentVelocity`，停下时清零；客户端在 `PostNetReceiveVelocity` 中把已有运动复制携带的线速度写回根组件。普通 Actor 的默认接收路径并不会替当前非物理 Scene 根完成这一步。起动、反向、停止时请求网络更新，不增加逐帧 Reliable RPC。

**新问题：已经继承速度，为什么仍落不回？**

修好顺序和速度后，正常网络下跳跃仍然失败。这提示问题不只是丢包或延迟。

**图 7｜移动平台、角色基座和空中制动的依赖链。**下方文字流程是可直接导入 Notion 的版本；单独图片文件：`figures/05-platform-ride-mechanism.png`。

```text
离开运动基座，进入 Falling
    → ApplyImpartedMovementBaseVelocity：继承平台水平速度
    → PhysFalling / CalcVelocity：继续计算空中运动
    → 没有水平输入，BrakingDecelerationFalling = 1500 执行制动
    → 继承的水平速度很快消失，平台仍继续移动
    → 角色落到平台后方
```

平台速度为 150 cm/s，制动为 1500 cm/s²，理想化估算约 0.1 秒即可刹停。项目选择无输入起跳时保留水平惯性，因此将实际角色的空中制动改为 0；空中方向调整继续使用 `AirControl`。这会影响普通跳跃的手感，是运动规则取舍，不应包装成网络带宽优化。

同一构建通过模式恢复指定旧行为，正常网络下的客户端速度对照如下，速度单位为 cm/s：

| 模式 | 平台顺序与速度 | 空中制动 | 起跳前基座速度 | 离地首帧 / 约 0.25 秒后水平速度 | 落回平台 |
| --- | --- | ---: | ---: | --- | --- |
| Baseline | 旧顺序，不补速度 | 1500 | 0 | 0 / 0 | 否 |
| OrderedVelocity | 修复顺序及双端速度 | 1500 | 150 | 125 / 0 | 否 |
| PlatformInertia | 保留平台修复 | 0 | 150 | 150 / 150 | 是 |

125 已包含该帧的制动。前两种模式均记录双端跳跃失败，状态保留 `failed`；“失败符合预期”不等于把原报告改成成功。这也说明增加平台发送频率不能直接解决角色自行刹停的问题。

**功能通过以后，仍然要看校正有多大**

当时采用的 `PlatformInertia` 在 Normal、Moderate、Harsh 各运行一次，双端四段动作全部通过；另有正常网络下的一次原 `Flow` 回归通过。每档一次是功能证据，不是可靠性成功率，也不是性能收益统计。

> **Q：三档动作通过，是否说明弱网平台已经完全修好？**
>
> 不能。上表的 13 次、72.12 cm 是早期运行结果，不是已测得的屏幕拉回距离。后续已经按同一 Move 找到平台状态差异参与起跳、落地误差的证据，但尚未完成自由跳跃修复。平台在客户端的离散更新仍可能造成世界空间跳变，相对平台位置为零不能证明镜头平滑。当前没有关闭服务器校正或放大容差来制造通过。

> **Q：这轮是否实现了平台预测回滚？**
>
> 没有。角色预测、校正和 Move 重演仍由 CMC 提供，平台仍使用 Actor 运动复制。本轮解决的是更新顺序、速度数据和运动规则配合；平台快照插值、统一时间轴或自定义预测需要另做设计与验证。

**后续定位：速度相同，起跳轨迹仍然可能分叉**

2026-09-27 的追加实验已记录客户端 SavedMove 与服务器处理记录，用 `MoveTimeStamp` 唯一配对，不直接相减两端的 World 时钟。Harsh 这一轮的关键证据如下，位置单位为 cm：

| 同一 Move | 客户端平台 X / 服务器平台 X | 角色状态与观察 |
| --- | --- | --- |
| 15.04216，起跳前 | 30788 / 30872.23 | 两端相对平台 X 均为 0，但世界位置已相差约 84.23 |
| 15.05883，离开基座 | 30788 / 30872.23 | 两端角色水平速度均为 150 cm/s；世界位置差约 84.23，并记录到相近大小的校正误差 |
| 16.48552，落回平台 | 31004 / 31079.06 | 两端角色世界 X 相同，但相对平台 X 分别约为 83.97 / 8.91，差约 75.06 |

```text
同一条 Move 在两端处理时，使用的平台状态不同
    → 站立时可以有相同的局部位置，却有不同的世界位置
    → 自由起跳切换到世界空间后，差异进入空中轨迹
    → 落地重新建立基座时，世界位置差与基座相对差再次转换
    → CMC 校验发现不一致，客户端收到纠正并重放后续输入
```

这支持“移动基座状态差异参与大幅校正”的解释，不证明差异全部来自复制频率，也不等于测得了单向延迟。两端记录的是**各自处理同一 Move 时**的快照，不是同一物理时刻。Normal 起跳曾出现约 7 cm 误差，而平台 X 差几乎为零；这部分仍不能用上述水平位置差全部解释。

**追加对照：发得更勤、保留基座和关闭平台运动**

| 实验 | 网络 / 频率上限 | 运行数 | Jump 校正次数 | 最大可比较误差 cm | 能说明什么 |
| --- | --- | ---: | --- | --- | --- |
| 自由跳跃，同 Move 定位 | Normal / 30 Hz | 1 | 2 | 7.00 | 正常网络仍有小残差 |
| 自由跳跃，同 Move 定位 | Moderate / 30 Hz | 1 | 8 | 40.01 | 已取得双端状态快照 |
| 自由跳跃，同 Move 定位 | Harsh / 30 Hz | 1 | 10 | 84.23 | 大误差与关键 Move 的平台位置差对应 |
| 自由跳跃，提高频率 | Harsh / 60 Hz | 3 | 11、13、13 | 64.56、79.47、77.46 | 提高上限没有消除大幅校正，不据此精确计算改善率 |
| AirBase，空中保留基座 | Harsh / 30 Hz | 1 | 4 | 11.08 | 改变了运动规则，不能算自由跳跃修复；已否决并撤回接入 |
| 自由跳跃，静止平台 | Harsh / 30 Hz | 1 | 0 | 0 | 本次平台逐帧位移为 0，双端完成升空和落地；不代表运动平台已解决 |

以上 8 个案例的自动断言均通过，但不是同一构建的完整 A/B，也不是 8 次同条件重复。原始报告与模块指纹见文末附录 H。三种网络档的两端模拟参数分别为 0/0/0、100/20/2、200/50/5（延迟 ms / 波动 ms / 丢包 %），不称为实测 RTT。

AirBase 的 4 次校正里，只有一次记录了 11.08 cm 的位置误差，其余三次为 0；该次误差的 X 分量为 0，而当时尚未拆出 Y/Z。因此既不能说画面拉回了四次，也不能直接断定剩余误差全是跳跃高度差。平台在空中仍影响角色运动本身就不符合设计要求，否决原因是**玩法约束**，不是这组数字不够好。

最后一次静止对照前已恢复正式角色的标准 CMC，并将测试快照扩展为 XYZ、速度、移动状态和 Move 模拟时长。该轮没有追加位置 RPC，没有采纳客户端权威速度，也没有放宽校正容差。静止对照沿用四阶段脚本，其中换向阶段平台仍静止，不能把它当作新的实际换向验收。零校正只是这次采样的观察结果；尚未用新三维记录完成同构建的运动平台重复对照。

**表现验收与原因定位必须分开**

| 层面 | 应看什么 | 不能混用的指标 |
| --- | --- | --- |
| 本地玩家体验 | 输入响应、镜头拉扯、起跳和落地是否突跳 | 历史 Move 误差不等于屏幕拉回距离 |
| 另一玩家看到的角色 | 同一个角色与平台是否连贯、有无穿插或突然移位 | 同一墙钟时刻的位置差可能包含正常显示滞后 |
| 计算与网络时序 | 同一 Move 的位置、速度、基座、运动模式和步长 | 不直接相减未对齐的客户端与服务器本地时间 |

当前拓扑是一名 Listen 主机玩家和一名远端客户端，不是两名独立远端客户端。后续若做表现验收，需要同时看两个玩家窗口，并分别记录胶囊、模型和平台位置；模型平滑和镜头表现不能由 Actor 坐标替代。现有 NullRHI 专用测试 Pawn 没有完成这部分验收。

> **Q：位置偏移到底是物理问题还是网络问题？**
>
> 不是简单二选一。已有证据更支持：网络与处理时序让两端使用了不同的平台状态，移动计算再把这份初始差异传播到轨迹。平台是代码沿固定轨道移动，角色由 CMC 处理运动和碰撞，不是在验证两个 Chaos 自由刚体是否确定性一致。仍需区分初始位置、速度、起跳时机、步长和碰撞状态，不能只凭“弱网时明显”就宣布全部原因已找到。

> **Q：直接发送客户端起跳速度，服务器验一下大小就接受，能保证轨迹一致吗？**
>
> 不能。即使速度完全相同，初始位置不同也会产生不同轨迹；时间推进和碰撞条件还会继续影响结果。本次已经有水平速度相同、位置相差约 84 cm 的记录。速度上限只限制幅度，不能证明起跳资格、次数、方向或平台来源合法。若确需增加移动状态，应接入 SavedMove、移动数据序列化和重放规则；`ServerMoveHandleClientError` 是服务器模拟后的误差处理入口，不是客户端跳跃 RPC。本项目未采用客户端决定最终起跳速度的方案。

> **Q：是否必须回滚整个世界，才能解决平台跳跃？**
>
> 不必预先作此结论。平台历史查询是一个候选方向，但 CMC 的 Move 时间戳不是直接可用的服务器绝对时间，时间映射、历史范围、版本变化和重放一致性都需要设计。只临时挪回平台、算一次速度再恢复，并不等于完整碰撞世界已回滚，也不能保证完全同步。本项目尚未实施该方案。

> **Q：调小 MaxSmoothNetUpdateDist 就能让误差不可见吗？**
>
> 不能这样理解。UE 5.5 中它用于限制网络平滑的网格偏移距离，并非“小于阈值就不修正碰撞体”的开关；调小也不等于更柔和。`NetworkSmoothingMode` 主要用于远端代理的表现路径，不应当作本地玩家预测重放的通用修复。应先查模拟差异，再独立验证胶囊、模型和镜头，不能用视觉平滑宣称权威碰撞已一致。

截至 2026-09-28，后续优化暂停。当前可复述的结论是：已经修复更新顺序、基座速度传递和空中制动问题；已定位移动基座状态差异参与弱网跳跃校正，完成了频率及静止对照；**自由跳跃弱网拉扯尚未完成修复，双端视觉也未验收**。不是“全部归因于初速度”，也不是“已实现平台预测回滚”。

专项复现入口为 `Scripts/RunMultiplayerNetworkTests.ps1 -Scenario RideMotion`，三种模式通过 `-PlatformSyncMode` 选择；默认回归 `All` 不会自动包含此专项。完整条件见实验总报告（仓库路径：`Docs/Reports/2026-09-27/NetworkExperimentReport.md#5-问题三平台载人通过后走动与跳跃为什么仍可能失败`），双端阶段指标与失败对照见附录 G（见文末附录；仓库路径：`Docs/Reports/2026-09-27/Appendix.md#g-动态载人专项编辑器构建`）。

### 阶段八：不把所有绿色结果拼成“全部完成”

正式性能和最终正确性不是同一构建。A→B 新增主机超时错误处理保护、对应测试断言，并修正计数说明文字；机关复制与采样算法没变，但数据归属依然必须分开。

| 证据 | 构建 | 实际用途 |
| --- | --- | --- |
| 42/42 正式性能轮次 | A | 静止 24 轮与运动 18 轮，各组 3 次，用于上面的成本对照 |
| 15/15 最终正确性案例 | B | 5 种模式 × 3 档网络 × 每档 1 次，保留 156 条 ASSERT 与双端 DONE |
| 4/4 最终短验收 | B | 500 板两种设置、20 平台两种频率，各 1 次、预热 2 秒、采样 8 秒 |
| 3/3 动态载人最终场景、2 个失败控制组、1 次 Normal Flow 回归 | 后续编辑器构建，见阶段七指纹 | 动作与根因对照，不等于再次完成上述 15/42/4 验证矩阵 |

4 轮短验收只证明最终程序还能生成、复制和采样负载，不与正式三轮数据混算。15 个案例中的三个网络档位也不是同条件重复三次，不能从中推导低概率故障率。

Normal、Moderate、Harsh 的两端模拟参数依次为 0/0/0、延迟 100 ms / 波动 20 ms / 丢包 2%、200 ms / 50 ms / 5%。这些是设置，不是测得的 RTT。首次建房失败和首次重开失败是开发注入，与真实丢包超时分开记。

此前构建 B 的 Development 打包运行、Shipping 编译通过，蓝图检查 96 个对象，其中 `/Game` 下 17 个，0 错误、0 警告、0 加载失败。它们仍不能证明所有资产摆放和 UI 操作正确，也不是新增平台修复后的重新打包记录。

**仍需单独验证的两个时序**

**胜利通知同步重入。** 如果玩家先在终点，最后一个宝物随后完成，进度委托可能同步触发胜利并嵌套更新 GameState。当前 CoopGameState（仓库路径：`Source/multiplayer/Core/multiplayerCoopGameState.cpp`） 在广播前保存快照和本次胜利转换，避免外层再次读取被内层改变的成员而重复通知。

这是历史静态审计已有修复；本轮 Flow 先完成宝物再进入终点，没有专门制造上述反向顺序，也没有统计胜利广播次数。普通胜利通过不能代替该专项。

**GameState 晚到或监听建立得晚。** 当前 VictoryPresenter（仓库路径：`Source/multiplayer/UI/multiplayerVictoryPresenterComponent.cpp`） 拿不到 GameState 时等待 World 就绪事件，绑定后再补读当前胜利状态，结束时清理订阅。普通远端 Widget 已通过，但没有强制 GameState 延迟到达；LateJoin 只验证目标和压力板，不是胜利后加入的 UI。

> **Q：为什么事件监听之外还要补读当前值？**
>
> 监听负责以后发生的变化，补读负责订阅前已经成立的状态。两者解决不同时间窗口；有了这份设计仍要制造相应时序验证，不能仅凭代码存在就宣布覆盖完成。

复现还需要匹配构建、源码与配置。实测基于 dirty 工作区，单独检出基础 commit 不够；hash 能检查文件是否一致，却不能还原缺失的源码。`GameThreadTime` 原始列全零也按不可用保留，没有改写成“GT 为 0 ms”。原始数据与限制均见附录（见文末附录；仓库路径：`Docs/Reports/2026-09-27/Appendix.md`）。

### 已知限制与可选续做：当前暂停，不是必须立即增加的任务

以下是现有证据仍未覆盖的方向，不计入已通过结果，也不要求全部完成后才能展示项目。当前先复习已实现的状态同步、生命周期治理、实验设计和取舍；若恢复开发，按具体问题选择其中一项，不重新跑已回答过的实验。

1. **补特殊顺序。** 先入终点再完成目标，强制延后 GameState 绑定，胜利后再加入；分别记录双方胜利通知次数和本地界面状态。
2. **补真实操作。** 有画面跑双人通关、点击重开和退出；平台四段自动动作已经覆盖，下一步验证镜头、动画、普通跳跃手感与首段过渡，保存视频并对齐日志。
3. **补双机网络。** 用同一构建在两台机器验证搜索、加入、真实网络中断和恢复后的再次搜索；公网另列网络条件，不能用同机结论替代。
4. **补最终版性能。** 在同一最终构建交错运行单变量 A/B，每组至少 3 轮，保留散布；不与构建、其他压测同时争用资源。
5. **继续自由跳跃定位，而非重新开始。** 同 Move 核对、60 Hz 三轮和静止平台单轮已经完成。若恢复，使用已补齐的 XYZ、速度和模拟时长记录完成同构建静止/运动对照，解释残差并验收空中反向、边缘脱离；不再试已否决的空中保留基座，不以客户端权威速度或关闭校正制造通过。
6. **有问题再细分流量。** 若总发送量确实成为约束，再按 Actor 与属性分析字节来源；未量出问题前，不引入通用世界回滚或更复杂复制架构。

这条主线最终回答的不是“加了多少功能”，而是：规则是否完整、远端是否消费、失败是否影响了不该清理的状态、成本是否来自受控变量，以及现有证据究竟能支持多大的结论。

**B.4 从逐轮值复算正文**

- 每组按照 matrix、数量、optimization 分组，各有 3 轮，取三个均值的中位数；P95 一列同样取三个 P95 的中位数。
- 500 板均值：`(1.209885 - 0.132682) / 1.209885 × 100% = 89.0335%`；绝对差 `1.077203 ms`。
- 20 平台发送量：`(12269.252 - 7830.583) / 12269.252 × 100% ≈ 36.1772%`；计算时使用 JSON 全精度值。
- 500 板发送量不是减少：休眠组相对唤醒组约增加 1.7%，不声称存在带宽收益。
- 0 板没有新增负载，两种设置的复制均值仍波动，甚至休眠标签组更高；不能概括为“所有档位都改善”。
- 原构建 A 的 counterSource 写有 `wire packets`，措辞过强。真实口径是引擎发送缓冲字节及配置的包头开销，不是网卡实抓流量；原记录未改写，构建 B 只修正说明文字。

### F. 构建 A/B 的解释边界与验收空白

- 本节 A/B 批次为同机双进程、NullRHI，非双物理机、公网或专用服务器；后续 D 专项也为同机 NullRHI，但使用另一编辑器构建。
- 合成机关关闭交互碰撞且始终网络相关，数量不是正式关卡容量结论。
- 属性状态和 Widget 入 Viewport 的通过，不能证明菜单按钮操作、像素显示、平台视觉平滑与门碰撞过渡都正确。
- 未强制 GameState 晚到，未专测胜利通知嵌套重入次数，未验收胜利后晚加入的界面。
- 发送量是整个被测服务器对其连接的引擎计数，不是平台独占字节，不证明成功送达或网卡实际流量。
- 3 轮性能样本保留散布但样本量有限，且按组执行存在时间漂移；不作跨机器显著性与玩家容量承诺。
- 数据中的初次回归、历史失败与最终结果一并保留，不修改旧记录让报告更好看。
