# Co-op 项目讲解：协作规则、GAS 生命周期与恢复

面向游戏客户端初级岗位：先讲客户端为何需要预测和本地表现，再讲哪些结果必须由服务器提交；不把所有复杂性概括成“处理了很多边界”。

## 1. 项目介绍

基于 UE5.5、C++ 与蓝图实现双人合作闯关，包含机关协作、波次敌人、技能战斗和撤离。使用独立服务器与双客户端，重点是联机状态一致性、GAS 准入/提交/取消和断线后的有限状态恢复。

与 FPS 的区别：FPS 重点讲逐发武器事务、群体资源和性能归因；本项目重点讲持续效果、技能替换、预测失败与会话恢复，不把同一套框架包装成两个亮点。

## 2. 模块边界与数据驱动

| 模块 | 拥有的状态 | 消费方式 |
| --- | --- | --- |
| GameMode | 对局规则、正式接纳、重开、服务器恢复票据/快照 | Controller 发请求，服务器校验并提交 |
| GameState | 共享进度与结果 | 客户端订阅后补读当前快照 |
| GameInstance | 地址连接、取消、有限重试与网络失败归属 | 不裁决生命、机关或技能 |
| 机关 Actor / Occupancy | 压力板成员、门/钥匙业务状态 | 服务器提交，客户端播放过渡 |
| Character / ASC / GA | 输入协调、能力状态、预测上下文与任务 | 通过原生 GAS 激活、Commit 和 End |
| AttributeSet / GE | 生命、能量、护盾及效果结算 | 属性事件驱动 HUD，不复制第二套血量 |
| Progression / Coop | 成长配装、倒地与救援 | 不替 GA 结算投射物或范围伤害 |

战斗 Data Asset 保存技能基础数值、动画/Cue 资源和能力关系；有效规则在基础配置上应用技能等级。机关及实验 JSON 使用完整校验和失败回退。蓝图绑定真实表现事件，不另写扣费、伤害和判胜。

当前 ASC 与属性集在 Character 上。重连重建 Pawn 后显式恢复白名单状态，不声称 PlayerState 常驻、任意 GE 存档或跨服迁移。一个 Character 的方法分多个 cpp 是实现文件组织，不等于拆成了多个独立组件。

## 3. 亮点一：机关同步的是状态，不是历史动画

```text
服务器 Overlap → 占用组件去重并验证玩家资格
  → 机关/合作门提交状态 → GameState 更新进度
  → RepNotify/委托 → 客户端动画与 HUD
晚加入/换绑定 → 补读当前状态，而非等待以前的广播重播
```

- 按有效玩家而不是 Overlap 次数统计，处理多组件、倒地、销毁和离开区域。
- 静止机关网络休眠，改变前唤醒；门/压力板传状态，客户端演出，不可靠多播不承担持久事实。
- 移动平台的基座速度、更新阶段和角色起跳必须与 CMC 配合。角色和平台分别平滑仍可能有相对误差，不能一句“开插值”就认定解决。
- 历史平台专项按同一 Move 时间戳配对客户端/服务器记录，区分是否站在同一基座、何时校正、跳跃惯性与复制频率。历史结果不冒充本轮专项重测。

源码：[机关](../Source/multiplayer/Mechanisms/)、[对局](../Source/multiplayer/Core/multiplayerGameMode.cpp)、[网络设计](NetworkDesign.md)。

## 4. 亮点二：能力规则只有一条链

```text
本地按住预览（不扣费、不复制）
  → 确认输入/方向 → 真实 AbilitySpec 的 CanActivateAbility
  → 原生 GAS 预测激活；服务器按同一上下文独立准入
  → Commit 本轮成本与冷却 → 起手任务 → 服务器出手/GE 结算
  → EndAbility 结束任务、动画及临时施法状态
```

- 预览和正式准入复用真实能力条件，不在 HUD 另写成本/冷却判断；正式提交仍复核当时状态。
- Data Asset 的能力关系接入 GAS 原生 required/blocked/block/cancel，不另存一套 bool 动作锁。
- 相同语义的能量消耗合并成一个成本 GE；伤害、治疗、防御等语义不同的效果不硬合成万能类。
- 普攻弹体、R 圆柱范围与遮挡、正面格挡/弹反均由服务器重建和结算；客户端只提供意图。
- 冲刺使用 GAS RootMotionSource 和 CMC；不是客户端自行改位置，也不是用 Root Motion 掩盖网络错误。
- 取消已提交技能不自动退款，更不回滚已经造成的伤害；持续效果是否结束由其所有权和规则决定。

源码：[输入/业务条件](../Source/multiplayer/Combat/multiplayerCombatCharacter.cpp)、[ASC 关系适配](../Source/multiplayer/Combat/multiplayerCombatAbilitySystem.cpp)、[能力与效果](../Source/multiplayer/Combat/multiplayerCombatAbility.cpp)、[选点](../Source/multiplayer/Combat/multiplayerCombatTargeting.cpp)。

## 5. 亮点三：预测键、激活版本和效果句柄不互相替代

| 真实问题 | 对应处理 | 为何只用 IsActive 不够 |
| --- | --- | --- |
| Commit/标签/动画通知同步取消并重启同一能力 | 跨回调边界复核激活版本 | 新激活也是 Active，旧调用栈仍可能继续 |
| 旧预测拒绝到达时同资产新动画已开始 | 预测键与播放身份限定清理归属 | 只按动画资产停播会停掉新动作 |
| 多个效果都限制移动，先结束一个 | 保留各 GE/标签的有效状态 | 某个技能不能直接把全局状态写回允许移动 |
| 范围遍历中发生死亡/销毁/配置变化 | 本轮规则快照 + 逐目标实时资格复核 | 快照不能替代目标此刻仍合法的检查 |

保护只放在能触发外部回调或异步完成的边界，不把每次普通 Getter 包成事务。项目是在 GAS 原生生命周期上补业务归属，不是自研预测、线程安全框架或全局事件总线。

例子：R 起手期间被眩晕 → 当前任务取消、未出手则不产生伤害；随后重新释放 R → 新激活接管任务；旧动画/任务晚到不能清理或结算新一轮。由真实能力、动画和取消回归验证，不仅靠序号比较的单元测试。

## 6. 亮点四：恢复当前状态，不重播离线过程

```text
地址连接 → 当前 Controller 握手 → GameMode 验证服务器票据
  → 校验配装/恢复位置 → 重建支持的生命、资源和效果状态
  → 扣除离线时间，补算支持的持续伤害/倒地超时
  → 成功才接纳并轮换票据 → 客户端就绪并补读共享状态
```

恢复失败不会消费原凭证并把默认新生冒充恢复成功。只覆盖仍在运行的同一服务器/本局、120 秒保留窗口与持有票据的客户端；半次普攻、冲刺、救援和旧回调不恢复。服务器重启、账号持久化和任意 GE 反序列化不在范围内。

“丢包/乱序/重复/抖动”的回答要分层：原生可靠通道与属性复制负责各自协议保证；业务仍要处理不同 Actor/RPC/属性之间无全局顺序、重复请求及过时操作。机关保存持久状态，技能复核权威条件，预测失败只清理对应请求，连接超时有限重试；不重写 UDP 或为每个消息新增可靠重发器。

## 7. 可验证结果与边界

- 2026-10-24 完整 Automation 174/174，0 测试警告/失败；Editor、Shipping 原生编译通过。
- 同轮 Combat、CombatLifecycle、CombatExpansion、CombatReconnect 的 Normal/Harsh 各一轮，共 8/8 通过；24 个 UE peer 正常退出、0 强杀。
- Harsh 三端设置 PktLag=200、Variance=50、Loss=5，不作为实测 RTT。专项在 CombatTest、NullRHI，验证取消、拒绝、弹反、救援和存活/倒地/死亡恢复，不是正式图画面和通关。
- 没有新的整局帧率/带宽收益、完整冷启动特效、公网或新发布包验收。历史机关 89.0% CPU、平台 36.2% 发送量等必须带原规模、拓扑和统计对象讲。

详细机制见 [GAS 调用链](Study/GAS架构与调用链.md)，测试入口、原始失败和本轮记录见 [Tests](../Tests/README.md)。
