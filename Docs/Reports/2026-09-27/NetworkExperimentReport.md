# Co-op 网络实验总报告

整理日期：2026-09-27。本文合并规模压测、玩法弱网回归和动态平台载人实验。逐轮数据、构建指纹与证据索引见[附录](Appendix.md)；具体故障的发现与修复见[踩坑报告](ProjectPitfalls.md)。本文仅整理已有记录，没有重新编译或运行游戏。

## 1. 先说结论

已有实验分别回答三个问题：稳定机关和持续运动对象的网络成本是什么；双人玩法在模拟弱网和连接失败时能否完成；角色在运动平台上站立、走动、换向、跳起后能否落回。它们不是同一次构建、同一种测量环境，不能合并为一个通过率。

| 问题 | 已有结果 | 结论边界 |
| --- | --- | --- |
| 多个静止机关没有状态变化，还会不会消耗复制 CPU？ | 500 个新增压力板，休眠前后复制作用域平均耗时的三轮中位数由 1.210 降至 0.133 ms | 休眠明显减少这类对象的复制检查；不是整个游戏快了 89% |
| 持续移动的平台降低更新频率上限，是否减少发送量？ | 20 个新增平台，100/30 Hz 对照由 12,269.3 降至 7,830.6 B/s | 本条件下引擎发送计数减少约 36.2%；不等于网卡流量或视觉质量已经验收 |
| 优化及失败恢复是否破坏双人流程？ | 构建 B 的 15/15 回归与 4/4 短压测验收通过 | 覆盖指定自动断言，不代表全部 UI、真实 LAN 或长期稳定性 |
| 平台能载人后，走动和跳跃也正确吗？ | 后续编辑器专项中，最终方案在三档网络各完成一次双端四阶段动作；两个旧行为对照均在跳跃失败 | 动作闭环通过；Harsh 跳跃仍有 13 次校正和最大 72.12 cm 可比较误差，不代表画面平滑 |

正文只放问题、设计、关键结果和下一步；原始报告与逐轮表格留在附录，不在多篇正文反复抄写。

## 2. 实验设计

### 2.1 为什么静止与运动要分开测

静止机关和移动平台不是同一种负载。前者关注“没变的时候是否仍然反复检查”；后者关注“位置持续变化时发送多少”。将两个变量一起改，会无法判断收益来自哪里。

| 实验 | 想验证的问题 | 施加的负载 | 只改变的参数 | 固定条件 |
| --- | --- | --- | --- | --- |
| S：静止机关 | 不变的状态是否仍有复制检查成本？ | 原地图上新增 0、50、200、500 个压力板 | 保持唤醒 / 网络休眠 | 新增平台为 0；两组压力板频率上限都为 30 Hz |
| M：运动对象 | 更新频率上限对持续位置复制有什么影响？ | 原地图上新增 1、5、20 个往返平台 | 更新频率上限 100 / 30 Hz | 新增压力板为 0；运动方式与背景相同 |
| R：正确性 | 并发交互、晚加入、断线和重开是否正确？ | 一名主机玩家与一名远端玩家 | Normal / Moderate / Harsh 网络档位 | 构建 B，同一套断言 |
| D：动态载人 | 走动、换向、起跳和落回是否正确？ | 一个水平运动平台与真实网络移动的测试角色 | 旧行为 / 修复顺序与速度 / 最终惯性规则 | 后续编辑器构建，30 Hz 平台上限 |

数量是用于看出成本曲线的压力阶梯，不是“支持 500 名玩家”或“最多 20 个平台”的容量承诺。0 档用来观察原地图背景与测量波动；中间档检查趋势；最大档放大差异。运动对象每次都可能产生新位置，因此无需与静止机关使用相同数量。选择这些档位不意味着已找到性能上限。

### 2.2 环境与版本

- 全部使用 UE 5.5.4、OnlineSubsystemNull、同机两个独立进程（Listen Server 主机与客户端），均使用 NullRHI，不渲染画面。
- 本机为 i7-14650HX、约 64 GB 内存、Windows 11 25H2。双进程会争用同一台机器的资源。
- 地图：`/Game/Stylized_Egypt/Maps/Stylized_Egypt_Demo`。主机从合作地图启动，建房原地监听；没有增加自动选图功能。
- S/M 正式性能使用 Windows Development 打包构建 A；R 回归和短验收使用后续打包构建 B。D 动态载人专项使用更晚的 `multiplayerEditor Win64 Development`，从编辑器以 `-game -NullRHI` 启动。三批指纹见附录。

A→B 增加了主机处理远端超时的保护、对应断言并修正计数器说明；机关复制与采样算法未变，但 42 轮正式对照没有在 B 上重跑。D 的平台与角色修复发生得更晚，不能借用 A/B 的百分比称为这些修复的性能收益。历史实测基于 dirty 工作区，单凭基础 commit 不能重建相同二进制。

### 2.3 怎样保证测到的不是空负载

自动脚本启动双方，调用真实 Session 创建、搜索和加入入口。主机生成合成机关后，客户端必须收到实际对象，并确认对象数量、唯一引用及所有平台已移动至少 5 cm，才能进入采样。

每组预热至少 5 秒、采样约 30 秒、重复 3 轮：静止系列 4 档 × 2 设置 × 3 轮 = 24 轮；运动系列 3 档 × 2 设置 × 3 轮 = 18 轮，共 42 轮。采样结束再检查负载。平台“曾移动”的标记不能单独证明每秒更新次数或采样全程的轨迹质量。

合成机关强制网络相关、关闭交互碰撞，避免碰撞或距离剔除混入对照。因此它是复制压力实验，不是把真实关卡扩到相同规模后的完整玩法测试。

脚本按组依次执行，没有随机交错。后续应交错 A/B 顺序来减少温度、后台负载与时间漂移影响。

### 2.4 规模实验测什么，怎么算

| 指标 | 来源与算法 | 不能替代什么 |
| --- | --- | --- |
| 复制 CPU 均值 / P95 | 服务器 CSV 的 `Exclusive/GameThread/ServerReplicateActors`；每轮分别求均值、nearest-rank P95 | 不是整条 Game Thread，也不是总帧时 |
| 引擎发送 B/s | `OutTotalBytes` 在采样段的增量 ÷ 实际采样秒数 | 不是网卡抓包或成功送达量，含背景通信与配置的包头开销 |
| 每帧每连接复制调用、休眠数 | 同一 CSV 的 Replication 计数器 | 不是实际成功发送的属性次数 |
| 运行帧节奏 | CSV 的 `FrameTime`，以 `1000 / 平均帧时` 估算 | NullRHI 下不是有画面的渲染 FPS |

正文表格取每组三轮统计值的中位数；“P95”一列是三轮 P95 的中位数，不是合并所有帧后重新计算。原始 `GameThreadTime` 列全零，判为不可用，不能写成 GT 没有成本。

## 3. 问题一：静止机关也要反复做复制检查吗？

### 实测结果

下表“复制耗时”只指上面定义的复制作用域。频率上限保持一致，只有休眠设置不同。

| 新增压力板 | 唤醒均值 / P95（ms） | 休眠均值 / P95（ms） | 复制调用（唤醒 → 休眠） | 发送 B/s（唤醒 → 休眠） |
| ---: | ---: | ---: | ---: | ---: |
| 0 | 0.092 / 0.204 | 0.120 / 0.247 | 11.04 → 11.06 | 1931 → 1868 |
| 50 | 0.199 / 0.493 | 0.128 / 0.253 | 31.71 → 11.10 | 1890 → 1850 |
| 200 | 0.504 / 1.270 | 0.120 / 0.253 | 93.65 → 11.09 | 1879 → 1875 |
| 500 | 1.210 / 3.222 | 0.133 / 0.269 | 215.98 → 11.08 | 1848 → 1879 |

500 档平均耗时中位数减少约 1.077 ms，即 89.0%。三轮均值范围为唤醒 1.168～1.309 ms、休眠 0.121～0.136 ms；同时休眠对象数由背景的 7 个变成 507 个，复制调用降回接近背景，几个指标互相印证。

### 这个结果说明什么

“没有新属性需要发送”不等于“复制系统完全不检查对象”。对象规模增加时，保持唤醒的检查成本持续增长；休眠让稳定对象退出这部分反复处理。

本实验没有证明静止机关的带宽明显下降：发送量仍在约 1.8～2.0 KB/s 的背景附近，500 档休眠组甚至略高。状态没变，本来就很少发属性。本次主要收益在复制检查 CPU，而非发送字节。

0 档没有新增对象，两组本应没有负载差异，六轮均值却在 0.0805～0.1231 ms 间波动。这说明不能看到小幅变化就宣称优化有效；500 档差距远大于本次控制组波动，但仍不是跨硬件统计结论。

### 已落地与未覆盖

门与压力板在稳定时休眠，服务器在改变复制属性前 `FlushNetDormancy`，再写状态并请求更新。Flow 已检查休眠后的远端门开关与网格终点；LateJoin 检查既有目标进度和激活压力板。

Flow 已检查门打开、关闭、再次打开以及 Pawn 销毁后的占用清理；不是没有测过重复开关。仍缺高次数切换与胜利后晚加入的定向验证。正式压力板原本为 5 Hz，本实验两组都使用 30 Hz；89.0% 是合成参数对照，不能直接当正式关卡或历史版本收益。

## 4. 问题二：平台是否需要很高的复制频率？

### 实测结果

| 新增平台 | 100 Hz 上限发送 B/s | 30 Hz 上限发送 B/s | 发送计数下降 | 复制均值（100 → 30，ms） |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 2436.7 | 2186.4 | 10.3% | 0.148 → 0.137 |
| 5 | 4499.6 | 3414.2 | 24.1% | 0.189 → 0.159 |
| 20 | 12269.3 | 7830.6 | 36.2% | 0.254 → 0.231 |

20 档三轮发送量范围分别为 12158.0～12295.6 B/s、7821.3～7858.9 B/s，两个区间没有重叠。复制 CPU 均值范围则有重叠，不能凭三轮就宣称 CPU 显著改善。

### 这个结果说明什么

平台持续运动会产生新位置，降低频率上限能减少发送计数。对象越多，背景固定开销占比越小，这项差异越容易观察。

但是，100/30 Hz 是设置的上限，不是实际发送次数。本次进程实际约 45 FPS，不能说“每秒 100 次降成了 30 次”。生产平台在本轮以前已经使用 30 Hz，100 Hz 是人为施压基线，不是一次真实旧版本升级。

### 已落地与后续动作验证

继续使用服务器驱动位置、Actor Movement Replication 同步的简单方案，没有加入自研预测回滚。最终构建 Flow 与 Ride 共 6 次载人检查通过，每次 46/46 个有效基座样本。横向偏移在进入 Ride 阶段 1 秒后开始统计，该统计段的最大值为日志精度下的 0.0 cm，不包含上平台阶段与 Ride 首秒。

这批构建 B 的 Ride 只证明角色站立在平台上的被测条件。后续已经增加走动、换向与跳跃专项，结果见第 5 节；不能再把“尚未测试这些动作”当作待办。载人专项仍没有渲染画面，也没有证明降低频率后的视觉质量，因此不继续盲目降低频率。

## 5. 问题三：平台载人通过后，走动与跳跃为什么仍可能失败？

### 实验设计

原 Ride 场景只验证“站着跟平台移动”。后续 D 专项复用真实 Session、平台业务类和 CMC 网络移动路径，让测试角色连续完成站立、横向行走、平台换向、起跳并落回。每段约 4 秒，主机与客户端分别采样和断言；运动中不传送角色，也不由服务器替客户端写行走位置。测试 Pawn 读取实际关卡角色的五项关键移动参数，但不是完整的角色蓝图、相机与动画。

专项在 Normal（0 ms / 0 ms / 0%）、Moderate（100 ms / 20 ms / 2%）、Harsh（200 ms / 50 ms / 5%）下运行，数字是两端分别配置的延迟、波动和丢包参数，不是实测 RTT。主对照的平台复制频率上限为 30 Hz，不代表每秒实际收到 30 次更新。三种模式使用同一个测试构建中的开关恢复指定旧行为，不等于重建历史版本的所有条件：

| 对照模式 | 平台顺序与基座速度 | 角色空中制动 | Normal 跳跃结果 |
| --- | --- | ---: | --- |
| Baseline | 旧更新顺序，未补根组件速度 | 1500 cm/s² | 双端失败，起跳前基座速度为 0 |
| OrderedVelocity | 平台改为 PrePhysics，并补服务器与客户端基座速度 | 1500 cm/s² | 双端失败；起跳前已有 150 cm/s，约 0.25 秒后水平速度降为 0 |
| PlatformInertia | 保留上述平台修复 | 0 cm/s² | 双端通过；起跳前和约 0.25 秒后水平速度均为 150 cm/s |

### 排查中发现的三层原因

1. **更新顺序**：平台运动组件原先晚于 CMC 所在的 PrePhysics 更新。将平台组件调至 PrePhysics，使基座位移先进入角色本帧移动，而不是给角色额外做一套附着或搬运。
2. **位置不等于速度**：`SetActorLocation` 挪动非物理根组件，不保证 CMC 起跳时能读到正确的基座速度。服务器按实际位移更新根速度；客户端从复制运动中接收速度并写回根组件。开始、反向、停下时请求网络更新，但不增加逐帧 Reliable RPC。
3. **继承后又被制动**：补好速度后，旧的 `BrakingDecelerationFalling=1500` 仍会迅速消掉继承的平台水平惯性。最终选择把实际玩法角色的空中制动调为 0，允许从运动平台原地起跳后保持水平速度。这是玩法手感取舍，不是带宽优化；普通跳跃手感仍需真实画面验收。

Baseline→OrderedVelocity 同时包含顺序与速度修复，不能拆出各自的收益百分比。OrderedVelocity→PlatformInertia 则说明修好平台数据后，旧空中制动仍足以让跳跃失败；不能把所有掉落都归咎于网络丢包或低发送频率。

### 实测结果与测量口径

两个旧行为对照各跑一次 Normal，均为前三段通过、跳跃失败；最终方案在 Normal、Moderate、Harsh 各跑一次，四段的主机与客户端断言均通过，另有一次 Normal 的原 Flow 合作流程回归通过。单次通过不是稳定性成功率。[逐阶段指标、失败原值及证据索引](Appendix.md#g-动态载人专项编辑器构建)放在附录。

| 最终方案的跳跃阶段 | 客户端校正次数 | 最大可比较校正误差 | 动作结果 |
| --- | ---: | ---: | --- |
| Normal | 2 | 4.75 cm | 双端起跳并落回 |
| Moderate | 8 | 43.68 cm | 双端起跳并落回 |
| Harsh | 13 | 72.12 cm | 双端起跳并落回 |

校正误差以 CMC 对应的历史 `LastAckedMove` 为参照：同基座时比较基座局部位置，双方均不依赖动态基座时比较历史世界位置；基座不一致单独计数。不能拿客户端**当前**位置减历史服务器位置。采样在 PostPhysics，避免读取到不同帧阶段的角色和平台坐标；阶段采样结束时冻结校正统计，防止回执等待时间混入。校正次数包含误差为零的校正，72.12 cm 也不是屏幕拉回距离。站立阶段相对平台位移为零，不等于平台世界位置或相机画面平滑。

三档运行的实际帧节奏不同（Normal/Moderate 约 44～45 FPS，Harsh 约 60 FPS），且每档只有一次，不能仅凭表中差异断言“丢包导致校正增加”的定量关系。专项使用编辑器 NullRHI；它验证动作与 CMC 校正记录，没有证明真实角色蓝图的视觉平滑、两台机器的体验或这组修复的 CPU／带宽收益。当前没有自研角色预测回滚或平台快照插值。

### 后续定位与频率对照（2026-09-29 更新）

同一 Move 的双端记录已经将关键起跳/落地校正关联到平台位置差；关键起跳的水平速度一致，不能再简单归因于未继承平台速度。随后在当前构建中完成 Harsh 30/60 Hz 各三轮、交错顺序的频率实验：两组校正次数中位数同为 12，每轮最大可比较误差的中位数分别为 67.16 / 76.54 cm。全部动作通过并正常退出，但未显示提高频率能稳定解决大校正。因此保留正式平台 30 Hz，下一步验证运动段与角色 Move 的时间一致性。

这六轮不是旧版 100/30 Hz 带宽实验的重跑，也不是新同步方案已经落地。条件、解释边界见[Move 时间戳专项](PlatformMoveTimestampValidation.md#后续验证提高平台复制频率能否解决大校正2026-09-29)，源数据见[附录 I](Appendix.md#i-平台频率与跳跃校正对照2026-09-29)。

## 6. 问题四：双人玩法与失败恢复是真的走通了吗？

最终构建 B 完成 5 种模式 × 3 档网络 × 每档 1 次，共 15/15 通过，保留 156 条 ASSERT 与每例双端 DONE。这里的三档网络不是同条件重复三次，不能据此估算低概率失败率。

| 模式 | 本轮检查结果 | 明确没有检查的内容 |
| --- | --- | --- |
| Flow，3/3 | 真实 Overlap 宝物归位、一次计数、不同玩家门规则、远端门表现、销毁占用 Pawn、载人、胜利界面加入 Viewport、失败后重试重开、新世界入场、双方退出 | 玩家按键与按钮点击、所有蓝图摆放、画面像素 |
| LateJoin，3/3 | 新客户端读取既有目标进度和激活压力板 | 胜利以后才加入的 UI |
| Reconnect，3/3 | 真正丢包超时、主机会话记录保留、恢复通信后新连接读取共享进度 | 旧 Pawn 身份/位置恢复、主机迁移、断线后再次完整搜索 UI |
| SessionRetry，3/3 | 注入一次建房失败，回收本次新监听，重试后成功加入 | 所有线上服务故障或平台 SDK 行为 |
| Ride，3/3 | 客户端真实 CharacterMovement 基座、位移与横向偏移 | 行走、跳跃、视觉平滑及障碍挤压 |

两端网络模拟参数分别为 Normal：0 ms / 0 ms / 0%；Moderate：100 ms / 20 ms / 2%；Harsh：200 ms / 50 ms / 5%，依次代表延迟、波动、丢包。它们不是测量得到的 RTT。

Reconnect 在主机端临时设置 100% 入站/出站丢包 12 秒，并将测试连接超时缩短为 5 秒，等待引擎真正报告断线后恢复网络。SessionRetry 和 Flow 的首次重开失败则是开发故障注入，二者不能都称为自然故障复现。

本轮实际发现并修复了两个闭环问题：原地建房后重开遗漏 `listen`，新世界退回单机；单个客户端超时误清理主机 Session，导致“直连成功但房间记录消失”。处理过程详见[踩坑报告](ProjectPitfalls.md)。

## 8. 复现入口

完整命令与参数见 [Tests/README.md](../../../Tests/README.md)。以下是各类实验的运行入口；执行会重新启动游戏，并非本次文档整理已经再次执行：

```powershell
$gameExe = '你的 Development 包/Windows/multiplayer/Binaries/Win64/multiplayer.exe'
.\Scripts\RunMultiplayerNetworkTests.ps1 -Suite Regression -Scenario All -Profiles Normal,Moderate,Harsh -Repeat 1 -OutageSeconds 12 -TimeoutSeconds 120 -GameExecutablePath $gameExe
.\Scripts\RunMultiplayerNetworkTests.ps1 -Suite Scale -Matrix All -Repeat 3 -WarmupSeconds 5 -SampleSeconds 30 -TimeoutSeconds 120 -GameExecutablePath $gameExe
# 后续动态载人专项需显式选择 RideMotion；默认 Regression/All 不包含它。
.\Scripts\RunMultiplayerNetworkTests.ps1 -Suite Regression -Scenario RideMotion -Profiles Normal,Moderate,Harsh -Repeat 1 -PlatformSyncMode PlatformInertia
```

动态载人历史记录使用编辑器二进制，不能在上面两条打包运行命令后默认继承 `$gameExe` 的结果。先完成相应构建，再运行一套测试，不与编译或其他压测并行。复现旧结果还需匹配附录中的构建、源码与配置指纹；仅检出记录中的 commit 不够，因为实测基于未提交工作区。
