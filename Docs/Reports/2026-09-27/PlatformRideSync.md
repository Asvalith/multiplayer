# 弱网下的移动平台：从站得住到走得动、跳得回

日期：2026-09-27。配套：[网络实验总报告](NetworkExperimentReport.md) · [项目踩坑报告](ProjectPitfalls.md)。

> 本轮修复平台更新顺序、运动基座速度和空中制动规则。最终方案在三档网络下各完成一次双端动作检查，原合作流程单次回归通过；两个旧行为对照均在跳跃阶段失败。较差网络下仍记录到 72.12 cm 的最大可比较校正误差，因此结论是“动作流程通过”，不是“弱网已经完全平滑”。

## 1. 本轮要解决什么问题

原来的载人测试证明了角色站在平台上时能够跟随移动，但没有覆盖在平台上走动、平台反向、起跳和落回。这些动作会改变角色与平台之间的关系，不能由“站着通过”推导出“所有载人玩法都正常”。

本轮保持现有合作玩法，不增加射击模式，不改成专用服务器，也不重写角色移动系统。目标是检查：

- 平台移动与角色更新的顺序是否正确。
- 平台位置、速度和角色脚下的运动基座是否一致。
- 角色起跳后能否按照既定玩法保留平台带来的水平速度。
- 延迟、波动和丢包下，服务器与客户端是否都观察到真实行走、跳跃和落地。

这里的“同步优化”包括修复错误的数据与更新顺序，不预先承诺降低带宽或消除所有视觉抖动。

## 2. 实验怎样设计

### 2.1 环境与范围

- UE 5.5.4，Windows，同机两个独立进程，分别作为 Listen Server 主机和远端客户端。
- 通过项目原有 Session 创建、搜索和加入路径建立连接，不用两个单机世界代替真实联网。
- 自动测试默认使用 NullRHI，设置运行帧率上限为 60；帧上限不是实际每帧耗时保证。
- 主机生成一个固定水平轨道平台，平台实际移动、碰撞和网络复制仍使用项目业务类。
- 服务器生成并接管测试角色，只在搭建阶段设置初始位置。运动过程中不传送角色，不用服务器直接写位置模拟玩家行走。
- 测试角色使用派生 CMC 观察校正，移动预测、服务器校正与输入重演仍由原引擎实现。
- 测试从关卡实际生成的角色读取最大行走速度、跳跃速度、空中控制、空中摩擦和空中制动，并把这些关键参数同步给测试双方。它不是完整克隆蓝图角色的所有资产和配置。
- 当前主对照使用平台更新频率上限 30 Hz。它不是客户端恰好每秒收到 30 次位置的保证。

本轮最终运行环境为编辑器 `-game -NullRHI`，不是 Development 打包验收。此前的打包回归与性能矩阵属于不同轮次，不能将其环境和通过次数套用到本轮。

### 2.2 四个连续动作

客户端先确认已经接管测试角色，并且角色的真实运动基座就是测试平台，主机才开始运动。

| 阶段 | 实际行为 | 主要检查 |
| --- | --- | --- |
| 站立 | 不输入移动，让平台载着角色前进 | 保持平台基座，平台确实移动 |
| 行走 | 客户端逐帧提交横向往返输入，再留出停止后的观察时间 | 两端都观察到相对平台的真实横向位移，且未掉出平台 |
| 换向 | 服务器让正在运动的平台返回起点 | 平台确实沿反方向移动，角色仍以它为基座 |
| 跳跃 | 平台再次前进；客户端发起一次跳跃，停止按住跳跃，观察落地 | 明显向上离地、进入下落、落回平台，结束时仍站在平台上 |

每段采样约 4 秒，按实际累计帧时间截止，不人为删除开头的校正峰值。客户端输入在每帧末尾提交，由下一帧 CMC 消费，不用测试驱动的低频轮询代替持续输入。

服务器与客户端各自采样，并各自判断动作。阶段命令也经过网络，因此双方采样窗口并非精确对齐的同一段服务器时间，不能直接把两份逐帧位置按行相减。

### 2.3 网络档位

| 档位 | 两端分别配置的 `PktLag` | `PktLagVariance` | `PktLoss` |
| --- | ---: | ---: | ---: |
| Normal | 0 ms | 0 ms | 0% |
| Moderate | 100 ms | 20 ms | 2% |
| Harsh | 200 ms | 50 ms | 5% |

这是施加到两个进程的模拟器参数，不是抓包测出的 RTT，不能把 Harsh 简写成“实测 200 ms 网络”。本轮也没有模拟公网 NAT、真实拥塞、带宽整形或移动网络切换。

### 2.4 三种对照模式

| 模式 | 平台更新与速度 | 角色空中制动 | 用来回答什么问题 |
| --- | --- | --- | --- |
| `Baseline` | 恢复旧的较晚 Tick；不补平台根组件速度 | 显式恢复旧值 1500 | 旧方案在动态载人动作下有什么问题 |
| `OrderedVelocity` | 平台改为 PrePhysics；补齐服务器速度和客户端接收速度，关键状态变化请求网络更新 | 保持旧值 1500 | 修好平台数据与顺序后，为什么起跳仍可能失败 |
| `PlatformInertia` | 保留上述平台修复 | 使用实际玩法角色配置；本轮确认的目标为 0 | 在保留空中惯性的玩法规则下，载人动作是否正确 |

这些模式在同一测试构建中恢复指定旧行为，不是宣称重建了历史版本的全部环境。`Baseline → OrderedVelocity` 同时包含一组相关修复，不能用该对照单独计算 Tick 顺序或速度修复各自贡献多少；`OrderedVelocity → PlatformInertia` 则用于进一步区分空中制动的影响。

模式开关只用于显式动态载人实验。普通玩法不通过测试开关切换网络策略。

## 3. 排查过程：为什么不是改一次就结束

### 3.1 先补测试，发现过去的通过范围太窄

最初的验证只检查是否站在平台上以及是否随平台前进。角色起跳时会离开基座，落地时重新建立基座；这一条路径根本没有被覆盖。

因此本轮先增加四段真实动作，并同时验证服务端结果。测试的目的不是让已有断言继续变绿，而是暴露原来没有进入的分支。

### 3.2 问题一：平台比角色更晚更新

源码检查发现，Transporter 继承 `UActorComponent`，没有显式设置 TickGroup，沿用引擎默认的 `TG_DuringPhysics`；CMC 的移动更新则在 `TG_PrePhysics`。

UE 会为站在运动基座上的角色建立更新依赖，但基座 Actor 上较晚 TickGroup 的组件不会被这一条依赖自动提前。因此，“角色已经识别出脚下平台”并不代表“平台一定先移动，角色再跟随”。

处理：把 Transporter 放到 `TG_PrePhysics`，让它符合 CMC 的运动基座依赖条件。没有让角色每帧额外附着到平台，也没有自行再搬动一遍角色。

这是可以由源码确认的顺序问题，但它对具体画面抖动的影响仍需结合有画面的实验，不能只凭静态阅读承诺消除抖动。

### 3.3 问题二：平台位置在动，报告的速度却可能是零

平台通过 `SetActorLocation` 改变位置，但这不等于自动维护根组件的 `ComponentVelocity`。角色站着跟随平台时主要看基座变换；起跳离开时还要读取基座速度，这两条路径需要的数据不同。

处理分成两端：

1. 服务器按本帧实际位移除以帧时间更新根组件速度，到达终点并停 Tick 时清零。
2. 平台已有的 `RepMovement` 包含线速度；客户端在 `PostNetReceiveVelocity` 中接收并写回根组件速度。

为什么客户端也要处理？当前平台使用非物理的 Scene 根，UE 5.5 的普通 Actor 默认接收函数不会替这一结构填好组件速度。CMC 从承载网格读取不到速度时，会回退到 Actor 根速度。

开始、反向和真正停下时请求网络更新，帮助关键变化尽快进入复制调度；这仍不是“立刻保证送达”，也没有增加逐帧 Reliable RPC。

### 3.4 修完两项，起跳为什么还是落不回？

中间运行暴露了新的问题：站立、行走和换向的动作检查已经可以通过，但跳跃仍可能失败，正常网络下也能出现。起跳前读取到平台速度，不能证明这份速度会一直保留到落地。

继续沿引擎调用链查看：

```text
角色进入 Falling
    → ApplyImpartedMovementBaseVelocity：把平台速度加入角色 Velocity
    → PhysFalling：更新空中水平速度
    → 没有空中输入时，CalcVelocity 执行制动
    → BrakingDecelerationFalling = 1500 迅速消掉继承速度
    → 平台继续前进，角色落到平台后方
```

以平台速度 150 cm/s、制动 1500 cm/s² 作理想化估算，约 0.1 秒即可刹停，水平前移只有约 7.5 cm。这个计算用于解释量级，不是实测结果。跳跃期间平台还会继续前进，因此双方即使完全按相同规则执行，也可能一起掉落。

`FormerBaseVelocityDecayHalfLife` 不是此次直接原因。它涉及 Root Motion 覆盖时的辅助基座速度处理，不能看到“速度衰减”几个字就修改它。本项目测试角色没有因此需要自定义 Root Motion 网络方案。

最终玩法选择：无输入起跳时保留平台带来的水平惯性，方向调整继续交给 `AirControl`。确认这一选择后，项目 Character 的 `BrakingDecelerationFalling` 改为 0，而不是只给测试 Pawn 单独调成 0 来通过测试。

这是一次玩法运动规则修正，不应包装成网络带宽优化。它也会改变普通地面起跳后松开方向键的手感，需要回到真实关卡检查。蓝图若保存了旧覆盖值，修改 C++ 默认值未必会替它覆盖；所以测试从真实角色读取配置，并在双方应用、报告实际值。

## 4. 测量本身也需要防止误判

### 4.1 在同一个帧阶段采样

若在 CMC 更新前读取角色位置，却读取到平台更新后的坐标，相减得到的“相对跳变”可能只是采样顺序错误。

本轮采样放在 `TG_PostPhysics`，等待平台和角色完成本帧移动。输入仍逐帧提交，只是由下一帧消费，不通过改变 CMC 的校正规则来获得好看的数据。

### 4.2 校正距离不能拿当前角色位置减历史服务器位置

服务器校正针对某个已发送的历史 Move，而角色现在通常已经继续移动。把当前角色位置与这份历史位置相减，会把正常前进也算成错误。

观测组件在 `OnClientCorrectionReceived` 中读取 CMC 已确认的对应 `LastAckedMove`：

- 双方对应同一运动基座时，将服务器校正位置还原成基座局部坐标，与该 Move 的 `SavedRelativeLocation` 比较。
- 双方均不依赖动态基座时，比较该 Move 保存的世界坐标。
- 起跳、落地等导致基座不一致时单独计数，不在缺少历史基座变换的条件下伪造精确世界距离。

计数包括已接受但位置误差为零的校正，因此“收到几次校正”不等于“画面出现几次明显拉回”。服务器不接收这类客户端校正，其对应字段不适用，不能与客户端计数直接相加。

采样段结束时冻结校正计数和距离，防止等待驱动下一次轮询的时间混进四秒窗口。最终基座与换向位置断言仍在阶段完成检查时读取，服务器还需等待客户端回执；准确说法是“四秒采样，阶段完成检查时仍在平台”，不是所有验收状态都严格冻结在第四秒。

### 4.3 下落再落地，不一定是成功跳跃

只检查出现 `Falling` 后重新站上平台，短暂失去基座又落回也可能误通过。本轮还要求相对平台有明显向上高度变化，并分别检查客户端跳跃动作和服务器看到的升空、落地。

同时保留离地初期和约 0.25 秒后的水平速度，用于区分“没有继承速度”和“继承后被玩法制动消掉”。后者不是简单增加平台发送频率就能解决的。

### 4.4 位移指标不等于视觉质量

`maxRelativeStepCm` 是角色相对平台的逐帧三维位移。行走和跳跃本身就会增大它，不能将不同动作阶段的最大值统一叫作“网络抖动”。`maxPlatformStepCm` 记录本地平台位置变化量，也不能替代镜头、骨骼和动画的实际观感。

因此报告保留阶段、采样帧数、最大帧间隔、基座情况和校正范围，不只放一个最大位移数字。

## 5. 最终实测结果

### 5.1 功能与失败对照

每组只运行一次，用于定位原因与功能回归，不是稳定性成功率统计，也不能据此计算性能提升百分比。

| 模式 | 网络档位 | 完整通过 / 运行次数 | 双端站立 / 行走 / 换向 / 跳跃 | 自动导出的证据 |
| --- | --- | ---: | --- | --- |
| Baseline | Normal | 0 / 1 | 通过 / 通过 / 通过 / 失败 | [旧行为对照](../../../Tests/Evidence/2026-09-27/PlatformRide/baseline.json) |
| OrderedVelocity | Normal | 0 / 1 | 通过 / 通过 / 通过 / 失败 | [顺序与速度修复对照](../../../Tests/Evidence/2026-09-27/PlatformRide/ordered-velocity.json) |
| PlatformInertia | Normal | 1 / 1 | 全部通过 | [三档最终记录](../../../Tests/Evidence/2026-09-27/PlatformRide/inertia.json) |
| PlatformInertia | Moderate | 1 / 1 | 全部通过 | 同上 |
| PlatformInertia | Harsh | 1 / 1 | 全部通过 | 同上 |

两个控制组确实产生 Host 和 Client 的 `MotionJump=false`，报告保留 `failed`，没有因“符合预期”而改成成功。最终三档均有双方 `DONE passed=true` 和 `MotionServerObserved`。另外，正常网络下执行一次原 `Flow` 合作流程回归，结果通过，见 [回归证据](../../../Tests/Evidence/2026-09-27/PlatformRide/flow-regression.json)；它不等于重跑旧有全部回归矩阵。

正常网络下的客户端速度对照如下，速度单位为 cm/s：

| 模式 | 起跳前基座速度 | 离地首帧水平速度 | 离地约 0.25 秒后水平速度 | 空中制动 | 落回平台 |
| --- | ---: | ---: | ---: | ---: | --- |
| Baseline | 0 | 0 | 0 | 1500 | 否 |
| OrderedVelocity | 150 | 125.00 | 0 | 1500 | 否 |
| PlatformInertia | 150 | 150 | 150 | 0 | 是 |

这组结果说明：补齐基座速度确实让起跳取得平台惯性，但原制动会迅速把它消掉。首帧的 125 已包含该帧制动，不代表平台只传来了 125。最终三档双方报告的空中制动均为 0，客户端起跳前基座速度和约 0.25 秒后的水平速度均为 150；不是只在测试客户端偷偷改参数。

| Normal | 行走 | 179 / 179 | 0 | 0 | 12 | 1.80 |
| Normal | 换向 | 176 / 176 | 0 | 0 | 11 | 0 |
| Normal | 跳跃 | 178 / 114 | 2 | 4.75 | 12 | 19.13 |
| Moderate | 站立 | 181 / 181 | 0 | 0 | 18 | 0 |
| Moderate | 行走 | 181 / 181 | 2 | 1.76 | 17 | 2.87 |
| Moderate | 换向 | 182 / 182 | 0 | 0 | 17 | 0 |
| Moderate | 跳跃 | 181 / 116 | 8 | 43.68 | 16 | 43.68 |
| Harsh | 站立 | 240 / 240 | 0 | 0 | 15 | 0 |

| Harsh | 跳跃 | 240 / 155 | 13 | 72.12 | 23 | 65.12 |

本轮上述记录的 `comparableCorrections` 与校正次数相同，`baseChangeCorrections` 均为 0；这不是保证其他运行的基座切换都能比较。Host 对应校正字段不适用，未拿服务器的 0 与客户端比较。完整双端 24 段指标保存在最终 JSON 中。

结果同时暴露了仍未解决的问题：

- 无输入站立时相对位置可以保持不变，但平台本身仍通过离散位置更新前进；相对位移为 0 不等于世界空间或镜头平滑。
- 跳跃在较差网络下虽然落回了平台，仍出现 13 次校正、72.12 cm 的最大可比较误差；它不是已测得的屏幕拉回距离，也不能忽略。
- 同机运行的实际采样节奏不同，Normal/Moderate 约 44～45 帧/秒，Harsh 约 60 帧/秒。不能把其中某项下降单独归因于更好的网络处理；需要固定运行条件、增加重复次数后再作定量对照。

## 6. 这轮能证明什么，不能证明什么

根据最终双端断言，可以在对应条件内说明：自动提交的真实客户端移动输入经过 CMC 的预测与服务器验证路径，平台能够承载角色完成指定动作；平台速度与角色空中规则的配合得到针对性检查。

仍然不能由本轮直接声称：

- 自研了角色预测回滚。角色预测、校正和 Move 重演仍来自 CMC。
- 实现了平台快照插值、平台独立预测或整个世界的历史回滚。当前平台仍采用服务器移动加 Actor 位置复制。
- 弱网画面已经完全平滑。NullRHI 不渲染，无法验证相机抖动、角色网格平滑和远端旁观者的视觉表现。
- 找到了网络承载上限。本轮是一名远端乘客与一个合成平台，不是多人、多平台压测。
- 所有平台运动都适用。测试为固定水平轨道，没有覆盖旋转、任意曲线、物理挤压、墙体阻挡、垂直高速运动或运动中销毁。
- 断线重连、晚加入、所有关卡资产均已在这条动态载人场景中验证。它们需要额外测试，不能借用其他场景通过记录代替。
- 带宽或 CPU 已获得百分比收益。本轮首先验证玩法正确性，没有完成这组修改对应的性能对照。

## 7. 下一步按问题推进

1. 先定位弱网跳跃的较大校正：记录起跳、离基座、落地与校正对应的 Move 时间和基座状态，区分平台快照落后、参考系切换与角色运动差异；不关闭服务器校正或放大容差掩盖问题。
2. 固定运行条件，每组增加重复次数；打开画面验证主机与乘客视角，补充普通跳跃手感。若检查远端观察者，另增连接并记录拓扑变化，不把当前双进程试验说成已覆盖三方视角。
3. 保持动作和网络档位不变，再比较不同平台更新频率上限；同时看正确性、可见跳变与发送量，不只追求少发包。
4. 若证实离散位置快照是主要来源，再比较平台平滑或固定轨迹时间重建。不能一边保留 Actor 运动复制写根位置，一边让客户端用第二套曲线反复覆盖同一位置。

固定轨迹时间重建还需要处理突然停止、反向、时钟误差、晚加入与碰撞基座，不能把“客户端算一条插值曲线”等同于整个问题已经解决。
