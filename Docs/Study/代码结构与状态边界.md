本轮整理日期：2026-09-28，第一部分收尾更新于 2026-09-29。目标是让现有 Co-op Demo 的状态归属、数据关系与失败路径容易解释，不搭建通用状态机框架，也不引入新的平台预测方案。

## 1. 先按职责阅读

以下路径均相对于 `Source/multiplayer/`。

| 模块 | 文件 | 核心职责 |
| --- | --- | --- |
| 本地操作 | `Player/multiplayerCoopPlayerController` | 接受用户意图，维护本地操作状态，通过 RPC 请求服务器，接收失败回执 |
| 界面 | `UI/multiplayerVictoryWidget` | 展示状态、转发按钮事件；不拥有第二份操作锁 |
| 比赛规则 | `Core/multiplayerGameMode` | 权威校验、重开请求、旧 World 内的失败恢复 |
| 连接 | `Network/multiplayerGameInstance` | DS 地址连接、取消、退出、有限重连；按操作编号隔离同步通知重入 |
| 区域成员 | `Mechanisms/multiplayerPlayerOccupancyComponent` | 维护物理重叠和玩家资格，向机关通知变化 |
| 合作门 | `Mechanisms/multiplayerCoopGate` | 合并多个板的有效玩家，按规则决定开关 |

## 2. 什么时候用枚举，什么时候用 bool

`ECoopVictoryAction` 表达互斥的三种状态：

```text
Idle --请求重开--> RestartPending --拒绝/失败回执--> Idle
                              \--成功换 World--> 旧控制器随 World 清理
Idle --请求退出--> Leaving --退出失败--> Idle
                        \--回到菜单--> 旧界面随 World 清理
```

不能用多个独立 bool 拼出“正在重开又正在退出”的非法组合。状态只由 PlayerController 修改，Widget 只接收按钮是否可用及提示文字。发送请求不等于请求完成，成功也不靠客户端自行推测。

会话操作、自动重连、销毁用途仍是三个不同枚举：它们回答不同问题，强行合成一个巨大枚举会产生大量组合状态。`bLeaveInProgress` 则是跨会话清理和返回菜单两个阶段的独立限制，保留 bool 有明确含义。

只供 C++ 使用的枚举不添加 `UENUM`。需要蓝图菜单读取的 Session 操作继续保留反射；不为“看起来正式”增加无消费者的蓝图接口。

## 3. 为什么选择这些数据结构

| 结构 | 选择原因 | 不应该宣称的效果 |
| --- | --- | --- |
| `FPendingRestart` | 将请求者、旧比赛状态、跳转 URL、倒计时组成同一次请求的恢复快照，统一取出和清空 | 不是跨 World、跨网络的事务系统 |
| `FOccupantRecord` | 把一个角色的重叠次数和上次玩家资格放在一起，避免两张表不同步 | 不是把整个角色状态复制了一份 |
| `TMap<TWeakObjectPtr<ACharacter>, FOccupantRecord>` | 按角色查找/更新记录；多个碰撞体仍只算一个角色，弱引用不延长角色寿命 | 弱引用失效不会自动删除 Map 条目，也不会替你解除事件 |
| 合作门中的内联小集合 | 跨压力板去重玩家；为常见小集合提供内联存储，减少小规模临时分配机会 | 内联容量 4 不是人数上限，不代表已测得帧率提升 |

区域查找更新通常使用哈希表，但 `GetPlayerCount()` 仍会遍历有效记录。双人规模不额外维护一份容易失步的缓存计数。要扩大规模，应先测量人数查询频率和真实成本，再决定是否缓存。

区域组件关闭 Tick。控制器变化、重叠进出和销毁事件共同维护人数，不为处理“原地 Possess”增加逐帧扫描：

```text
Character 进入区域（未被控制） → 保存重叠候选，玩家人数不增加
同一 Character 被玩家 Possess → 更新资格，通知机关
原地 UnPossess               → 保留重叠记录，人数减少
最后一项重叠离开或角色销毁      → 移除记录，并解除该角色上的订阅
```

旧资格必须保存在记录里。控制器变化事件发生时，直接查询角色当前 Controller 只能得到新状态，无法据此还原变化前的人数。

## 4. 回调不是一句“通知完继续执行”

委托广播会同步调用监听者，监听者可以反过来退出房间。代码必须把它视为一个可能改变状态的边界：

```text
JoinGame：检查结果凭据和现有连接，复制选中的搜索结果
  → 开始 Joining，并分配本次操作编号
  → 广播状态：监听者可能调用 LeaveGame，取消本地加入意图
  → 广播返回：同时检查操作枚举、编号、退出限制、接口有效性
  → 只有仍拥有该操作，才向 OnlineSubsystem 提交加入
```

按值复制 `FOnlineSessionSearchResult` 是有意的快照开销，不能为了省复制改成指向共享列表的引用。操作编号区分“同一种操作”和“同一次操作”，不是线程锁。

回调清理使用自身的句柄与编号。Null 的某些 API 可以同步回调；调用返回 false 后，入口也不能把已经被回调结束或替换的操作再清理一次。重连成功先整理内部状态，最后才广播空闲，避免广播返回后拿旧状态覆盖监听者发起的新请求。

`ResultIndex` 保留名字以兼容现有蓝图，但值已经是本实例内不复用的结果凭据，而非列表行号。每次成功搜索分配新的凭据区间，加入时反查当前区间；旧列表即使第 0 行仍存在，也不能误指向新一轮的房间。菜单必须原样传回 `FmultiplayerSessionInfo.ResultIndex`，不能自行传数组下标。使用 `int64` 保存累计分配值，在超出对外 `int32` 范围前明确拒绝，不回绕复用。

操作编号只隔离本地逻辑，不能保证在线服务已经取消底层请求。为此单独保留 `Recovering`：

```text
Hosting / Finding / Joining --退出或超时--> Recovering
  Finding：请求 CancelFind；取消失败则继续等待原 Find 完成
  Hosting / Joining：保留完成回调，迟到成功只回收资源，不再连接
  有残留 Session：实际调用 DestroySession
  所有请求与资源均已收口 --> None，才允许下一次操作
```

每个请求阶段设 30 秒期限，定时器归 GameInstance，避免切 World 后丢失。恢复也超时则允许返回菜单，但保留回调和操作锁；如果服务永不响应，需要重启实例，不能把“解绑通知”伪装成“后台请求已取消”。Destroy 失败不使用 `RemoveNamedSession` 冒充资源回收，后续显式退出可重试。

这依赖 OSS 完成事件的契约，并不能识别 SDK 在全局回调中未携带的请求身份。非 Null 服务接入仍需专项验证，不因为增加超时就宣称支持所有后端。

## 5. 语法与注释约定

- 用 `enum class` 表达互斥状态，类型不发生隐式整数转换。
- 用带默认成员值的结构体保存一组相关数据，减少遗漏初始化和部分清空。
- 只读输入使用 `const`；大对象通常按 `const&` 传入，但越过可重入边界的数据有意按值保存。
- `MoveTemp(PendingRestart)` 转移旧快照后立即重置成员：先释放旧操作，再恢复和通知；不在所有赋值上机械添加移动语义。
- 局部重绑定检查的 lambda 立即执行，因此可以按引用捕获临时集合；不能把这种引用捕获照搬给异步回调。
- 持有的 UObject 使用 UE 对象指针机制；观察外部对象使用弱引用；Slate 控件使用共享指针，并在 `ReleaseSlateResources` 清理。
- 公共接口注释说明职责、前置条件和结果；实现注释重点解释顺序、所有权与取舍，不逐行翻译语法。
- 中文注释服务于理解；UE 宏、API 名及用于机器解析的日志标记保持稳定，不为了中文化破坏协议或检索。

随后补完了原先未处理的两项钥匙一致性问题：

- 附着只由服务器写、客户端由 Actor 内建附件复制恢复；Holder/Installed 的 RepNotify 只刷新状态，不再重复挂接。掉落先分离、最后恢复碰撞，避免同步拾取回调完成后又被旧掉落代码分离。
- 两种插槽入口共用提交顺序：占用插槽 → GameMode 校验进度 → 安装或消费钥匙 → 关闭触发区 → 发布进度。失败保留钥匙并释放插槽门闩，消费成功则在 EndPlay 清理携带关系。

`TFunctionRef<bool()>` 只借用一个同步钥匙操作，不保存回调、不建异步队列；`TGuardValue<bool>` 在作用域结束时恢复登记门闩，防止销毁或进度通知中的嵌套登记。这是服务器当前调用链的提交约束，不是多个 Actor 在网络上的原子复制保证。
